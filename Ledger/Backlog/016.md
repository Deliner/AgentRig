# B016 — Приёмка фичи по критериям и результатам проверок

## Context

Наличие тестов и успешный запуск отдельных проверок не доказывают выполнение всей карточки. Обвязка должна обнаруживать пропущенные требования и потерянные связи, сохраняя короткий цикл разработки. Назначение тестов принадлежит модулям проекта; карточки остаются описаниями требуемого поведения.

## Proposal

Согласованный критерий → способ проверки в реестре модуля → фактический результат → проверка готовности фичи.

VAC → затронутые проверки и проверка связей.
Merge → проверки затронутых фичей или модулей и ревью, если включено.
Завершение фичи → проверка свидетельств по всем обязательным критериям.

**К1. Каждый критерий имеет способ проверки.**

Используются идентификаторы критериев из согласованной версии карточки. Для каждого указан автоматический способ проверки через настроенную команду либо порядок ручной приёмки с наблюдаемым признаком успеха.

Связи находятся в реестрах модулей. Текст требований не копируется в другую спецификацию.

Приёмка: при проверке готовности обнаруживаются пропущенный критерий и отсутствие способа его проверки. Ссылка на произвольный тест сама по себе не подтверждает требование.

**К2. Согласованные постоянные свойства получают исполняемую защиту.**

Свойство, которое должно сохраняться при дальнейших изменениях, связывается с существующим механизмом инвариантов: записью, конкретным тестом и обязательной проверкой, запускающей его в необходимых случаях.

Приёмка: прослеживается связь от свойства до исполняемого теста и условий запуска. Файл теста без подключения к проверкам не считается защитой. Не каждый тест и не каждый критерий становятся инвариантом.

**К3. Проверка готовности выполняется одной штатной операцией.**

Агент запускает проверку готовности фичи. Обвязка сопоставляет критерии, связи и фактические результаты; использует применимые свидетельства и выполняет недостающие автоматические проверки через существующие команды.

Ответ по каждому критерию: подтверждён / нарушен / не проверен, с причиной и ссылкой на свидетельство. Delivery сохраняет краткий итог и ссылки.

Приёмка: агенту не нужно вручную собирать отчёты, пересказывать логи или писать скрипт приёмки. Подходящие результаты уже выполненных проверок используются повторно.

**К4. Свидетельство относится к проверяемому состоянию и условиям.**

Обвязка различает наличие проверки, её выполнение и результат. Пропуск запуска, недоступное необходимое окружение и неприменимый прежний результат не дают подтверждения.

Для ручной приёмки сохраняется фактически наблюдавшийся результат. Обычной проверке достаточно настроенной команды; специальные условия указываются, когда влияют на достоверность, по [B004, К11](004.md).

Приёмка: инструкция «проверить вручную» не заменяет наблюдение. Успешная нерелевантная команда или запуск в неподходящем окружении не подтверждают критерий. Причина отсутствия проверки сообщается явно.

**К5. Неполная приёмка препятствует завершению фичи.**

Переход к завершению → обвязка проверяет все обязательные критерии согласованной карточки → допускает завершение либо показывает оставшуюся работу.

Запись агентом успешного статуса без необходимых свидетельств не обходит проверку.

Приёмка: нарушенный или непроверенный обязательный критерий препятствует завершению. После получения необходимых подтверждений переход допускается. Ослабление критериев требует согласованного изменения требований.

**К6. Включённое ревью оценивает достаточность проверок.**

Перед merge существующее ревью сопоставляет критерий, способ проверки и свидетельство: различает ли проверка требуемое поведение и его нарушение. Используются операция, снимок и порядок повторного ревью из [B015](015.md).

При выключенном ревью модель не вызывается и её отчёт не требуется. Проверки связей, результатов и полноты приёмки продолжают действовать; отключение смыслового ревью обозначается отдельно.

Приёмка: замечание включённого ревью указывает конкретный критерий и недостаточность проверки. Успешный, но более слабый тест не подменяет требование. Формальная согласованность связей не объявляется доказательством смысловой достаточности.

**К7. Объём приёмки соответствует границе работы.**

VAC подтверждает собственный результат. Полная приёмка карточки требуется при завершении фичи. Промежуточный коммит не обязан закрывать все её критерии.

Приёмка: корректный промежуточный VAC допускается при незавершённой фиче; его успех не позволяет объявить готовой всю фичу. Область запуска тестов определяется К10.

**К8. Модуль владеет реестром проверок своей функциональности.**

Основная связь: проект → модуль → фича → критерий → тесты.

Реестр содержит назначение теста или смысловой группы, основание проверки, существующую команду и условия обязательного запуска. Основанием служат критерий карточки, инвариант или явно описанный контракт компонента. Завершённые фичи доступны через архивные карточки.

Тесты располагаются рядом с проверяемой функциональностью. Реестры принадлежат проекту и полезны без AgentRig; конфигурация рига определяет их обнаружение и выполнение.

Допускаются группы без ручной регистрации каждого параметризованного случая и связи нескольких тестов с несколькими требованиями. Карта выбора затронутых проверок использует эти же сведения. Риг объединяет реестры автоматически; агент читает нужную часть модуля.

Приёмка: связи нескольких модулей, группы и архивные основания доступны без переноса реестров в конфигурацию рига и без дублирования требований.

**К9. Линтер проверяет идентификаторы карточек и критериев, а затем все ссылки на них на фактическом снимке VAC.**

Правила идентификаторов:

- Карточка имеет устойчивый ID, согласованный между её заголовком, файлом и индексом. Один ID не принадлежит двум карточкам, включая архив.
- Критерий приёмки имеет ID внутри карточки. Повторы внутри карточки запрещены. Ссылка указывает пару «карточка + критерий», например `B016 / К5`.
- Каждая ссылка разрешается в существующее основание. Проверяются связи из Plan, реестров тестов и других предусмотренных записей. Существования карточки недостаточно, если нужного критерия в ней нет.
- Перестановка критериев сохраняет их ID. Перенос карточки в архив сохраняет её идентичность и доступность связанных требований.
- Удаление не оставляет висячих ссылок. Если критерий или карточка удалены, оставшиеся ссылки вызывают нарушение.

Реестры сопоставляются со списком тестов, обнаруженных тестовым инструментом. Проверяются:

- регистрация обнаруженных тестов у соответствующего модуля;
- существование указанных оснований и зарегистрированных тестов;
- однозначность идентификаторов;
- актуальность ссылок после переносов и удалений;
- существование связанных команд и условий запуска.

Снимок VAC → существующая проверка памяти и связей → проверка ID и разрешение ссылок → конкретное нарушение и skill → блокировка → исправление → повторная проверка. Агенту не нужно готовить отдельный отчёт или вручную запускать ревью идентификаторов.

Skill направляет установить назначение теста и восстановить связь либо удалить действительно ненужный тест. Отсутствие регистрации не доказывает бесполезность; формальная привязка всего набора к общей карточке не доказывает осмысленность.

Приёмка: непривязанный или удалённый тест, несуществующее основание, неоднозначный ID и сломанная ссылка обнаруживаются. Проверяются дубликаты ID, расхождение заголовка с индексом, отсутствующий критерий и ссылка на удалённую карточку. Перестановка критериев и корректное архивирование сохраняют связи. Корректные связи проходят. Полнота выполнения критериев проверяется при завершении фичи.

Линтер проверяет идентичность и целостность ссылок. Подмену смысла требования при сохранённом ID он сам по себе не доказывает — для этого остаются согласованная версия карточки и включённое ревью.

**К10. Запуск использует три области проверок.**

| Событие | Область |
|---|---|
| Коммит / VAC | Проверки, связанные с изменёнными и новыми файлами. |
| Merge | Все проверки затронутых фичей или модулей по совокупному изменению ветки. |
| Явный запуск «всё» | Полный набор проекта. |

Для удалённых файлов учитывается прежняя принадлежность. Ответ кратко показывает изменённые файлы, выбранные области и проверки.

Приёмка: три режима выбирают ожидаемые наборы, включая новые и удалённые файлы и предыдущие VAC ветки. Полный набор не запускается автоматически вместо выбора затронутых проверок.

**Границы и неизвестное.** Используются существующие память, каталог команд, runner, линтер и ревью. Отдельная система отчётов, расчёта стоимости или управления подготовкой не вводится. Безошибочность смысловой оценки не гарантируется.

До реализации нужно определить поддерживаемые способы обнаружения тестов, правила применимости прежних результатов и обработку файлов без установленной связи с проверками.

## Expected benefit

Тесты имеют понятное назначение, связи сохраняются при изменениях, а завершение фичи опирается на подтверждённые критерии. Агент получает готовый результат приёмки без ручного собирания доказательств.
