# B004 — Все правила линтера для семи языков и проверка их реальной работы

## Context

Правила AgentRig должны работать для Python, TypeScript, Rust, JavaScript, Go, Java и Kotlin, включая смешанные проекты. Поддержка подтверждается исполнением проверок. Выбранные стандартные языковые линтеры дополняют собственные правила.

## Proposal

Настройка языков, правил и параметров → проверка конфигурации и применимости → запуск выбранных проверок → фактический результат и инструкция исправления.

Изменение реализации линтера → выбор связанных эвалов → запуск CLI на подготовленных примерах → сравнение с заранее заданными ожиданиями.

**К1. Все действующие правила поддерживают семь языков.**
Набор фиксируется по действующему каталогу при выборе карточки в реализацию. Исходный состав: размеры файлов и каталогов, именованные условия, длина функций, количество параметров, архитектура директорий. Новые правила не расширяют текущую работу автоматически.

Приёмка: для каждой пары «правило — язык» работает проверка; запись в каталоге при отсутствующей реализации недостаточна. Сохраняются поведение Rust/Python и поддержка JSX/TSX.

**К2. Особенности языка учитываются без потери назначения правила.**
Описаны поддерживаемые расширения и способы подсчёта функций, методов, конструкторов, замыканий и параметров, где они применимы. Значения по умолчанию не ослабляются ради объявления поддержки.

Приёмка: примеры языковых конструкций дают ожидаемые измерения; пользовательские параметры правила применяются по К9.

**К3. Архитектурная проверка различает нарушение и неполный анализ.**
Проверяются архитектурные описания, локальные зависимости, публичные границы и циклы с учётом импортов, пакетов и модулей языка.

Приёмка: запрещённая связь определяется как нарушение. Невозможность разобрать конструкцию или разрешить зависимость обозначается как неполный анализ и не выдаётся за отсутствие нарушений. Ограничения описаны явно и не заменяют поддержку целой пары «правило — язык».

**К4. Заявленные возможности соответствуют фактическим результатам.**
Каталог, проверка конфигурации, объяснение выбора и документация соответствуют реализации. Встроенный линтер и отдельный `agentrig-lint` согласованы по измерениям и нарушениям. Исключения, уровни ошибок и параметры, включая пороги, сохраняются.

Приёмка: диагностика указывает правило, место, подходящий skill и команду повторной проверки. Языковые особенности учитываются без семи дублирующих комплектов skills.

**К5. Эвалы запускаются в отдельном воспроизводимом окружении.**
Случаи находятся в `tooling/worker/evals/`. Документированная команда Just запускает весь набор либо выбранный язык или правило.

Приёмка: запуск работает из чистого checkout с указанными зависимостями, без платных API и интерактивной сессии агента. Эвалы отделены от потребительских примеров и экспериментов с моделями.

**К6. Каждая пара проверяется настоящим запуском CLI.**
Предусмотрены корректный пример, намеренное нарушение и исправленная версия. Проверяются код завершения, существенные поля диагностики и отсутствие неожиданных нарушений.

Приёмка: ожидания заданы по контракту правила независимо от полученного вывода. Простое обновление ожидаемого результата не считается исправлением реализации.

**К7. Проверяются границы и отрицательные случаи.**
Набор включает пороговые значения, обычные конструкции языка, некорректные и неподдерживаемые исходники. Для архитектуры — отсутствующие описания, запрещённые зависимости, нарушение приватности, циклы и исправления.

Приёмка: случаи дают предусмотренные результаты в независимых потребительских проектах и смешанных языковых деревьях.

**К8. Нужные эвалы выбираются автоматически на границах проверки.**
Выбор следует существующей карте связей и [B016](016.md):

- **VAC:** проверки, связанные с изменёнными и новыми файлами.
- **Merge:** проверки затронутых фичей или модулей по изменениям всей ветки.
- **Явное «всё»:** полный набор.

Добавление и перенос случаев учитываются в выборе проверок. Изменение общей реализации затрагивает все связанные с ней случаи.

Приёмка: поломка правила обнаруживается соответствующим эвалом; вывод указывает случай и расхождение, команда завершается неуспешно. Намеренно ошибочные примеры изолированы без отключения проверок обычного кода и самого окружения. Временные результаты не попадают в Git.

**К9. Параметры правила настраиваются отдельно для каждого языка.**
В конфигурации правила пользователь задаёт общие значения и языковые переопределения. Переопределять можно отдельные поддерживаемые параметры; остальные сохраняют общие значения.

В смешанном проекте к каждому файлу применяются настройки его языка. Пороги предупреждений и ошибок также настраиваются независимо. Объяснение проверки показывает итоговые значения и источник каждого из них.

Приёмка: одно правило с разными параметрами для двух языков работает согласно этим настройкам. Изменение переопределения одного языка не влияет на остальные. Без переопределения используются общие значения. Неподдерживаемый параметр вызывает ошибку конфигурации и не игнорируется молча.

**К10. Стандартные проверки используют существующие точки запуска.**
Пользователь выбирает стандартные линтеры и проверки форматирования. Риг подключает их через каталог команд, сохраняя проектные настройки. Они дополняют собственные правила.

Приёмка: нарушения собственной и выбранной стандартной проверки видны в результате. Отсутствующий инструмент не считается успешно выполненной проверкой.

**К11. Отчёт показывает фактическое покрытие и доступность.**
Для языков и окружений видны подключённые проверки, области применения, отключения, отсутствие поддержки и невозможность выполнения с причинами. Готовность подключения отличается от результата проверки кода.

Обычная проверка требует одного запуска настроенной команды. Особые условия фиксируются в существующем реестре модуля по [B016](016.md) только при необходимости. Подготовка не дублируется; дополнительных документов перед каждым запуском не требуется.

Приёмка: недоступный инструмент, исключённые файлы и отключённая проверка различимы. Отсутствующее условие оставляет проверку невыполненной; неизвестная ошибка не объявляется автоматически проблемой окружения. Неподходящее окружение не подставляется молча. После изменения настроек повторная проверка обновляет отчёт.

**Детерминированные опоры:** проверка конфигурации; снимок изменений; карта выбора проверок; фиксированные входы и ожидания эвалов; код завершения и диагностика CLI.

**Границы и неизвестное.** Используются существующие runner, кандидатные бинарники, конфигурация и тестовая инфраструктура. Отдельный сервис, универсальный фреймворк и дублирование достаточных тестов не требуются. Настройка проекта относится к [B006](006.md); отдельный реестр покрытия не создаётся.

Конкретные стандартные инструменты нужно определить до реализации. Реакция допуска на неполный архитектурный анализ согласуется в [B015](015.md); здесь такой результат не считается успешной проверкой.

## Expected benefit

Агент получает работающие правила для выбранных языков и точное направление исправления. Изменения самого линтера проверяются автоматически без ручных экспериментов и лишних полных прогонов.
