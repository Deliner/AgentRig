# B004 — Complete lint coverage and executable language evaluations

## Context

Moved from [P013 at the migration base](https://github.com/Deliner/AgentRig/blob/f6cd86efbae8ec501759f0c250b9bd4b76e300d7/Ledger/Plan/013.md) under the user's current-execution Plan rule. No implementation or priority is implied. The following source context records earlier requests and observations; it is not current verification. Reassess related ideas and actual prerequisites when selected.

The user requested ALL current rules for Python, TypeScript, Rust, JavaScript, Go, Java and Kotlin after the architecture improvements. During planning the user added a requirement to deliver a test environment together with the rules and keep its evaluations in a separate directory. tooling/worker/evals/ is the planned product-owned location; implementation chooses the smallest cohesive internal layout.

At revision 7721e83 the catalog contains six rule kinds. Rust and Python advertise three syntax measurements plus architecture; JavaScript, TypeScript and TSX advertise architecture only. Go, Java and Kotlin have no registered handlers. The two language-independent structural measurements do not need separate parsers. This is baseline evidence, not implementation acceptance.

## Proposal

Extend all current AgentRig lint rules to Python, TypeScript, Rust, JavaScript, Go, Java and Kotlin. Deliver a dedicated executable evaluation environment alongside the language support, using the ownership and development flows established by [B003](003.md). This covers AgentRig's own rules, not integration of every third-party linter.

Retained requirements to reassess when selecting this idea:

- Cover every current rule for all seven languages: nonblank-lines, directory-entries, named-if-condition, function-lines, parameter-count and directory-architecture. Reconcile the actual catalog at implementation time without omitting current rules. Keep language-independent measurements shared.
- Preserve Rust/Python behavior, complete JavaScript/TypeScript syntax measurements, and add Go, Java and Kotlin handlers. Preserve existing variants including JSX and TSX. Document supported extensions and language-appropriate semantics for conditions, functions/methods, constructors, closures, receivers and parameters where applicable. Do not weaken thresholds or leave whole rule/language pairs unsupported to claim completion.
- Architecture checks cover inventories, local dependencies, public/private boundaries and measured cycles in all seven languages. Support the applicable package/module/import conventions. Unsupported or unresolved forms produce explicit incomplete-analysis diagnostics, never verified absence of dependencies. Document analysis limits without using them as a substitute for required language support.
- Keep capability declarations, configuration validation, rule catalog/examples, selection explanations and documentation consistent with implemented measurements. Embedded agentrig lint and standalone agentrig-lint agree. Preserve exclusions, severity settings, thresholds and existing consumer behavior.
- Canonical repair skills provide applicable, idiomatic guidance for these languages without seven duplicate instruction sets. Findings include rule identity, source location or directory, applicable skill and executable rerun guidance.
- Put the evaluation environment and its maintained cases under tooling/worker/evals/, with meaningful language/rule ownership and architecture inventories. Keep these lint product evaluations separate from consumer examples and agent/model evaluation infrastructure. Reuse the existing test runner and candidate binaries; do not introduce a separate evaluation service or general framework.
- Expose a documented command through the existing command catalog/Just interface to run all evaluations or a selected language/rule subset. A clean checkout can prepare and run it using documented prerequisites; no paid API or authorized interactive agent session is needed.
- Exercise every rule/language pair through actual CLI execution in isolated consumer directories. Include valid examples, intentional violations and repaired equivalents; verify exit status and stable semantic diagnostic fields such as rule, path, location and measured value where applicable. Assert absence of unexpected findings as well as presence of expected findings. Parser registration, mocked findings or output-file existence alone are not evidence.
- Include applicable threshold boundaries, ordinary language constructs and explicit malformed/unsupported-source outcomes. Architecture cases exercise missing inventories, forbidden/private edges, cycles and valid repairs. Include real consumer execution for newly supported languages and mixed-language inventory behavior. Declare expected diagnostics independently of the output being tested; broad snapshot replacement must not redefine a failing case as correct.
- Intentionally invalid fixtures are evaluated in isolated projects with their own configuration. Their storage and any necessary narrow fixture exclusions are explicit, without disabling checks on the runner or ordinary maintained product sources. Temporary evaluation outputs stay out of version control.
- Evaluation failures make the command fail and report the case and mismatch. Document how to add and rerun a case. Maintain affected commit groups for evaluators, fixtures and relevant implementations; run the complete evaluation set as part of full integration verification. Keep low-level tests where useful without duplicating the same scenarios unnecessarily.
- Extend existing language and architecture owners with the smallest sufficient implementation. The feature remains incomplete while a current rule is wholly unsupported for a requested language or its evaluation coverage only advertises support without exercising detection.

## Expected benefit

The user configures the same rule catalog for any requested language or a mixed-language project and can run evaluations proving that violations are detected, valid examples are accepted and repaired examples stop producing the finding. Declared support must include real measurements rather than merely accepting an extension.
