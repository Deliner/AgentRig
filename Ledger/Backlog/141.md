# B141 — Значения в коде только через именованные константы

## Context

- 2026-11-14 пользователь: «подумать потом о правиле по выносу всех там магических строк, магических символов, чисел и
  так далее в константы, чтобы все эти значения были именованными константами. Не знаю, как их лучше будет
  структурировать в репозитории, но пока давай пусть это все будет именованными константами».
- D073 не ввёл правило против магических чисел, потому что по синтаксису их не отличить от законных. Если именем
  обязано быть каждое значение, отличать не нужно.
- Правило `embedded-text` уже выносит из кода в файлы строки длиннее 20 строк.
- Пользователь сохранил карточку с открытыми вопросами и предложением агента по ним, чтобы обдумать их позже.

## Proposal

Строки, символы, байты и числа в коде пишутся только через именованные константы.

- **AC1. Находка на значение.** Lint выдаёт ошибку на каждый литерал строки, символа, байта или числа вне определения
  `const` или `static`. Находка называет файл, строку, сам литерал и навык.

  Проверка: `if retries > 3`, `split(',')` и `open("config.yaml")` дают по находке. `const MAX_RETRIES: u32 = 3;` и
  `if retries > MAX_RETRIES` находок не дают.
- **AC2. Где Rust требует литерал, проверки нет.** Это аргументы атрибутов, строка формата в `format!`, `println!`,
  `write!` и подобных макросах, аргументы `include_str!`, `concat!`, `env!` и подобных макросов.

  Проверка: `#[cfg(feature = "x")]`, `format!("{name}")` и `include_str!("a.txt")` находок не дают.
- **AC3. Навык.** Находка ведёт на навык. Он объясняет, как назвать константу по смыслу значения, а не по самому
  значению, и что делать, если Rust требует там литерал.
- **AC4. Риг и проекты.** Правило есть у самого рига и в Rust-проектах после `init`. Код рига приведён к правилу.

  Проверка: в проекте после `init` литерал в коде даёт находку. Гейт рига проходит.

**Границы.**

- Где лежат константы и как раскладывать их по репозиторию, карточка не задаёт. Это обсуждается отдельно.
- Смысл имени правило не проверяет: константа `THREE = 3` пройдёт.
- Текст внутри строки формата правило не проверяет, потому что Rust требует там литерал.
- Длинные тексты по-прежнему уходят в файлы по `embedded-text`.

**Открытые вопросы.**

1. Нужны ли исключения для простейших значений: `0`, `1`, пустой строки, `true` и `false`?
2. Проверять ли тестовый код?
3. Только Rust или Python тоже?

**Предложение агента по открытым вопросам, 2026-11-14.**

1. Исключить `0`, `1`, `true` и `false`. Имя вроде `ONE` для `len() - 1` или `v[0]` ничего не добавляет, а таких мест
   очень много. Пустую строку тоже исключить.
2. Тесты не проверять, как у `embedded-text` и большинства правил. Входные данные теста и есть пример, и имя для
   каждого из них превратит тест в список констант. Ожидаемые значения в тестах можно оставить литералами по той же
   причине.
3. Начать с Rust, как в `embedded-text`. Python можно добавить следующей карточкой.

**Неизвестное.** Сколько находок правило даст на Project и voxel-rust. Замер делается при поставке.

## Expected benefit

Каждое значение в коде имеет имя, которое говорит, что оно значит. Значение, которое используется в нескольких
местах, меняется в одном.
