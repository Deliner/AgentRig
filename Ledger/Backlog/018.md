# B018 — Архитектурный тип у фич нижнего уровня

## Context

В `architecture.yaml` фичи нижнего уровня указывается архитектурный тип. Тип
требует определённых частей внутри фичи и задаёт направление зависимостей между
ними, а линтер это проверяет. У составных фич типа нет: они почти без кода и
состоят из других фич. Фича внутри `shared` тоже может быть фичей нижнего уровня
со своим типом. Источник: [Requests.md](../Requests.md), записи от 2026-10-26 и
2026-10-27. Карточка согласована пользователем 2026-10-27.

## Proposal

**А1. Какие директории считаются фичами.** В настройках правила
`directory-architecture` задаётся корень фич (здесь это `Project`).

- Каждая поддиректория корня — фича первого уровня.
- Директория без типа — составная фича. Все её поддиректории, кроме `tests`,
  тоже фичи.
- `shared` устроена так же, как остальные директории.

**А2. Тип обязателен у фичи нижнего уровня.** Фича нижнего уровня — это фича
без вложенных фич: у неё либо нет поддиректорий, либо есть только `tests`. Такая
фича указывает `type` в своём `architecture.yaml`. Ошибкой с путём к контракту
считается:

- тип не указан;
- значение не из списка ниже;
- `type` указан у части фичи или у директории вне корня фич.

**А3. Части фичи по типу.**

| Тип | Части (снаружи → внутрь) |
| --- | --- |
| flat | частей нет, только файлы |
| layered | presentation → application → domain → infrastructure |
| hexagonal | adapters → ports → domain |
| onion | infrastructure → application → domain |
| clean | frameworks → adapters → use_cases → entities |
| custom | любые поддиректории |

Все части своего типа обязательны. Другие поддиректории, кроме `tests`,
запрещены. Если части не хватает или есть лишняя директория, это ошибка с
названием типа и директории. custom — произвольное устройство: тип ничего
дополнительно не проверяет.

**А4. Направление зависимостей.**

- Файл внутри части может использовать свою часть и части правее в таблице.
  Перескакивать через часть можно.
- Файлы в корне фичи (точка входа, подключение модулей) могут использовать любую
  часть. Части не используют корневые файлы.
- От `tests` не зависит никто.
- Нарушение — это ошибка с файлом, строкой и самой связью, например
  «hexagonal: domain → adapters».
- Тип не ограничивает зависимости на другие фичи. Проверка циклов между
  директориями остаётся как сейчас.
- Для flat и custom тип направление не проверяет, работает только общая
  проверка циклов.

**А5. Описание для пользователя.**

- README архитектурного линтера перечисляет типы, их части и правило
  направления.
- Навык `refactor-large-directory` объясняет, как выбрать тип по фактическому
  устройству фичи и как исправлять ошибки. Менять тип только ради прохождения
  проверки нельзя.

**А6. Этот репозиторий.** Каждая фича нижнего уровня в `Project` получает тип по
текущему устройству: flat, если в ней только файлы и `tests`, иначе custom.
Линтер проходит на всём репозитории. Перестройка кода под hexagonal и другие
типы в эту карточку не входит.

**Границы.**

- Пересечение с [B003](003.md) и навыком: сейчас там сказано, что отдельная
  папка на каждую роль не нужна. Для layered, hexagonal, onion и clean это
  меняется: части с фиксированными именами становятся обязательными. У flat и
  custom свобода сохраняется.
- Не проверяется, что в составной фиче почти нет кода.
- Остальная схема вложенных фич (B003) сюда не входит.

## Expected benefit

По типу фичи сразу видно её устройство и где искать нужную часть. Линтер не даёт
зависимостям идти против схемы.
