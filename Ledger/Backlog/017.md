# B017 — Управление Ledger через MCP и контролируемое размещение Markdown

## Context

Память проекта должна иметь понятное размещение, единый формат и согласованные реестры. Агенту нужны конкретные операции для работы с содержанием и состояниями карточек.

## Proposal

Агент вызывает операцию MCP → сервис проверяет допустимость → обновляет карточки, реестры и контрольные хеши → возвращает результат.

Область управления определяется существующей настройкой каталога памяти. Сейчас это Ledger.

**К1. Реестры и карточки доступны через общий набор операций.**

Обслуживаются Backlog, Plan, Decisions, Invariants, Archive и Docs.

| Операция | Вход → результат |
|---|---|
| **Получить список реестров** | Запрос → названия и назначение реестров. |
| **Получить список записей** | Реестр → ID, названия, ссылки и предусмотренные состояния, даты, порядок. |
| **Прочитать карточку** | Реестр и ID → содержимое карточки и сведения записи. |
| **Добавить карточку и запись** | Реестр и содержательные поля → согласованно созданные карточка и запись. |
| **Изменить карточку и запись** | Реестр, ID и изменения → согласованное обновление с сохранением идентичности. |
| **Удалить карточку и запись** | Реестр и ID → согласованное удаление либо конкретная причина недопустимости. |

Списки возвращают краткие сведения; полное содержимое получается отдельным чтением.

**Docs — важные документы.** Индекс находится в `Ledger/Docs.md`, карточки — в `Ledger/Docs/`. Используются общие операции реестров. Отдельные команды записи State, решений, инвариантов или произвольных видов документов не вводятся.

**Tmp — вспомогательные и временные материалы.** Карточки находятся в `Ledger/Tmp/`, отдельного реестра нет. Доступны пять операций:

- **Получить список имён файлов:** запрос → имена без содержимого карточек.
- **Добавить:** имя и содержимое → созданная карточка.
- **Прочитать:** имя → содержимое.
- **Удалить:** имя → удалённая карточка.

Приёмка: операции Docs согласованно обслуживают индекс и карточки. Операции Tmp работают с карточками без создания записей реестра.

**К2. Plan предоставляет операции управления выполнением.**

| Операция | Вход → результат |
|---|---|
| **Добавить карточки в Plan** | Выбранные карточки Backlog, версии, порядок и зависимости → записи «ожидает». |
| **Получить состояние карточки** | ID → состояние, даты, блокер и расположение. |
| **Поменять порядок** | Новый порядок ID → обновлённая последовательность; активная карточка сохраняется. |
| **Добавить перед текущей** | Выбранная карточка Backlog → вставка перед текущей без переключения. |
| **Приостановить текущую** | Прогресс и следующий шаг → состояние «на паузе». |
| **Возобновить карточку** | ID → состояние «в работе» и сохранённый контекст. |
| **Переключиться на выбранную** | Целевой ID и текущий контекст → текущая приостанавливается, выбранная активируется. |
| **Переключиться на предыдущую** | Текущий контекст → переключение на предыдущую по порядку Plan; отсутствие предыдущей вызывает отказ. |
| **Обновить прогресс** | ID, результаты, проверки и следующий шаг → актуальные сведения о выполнении. |
| **Зафиксировать блокировку** | ID, причина и условие продолжения → состояние «заблокирована». |
| **Снять блокировку** | ID и сведения об устранении причины → возможность продолжения без автоматического запуска. |
| **Завершить карточку** | ID и свидетельства → проверка [B016](016.md); завершение и автоматическое архивирование после успешного merge её ветки. До merge карточка остаётся Active. |
| **Переместить карточку в архив** | ID и свидетельства завершения → проверка приёмки и факта успешного merge её ветки, переход в Archive. До merge операция не допускается. |
| **Отложить выполнение** | Решение об отсрочке и контекст → сохранение продолжения в Backlog и удаление записи из текущего Plan. |

Одновременно активна максимум одна карточка. Переключения сохраняют прогресс и Git-состояние. Проверяются действующие ограничения зависимостей.

Готовность результата сама по себе не завершает карточку: она остаётся Active до успешного merge её ветки. Успешный merge → MCP переводит карточку в «завершена» и автоматически переносит её в Archive с обновлением реестров и хешей. Неуспешный или отменённый merge не завершает и не архивирует карточку.

Приёмка: каждый переход даёт указанное состояние и сохраняет необходимые сведения. Последний VAC выполняется при Active; до успешного merge карточка не архивируется, после успешного merge завершение и архивирование происходят автоматически. Архивирование не позволяет скрыть незавершённую работу.

**К3. Состояния и даты карточек доступны явно.**

Состояния Plan: **ожидает, в работе, на паузе, заблокирована, завершена**.

После снятия блокировки начатая карточка остаётся на паузе, неначатая — ожидает. Все карточки Archive завершены. После архивирования запрос по прежнему ID возвращает состояние и архивное расположение.

| Реестр | Поля дат |
|---|---|
| Backlog | Дата создания в Backlog. |
| Plan | Дата создания в Backlog; дата первого начала работы. |
| Archive | Дата создания в Backlog; дата завершения. |

Даты фиксирует сервис. До начала работы второе поле Plan пусто. Дата завершения соответствует успешному merge, завершившему карточку. Редактирование, перестановка, пауза и возобновление не сбрасывают ранее зафиксированные даты. При переносе существующих материалов известные даты сохраняются; вместо неизвестных исторических дат записывается текущая дата переноса.

Приёмка: состояния различимы, происхождение карточки сохраняется; в Plan и Archive ровно по два указанных поля даты.

**К4. Сервис обеспечивает формат и согласованность.**

MCP управляет форматированием, идентификаторами, индексами, архитектурным учётом и обязательными ссылками. Общие операции соблюдают действующие правила соответствующего реестра, включая согласование требований и неизменяемую историю.

Ответ содержит результат, затронутые ID и пути либо конкретную причину отказа. Частичное изменение не объявляется успешным. Сервис не дописывает требования самостоятельно.

Приёмка: карточки соответствуют индексам, ссылки разрешаются, общая операция изменения не обходит ограничения переходов.

**К5. Изменения Ledger проходят через MCP.**

Распознаваемая прямая запись Markdown в Ledger → хук отклоняет действие и указывает операцию MCP.

Чтение, поиск и просмотр остаются доступными напрямую. Обычное редактирование вне Ledger не требует `just write`.

После каждой записывающей операции MCP обновляет все затронутые файлы, вычисляет их хеши и записывает хеш в каждый файл и в собственное хранилище MCP.

Эталоны хешей хранятся в зашифрованном виде в собственной директории MCP внутри проекта и коммитятся в Git вместе с соответствующими файлами. Линтер использует эталоны из той же проверяемой версии Git. Отдельный механизм защиты доступа к директории эталонов не требуется.

Ключ шифрования встроен в поставляемый бинарник MCP. Поставляемый бинарник или комплект бинарников обеспечивает запись и проверку эталонов без отдельной настройки ключа пользователем.

Хеш вычисляется по содержимому файла **без самого поля хеша**, иначе возникает самоссылка. Это распространяется на все `.md` в Ledger: карточки, индексы, Docs, Tmp и архив. При удалении файла сервис обновляет соответствующий учёт.

Операция **«Проверить Ledger»** и проверки VAC/merge сопоставляют формат, состав, ID, ссылки и хеши. Линтер самостоятельно вычисляет хеш содержимого и сравнивает три значения:

1. Фактический хеш содержимого.
2. Хеш, записанный внутри файла.
3. Эталон этого файла, сохранённый MCP.

Любое расхождение, отсутствие хеша или эталона → ошибка с указанием файла → требование прочитать skill → исправление через MCP → повторная проверка.

Сравнение с сохранённым эталоном MCP обнаруживает изменение файла, в том числе пересчёт и подмену встроенного хеша.

Приёмка: изменения, добавления и удаления, расходящиеся с учётом MCP, обнаруживаются. Пересчёт только встроенного хеша не узаконивает ручную правку. Эталоны представлены в Git в зашифрованном виде; при проверке другой версии используются соответствующие ей эталоны. После установки бинарной поставки MCP записывает, а линтер проверяет эталоны без отдельной настройки ключа.

- Изменён текст, прежний хеш оставлен → нарушение.
- Изменены текст и встроенный хеш → нарушение относительно эталона MCP.
- Изменение выполнено через MCP, все три значения совпадают → проверка проходит.
- Записывающая операция затронула карточку и индекс → хеши обновлены у обоих.

**К6. Линтер запрещает Markdown вне Ledger, кроме явных исключений.**

В конфигурации правила задаётся разрешённый список имён. Предлагаемый минимальный список:

`README.md`, `LICENSE.md`, `License.md`, `AGENTS.md`, `Agents.md`, `SKILL.md`.

Проверяется фактическое расположение файлов независимо от способа создания. Другие `.md` вне Ledger вызывают нарушение.

Приёмка: Markdown в Ledger разрешён; файл с разрешённым именем вне Ledger разрешён; другой Markdown вне Ledger обнаруживается. Изменение настроенного списка меняет результат проверки.

**К7. Skill направляет к правильной операции и размещению.**

Нарушение → координатор [B002](002.md) требует skill → агент определяет назначение материала → выбирает соответствующий реестр, Docs для важных документов или Tmp для вспомогательных материалов → исправляет через MCP.

Skill объясняет операции и запрещает расширять исключения либо переименовывать материал в README только ради прохождения проверки.

Приёмка: чтение skill не снимает нарушение; корректное состояние проходит повторную проверку.

**К8. Коммит VAC допускается только при текущей карточке Active.**

Попытка коммита VAC → pre-commit хук проверяет фактическое состояние текущей карточки в Plan → при Active («в работе») допускает продолжение остальных проверок коммита.

Если текущей карточки нет, её состояние отличается от Active или состояние не удалось установить, коммит блокируется. Сообщение указывает причину и направляет выбрать либо возобновить карточку через MCP. Хук не активирует карточку автоматически.

Приёмка: Active проходит эту проверку; «ожидает», «на паузе», «заблокирована», «завершена», отсутствие текущей карточки и невозможность определить её состояние блокируют коммит. Прохождение этой проверки не отменяет остальные условия допуска VAC.

**К9. Перенос существующих материалов выполняется автоматически после проверки во временном клоне.**

При переходе существующего Ledger на MCP автоматический перенос сначала выполняется во временном клоне проекта. Проверяются сохранность содержимого, идентификаторов и связей, формат документов, размещение Markdown и соответствие хешей. Только после успешной проверки перенос выполняется в основном проекте.

Приёмка: ошибка переноса или проверки в клоне не приводит к переносу в основном проекте. Успешная проверка позволяет автоматически выполнить перенос в основном проекте с сохранением содержимого и связей. Известные даты сохраняются, неизвестные исторические даты получают текущую дату переноса.

**Границы.** Хеш не доказывает согласие пользователя или смысловую правильность. Последствия непрозрачных shell-записей обнаруживаются по файлам.

Встроенный ключ можно извлечь из бинарника. Поэтому шифрование эталонов не гарантирует защиту от намеренного обхода проверки агентом, имеющим доступ к бинарнику и файлам проекта.

## Expected benefit

Важные документы и вспомогательные материалы имеют определённое место, а операции, состояния и целостность памяти контролируются сервисом.
