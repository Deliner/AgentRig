# B002 — Согласованная работа хуков и понятные инструкции агенту

## Context

Несколько хуков могут одновременно предъявлять требования. Агент должен получать один понятный результат: что произошло, какие действия обязательны и можно ли продолжать работу. Пользователь управляет этим через конфигурацию.

Область — все поддерживаемые события Codex и Claude Code.

## Proposal

Событие → доступные факты → применимые требования → проверка их актуальности → объединение и упорядочивание → один ответ → разрешение или остановка действия.

Ответ содержит состояние действия, требования, причины, источники, ссылки на skills и следующий шаг. Объединение выполняется по правилам, без свободного пересказа моделью.

**K1. Архитектурное требование привязано к известной области изменения.**
Перед первой правкой в области, определяемой по явным путям события, хук требует применить архитектурный skill. Агент читает согласованную карточку и соответствующие `architecture.yaml`, сопоставляет ответственность с кодом, потребителями и сохраняемыми свойствами.

Skill требует размещать поведение у его владельца. Общий компонент не становится собственностью отдельного потребителя; расширение описания каталога не оправдывает неправильное размещение.

Приёмка: известный путь направляет к нужной области и skill; прочтение не считается доказательством правильного решения.

**K2. Фактическая структура проверяется независимо от предварительной подсказки.**
Хук не обязан предсказывать будущие изменения произвольной shell-команды. Состав и зависимости проверяются на снимке VAC, смысловое соответствие — перед merge по [B015](015.md). Изменение ответственности сопровождается согласованным изменением структуры и YAML.

Приёмка: изменения через непрозрачную команду всё равно попадают в проверку результата.

**K3. Совместимые требования сохраняются вместе.**
Повторные ссылки на один skill объединяются с сохранением причин, областей и самостоятельных условий выполнения. Отдельный хук не переопределяет общий порядок.

Приёмка: объединённый ответ не теряет ни одного применимого требования.

**K4. Разрешение не отменяет обязательную остановку.**
Если событие допускает блокировку и хотя бы одно требование её предусматривает, действие останавливается. Остальные требования сохраняются. Полное перечитывание complexity-discipline предшествует предметным инструкциям.

Приёмка: разрешающий хук не снимает блокировку другого.

**K5. Порядок подключения обработчиков не влияет на итог.**
При одинаковых результатах обработчиков их перестановка сохраняет решение, состав требований и порядок выдачи.

Приёмка: перестановки дают одинаковый общий ответ.

**K6. Противоречивый порядок отклоняется до применения настройки.**
Конфликты и циклы порядка выявляются при проверке конфигурации. Диагностика указывает требования и источники; победитель не выбирается произвольно.

Приёмка: противоречивая настройка не применяется, исправленная — применяется.

**K7. Повторная попытка не размножает инструкции.**
Повторный вызов перепроверяет условия. Уже доставленное напоминание без новой причины не разворачивается заново и само по себе не блокирует повтор.

Обязательное требование сохраняет блокировку до выполнения своего проверяемого условия. Пока оно не выполнено, ответ кратко сообщает оставшуюся причину остановки.

Приёмка: повтор не создаёт бесконечной цепочки напоминаний и не снимает сохраняющееся нарушение.

**K8. Диагностики объединяются по общей измеренной причине.**
Сохраняются затронутые пути, ограничения, серьёзность и способ повторной проверки.

Приёмка: связанные сообщения сокращаются без потери сведений; разные причины остаются различимыми.

**K9. Ослабление ограничений проверяется относительно исходных требований.**
Изменения архитектурных ограничений и проверок входят в существующее ревью перед merge.

Приёмка: само изменение YAML не считается обоснованием допустимости ослабления.

**K10. Смысловая оценка выполняется на согласованной границе.**
Ревью перед merge рассматривает владение поведением, публичные границы и ненужное усложнение по [B015](015.md). На VAC остаются механические проверки.

Приёмка: прохождение линтера не выдаётся за архитектурное одобрение; отдельное модельное ревью каждого VAC не требуется.

**K11. Ошибка настройки сохраняет путь восстановления.**
Ошибки конфигурации и маршрутизации обрабатываются с сохранением возможностей [B001](001.md).

Приёмка: неисправная настройка хуков не блокирует собственное исправление.

**K12. Ответ соответствует фактически доступному событию.**
До действия возможна остановка. После действия сообщаются факт выполнения, результаты и дальнейшие требования. Маршруты памяти и подсказки линтера сохраняются.

Приёмка: уже выполненное действие не объявляется предотвращённым; сценарии проверяются для поддерживаемых событий обоих клиентов.

**K13. Обновление действующего знания связано с VAC и merge.**
Вход в штатную проверку VAC → применимое напоминание о skills инструкций и памяти → проверка ссылок и структуры перед коммитом. Актуальность инструкций относительно поведения проверяется перед merge по [B015](015.md).

State отражает фактический исход работы. Закреплённые решения сохраняются, изменения оформляются преемниками; история остаётся в Git и Archive.

Приёмка: сломанные связи блокируют VAC, противоречащие результату инструкции — merge. Документированные сценарии воспроизводятся проверками. Обязательной правки README при каждом VAC нет.

**K14. Пользователь настраивает применение требований.**
В конфигурации задаются событие, условия по поддерживаемым данным, правило или skill и порядок. После `setup` применяется выбранное поведение.

Приёмка: изменение настройки меняет соответствующий маршрут; ответ позволяет найти сработавшее правило. Порядок не отменяет обязательных требований.

**K15. У состояния требования и блокировки один владелец.**
Область применения задаёт проверяемые условия возникновения, выполнения и прекращения требования. Общий механизм учитывает эти условия и согласует допуск с другими хуками.

Первый случай — серия правок конфигурации по [B006, K10](006.md).

Приёмка: выполненное требование не заставляет повторять чтение внутри разрешённой серии; прекращение допуска требует нового чтения. Выполнение одного требования не отменяет другого.

**Границы.** Чтение skill не доказывает понимания. Конфликты произвольных текстовых указаний автоматически не разрешаются. Не добавляются универсальный язык правил, отдельные диспетчеры допуска или система оценки агентов. Обычное редактирование допускается без `just write`.

## Expected benefit

Агент получает необходимые требования в нужной ситуации, выполняет их без повторных ритуалов и продолжает продуктовую работу.
