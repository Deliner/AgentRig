# B002 — Согласованная работа хуков и понятные инструкции агенту

## Context

**Исходный запрос.** Несколько хуков могут одновременно выдавать требования. Нужно сохранить их смысл, определить влияние на действие и предоставить агенту понятный порядок дальнейшей работы.

**Согласованное уточнение.** Конфликты порядка нужно исключать до применения настройки: хуки сообщают требования, а общий механизм задаёт их порядок. Гарантия относится к требованиям, которые обвязка представляет и проверяет явно.

**Область действия.** Все типы хуков, поддерживаемые выбранным harness. Работа проверяется для Codex и Claude Code. Архитектурные подсказки — один из случаев применения.

Предыдущий контекст: [B002 до согласования карточки](https://github.com/Deliner/AgentRig/blob/349f366c1c35277702e7a43f1fda0edee23f7646/Ledger/Backlog/002.md), перенесённый из [P011](https://github.com/Deliner/AgentRig/blob/f6cd86efbae8ec501759f0c250b9bd4b76e300d7/Ledger/Plan/011.md).

## Proposal

**Что получает агент**

Предлагается **один общий ответ на событие**, содержащий:

1. Событие и затронутое действие.
2. Результат: действие разрешено, остановлено либо уже выполнено.
3. Требования и подсказки с источниками, причинами, областью применения и ссылками на skills.
4. Порядок обязательных действий.
5. Указание, что делать дальше.

**Иллюстративный пример ответа перед редактированием** — названия правил и формулировки здесь условные, это не обязательный формат протокола:

```text
Действие: изменить module/architecture.yaml.
Результат: действие НЕ ВЫПОЛНЕНО.

Причина остановки:
Хук complexity-discipline требует полного перечитывания skill.

Выполнить по порядку:

1. Прочитать .agents/skills/complexity-discipline/SKILL.md.
   Источник: правило полного перечитывания complexity-discipline.

2. Прочитать .agents/skills/refactor-large-directory/SKILL.md.
   Затем проверить ответственность изменяемого каталога,
   его границы и существующих потребителей.
   Источник: правило архитектурных изменений.
   Область: module/architecture.yaml.

Дальше:
Выполнить требования и повторить исходное редактирование.
Повторная попытка снова проходит применимые проверки.
```

Таким образом, «объединение» означает **сбор всех применимых требований в явный список с сохранением источников**, а не создание нового пересказа, в котором часть условий может исчезнуть.

**Как пользователь управляет поведением**

Предлагаемая поверхность настройки — существующий `agentrig.yaml`. Пользователь задаёт:

| Что настраивает | Как это влияет на работу |
|---|---|
| Событие для хука | Когда он участвует в обработке |
| Условия применения | Для каких ситуаций он срабатывает; используются сведения, доступные в событии |
| Правило или skill | Какое требование получает агент |
| Порядок требований | Задаётся в одном месте для общего механизма; отдельные хуки не могут его переопределять. Порядок не отменяет другие обязательные требования |

**Пример управления:** пользователь ограничивает архитектурную подсказку выбранными каталогами → применяет настройки через существующий `setup` → при следующих подходящих событиях подсказка появляется для этих каталогов.

Каждый ответ указывает сработавшие правила и соответствующие настройки, чтобы пользователь мог изменить причину поведения, а не угадывать её.

**Проверка настройки:** пользователь задаёт порядок → проверка конфигурации обнаруживает противоречия и циклы → конфликтующая настройка не применяется; пользователь получает указание на конфликтующие требования и их источники.

**Иллюстративный пример:** одновременно заданы «А перед Б» и «Б перед А» → пользователь получает сообщение: «Настройка не применена: порядок А → Б → А образует цикл», с указанием обоих источников → исправляет порядок → повторяет применение настройки.

**Правила работы**

**Событие → выбрать применимые хуки → получить все результаты → объединить одинаковые требования → упорядочить по общей настройке → составить общий ответ → применить допустимое для события решение.**

- Совместимые требования сохраняются вместе. Один skill указывается один раз со всеми причинами обращения к нему.
- Если хотя бы один хук требует остановки, остановка сохраняется вместе с остальными подсказками. Разрешение другого хука не отменяет остановку.
- Хуки сообщают требования; общий механизм задаёт порядок. Отдельный хук не может переопределить общий порядок.
- Полное перечитывание complexity-discipline предшествует предметным инструкциям.
- Порядок подключения обработчиков не меняет решение и состав требований.
- Противоречия и циклы в настройке порядка выявляются до её применения. Конфликтующая настройка не применяется; система не выбирает победителя самостоятельно.
- До действия возможна его остановка. После действия ответ сообщает, что оно уже выполнено, результаты проверки и дальнейшие требования. Возможности конкретного события harness учитываются явно.
- В существующем цикле напоминаний различаются доставка напоминания и сохраняющееся нарушение. Повторная попытка не блокируется только ради повторной доставки того же напоминания; нарушения проверяются снова. Доставка не доказывает понимания.

**Критерии приёмки**

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| K1 | Первое изменение кода в модуле | До правки выдано требование изучить архитектурные описания, владельца поведения и потребителей |
| K2 | Создание, перенос файлов или изменение архитектурного описания | Выдана соответствующая подсказка о принадлежности файлов и границах ответственности |
| K3 | Несколько совместимых требований | В общем ответе сохранены все требования, причины, источники и области; повторные ссылки на skills объединены; требования выданы в общем установленном порядке, который отдельные хуки не переопределяют |
| K4 | Остановка одновременно с разрешением другого хука и другими подсказками | Действие остановлено, разрешение не отменяет остановку, подсказки сохранены; полное перечитывание предшествует предметным требованиям |
| K5 | Перестановка обработчиков | Решение и состав требований одинаковы |
| K6 | Применение настройки с противоречиями или циклом порядка, например А → Б → А | Настройка не применяется; показаны конфликтующие требования и их источники. После исправления настройка применяется, требования выдаются в установленном порядке |
| K7 | Повторная попытка | Доставленное напоминание не создаёт повторного запрета само по себе; сохраняющиеся нарушения проверяются |
| K8 | Диагностики одной измеренной причины | Объединены с сохранением путей, границ, серьёзности и способа повторной проверки. Несвязанные ошибки не склеены |
| K9 | Ослабление архитектурных ограничений или проверок | Фактическое изменение оценивается существующим ревью относительно исходных требований |
| K10 | Завершение изменения | Проверка приёмки связана с наблюдаемым поведением и потребителями; архитектурное ревью охватывает владение, публичные границы и ненужное усложнение |
| K11 | Ошибка конфигурации или маршрутизации | Сохраняется восстановление по B001 |
| K12 | Разные поддерживаемые типы событий и оба клиента | Общие правила соблюдаются с учётом возможностей события; сохраняются маршруты памяти и подсказки линтера |
| K13 | Воспроизведение документированных сценариев | Реальные ответы и действия соответствуют описанию; наличие текста инструкции само по себе недостаточно |
| K14 | Изменение условий применения хука пользователем | После применения настройки меняется набор подходящих событий; ответ позволяет определить сработавшее правило |

**Ограничения.** Обычные правки допускаются без `just write`. Неизвестные цели shell-команды не выдаются за известные. Не добавляются универсальный поиск противоречий в произвольном тексте, учёт прочтений skills, счётчики эскалации и отдельная система оценки агентов. Проверки сочетаний входят в существующий набор тестов.

**Граница гарантии.** Конфликт порядка исключается в применённой конфигурации для требований, которые обвязка представляет и проверяет явно. Противоречия внутри произвольного текста skills, например «удали файл» и «сохрани файл», этой проверкой не исключаются; автоматическая защита от всех таких случаев не обещается.

## Expected benefit

**Нужный результат.** Агент понимает, выполнено ли действие, что ему требуется сделать, почему и откуда пришло каждое требование. Пользователь понимает, какими настройками управлять этим поведением.
