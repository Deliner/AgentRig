# B008 — Запрет комментариев кроме ссылок на решения и инварианты

## Context

В коде разрешены только комментарии-ссылки `DECISION: DNNN` и `INVARIANT: INNN`. Исключений для документационных комментариев, лицензий и служебных директив нет. Полезные объяснения сохраняются через существующие решения и инварианты.

## Proposal

Проверка снимка на VAC → обнаружение недопустимого комментария → ошибка и требование прочитать skill → содержательное исправление → повторная проверка.

На merge → существующее ревью затронутых записей и кода → проверка соответствия объяснения реальному решению или свойству.

**К1. Линтер отклоняет комментарии, не являющиеся допустимыми ссылками.**
Разрешённый комментарий содержит только ссылку установленного формата. Добавление маркера к произвольному пояснению не делает его допустимым. Форма комментария не освобождает от правила.

Приёмка: обычные, документационные и служебные комментарии отклоняются. Корректная ссылка принимается; ссылка с добавленным пояснением — нет. Текст внутри данных не принимается за комментарий только из-за похожих символов.

**К2. Ссылка проверяется через существующую память проекта.**
Указанная запись должна существовать. Инвариант должен иметь предусмотренную действующим механизмом связь с точной исполняемой проверкой. Отдельный реестр ссылок не создаётся.

Приёмка: несуществующий идентификатор и нарушенная обязательная связь инварианта обнаруживаются. Наличие ссылки не объявляется доказательством истинности свойства; результат исполнения проверки учитывается отдельно по [B016](016.md).

**К3. Нарушение требует прочитать skill исправления.**
Диагностика показывает правило, расположение комментария, назначенный skill и команду повторной проверки. Требование чтения передаётся через общий механизм [B002](002.md), включая объединение повторных требований.

Приёмка: VAC с нарушением отклоняется, агент получает применимую инструкцию. Чтение skill само по себе не снимает нарушение: исправленный код должен пройти повторную проверку.

**К4. Skill помогает сохранить нужное знание без фиктивных записей.**
Агент определяет назначение комментария:

- Контекстный выбор → существующее или обоснованно новое решение.
- Проверяемое обязательное свойство → инвариант с исполняемой проверкой.
- Ненужное пояснение → удаление.

Skill использует действующие правила различения решений и инвариантов и соответствующие skills редактирования памяти. Запись для каждого комментария не требуется. Создание фиктивных записей и подстановка посторонних идентификаторов запрещены.

Приёмка: сохранённая запись соответствует смыслу исходного объяснения и затронутому коду. Смысловую корректность оценивает существующее ревью на merge по [B015](015.md); линтер проверяет форму и связи.

**К5. Исправление сохраняет поведение.**
Удаление комментария не должно менять требуемую работу кода или инструментов. Если служебный комментарий влияет на исполнение, простое удаление не считается исправлением.

Приёмка: необходимые поведенческие проверки проходят после изменения. Если запрет и сохранение поведения невозможно совместить, противоречие предъявляется для согласования; агент не вводит исключение и не ослабляет проверку самостоятельно.

**К6. Правило подтверждено воспроизводимыми CLI-эвалами.**
В окружении [B004](004.md) проверяются запрещённые формы комментариев, допустимые ссылки, дополнительный текст после маркера, несуществующие записи, нарушенные связи и исправленные варианты.

Приёмка: фактические находки и код завершения соответствуют заранее заданным ожиданиям; неожиданных нарушений нет.

Проверки выбираются по [B016](016.md): VAC — изменённые и новые файлы; merge — затронутые фичи или модули всей ветки; полный набор — явный запуск.

**Детерминированные опоры:** снимок кода; распознанный комментарий; формат ссылки; существование записи и обязательных связей; диагностика линтера; событие чтения skill; повторная проверка; merge.

**Границы и неизвестное.** До реализации нужно согласовать языки первой поставки и определить распознаваемые конструкции, включая документационные формы. Неподдерживаемый анализ не считается успешной проверкой.

Используются существующие линтер, память, координатор требований, ревью и эвалы. Дополнительный журнал комментариев и отдельный ревьювер не создаются.

## Expected benefit

Обычные комментарии не накапливаются. Значимые объяснения и проверяемые свойства сохраняются в предназначенных для них записях, а агент получает понятный способ исправления непосредственно из ошибки.
