# B034 — Зонирование модулей

## Context

Набор II улучшений качества (переносимо на любое приложение, agent-native) — мозгоштурм и
экспертный разбор 2026-10-31. Пользователь согласовал весь набор (10 кластеров C1–C10) на
автономное исполнение по моей рекомендации, по одной карточке за ветку. C1 — фундамент: без
класса зоны остальные правила либо бланкет-вредят в горячем коде, либо непереносимы между
приложениями. Контракт — ревизия карточки в Git.

## Proposal

Модуль помечается классом зоны из фиксированного набора (напр. `pure`, `io-adapter`,
`api-surface`, `hot-core`, `test`), и структурные правила применяются с интенсивностью этого
класса — одно переносимое правило, разные пороги/включённость по зонам. Так единый набор
дисциплины ложится на любой домен, а не на один. Граница зоны явная (модуль/каталог), не
выводится по месту вызова.

- Класс зоны объявляется в архитектурном контракте модуля; значение из фиксированного набора;
  неизвестный класс — ошибка конфигурации (`lint-config-check`). *[контракт]*
- Хотя бы одно существующее правило детерминированно меняет поведение (порог/включённость) по
  классу зоны, **аддитивно** — без ослабления действующих порогов ([D035](../Decisions/035.md)).
  *[правило]*
- Возможность уезжает в `init` ([D053](../Decisions/053.md)/[I020](../Invariants/020.md)); наш
  код зелёный под новым поведением (догфуд).

**Границы.** Только Rust-движок и `Project`. Расширение схемы `architecture.yaml` новым полем
требует решения (сейчас [D043](../Decisions/043.md) ограничивает поля purpose/files/directories)
— фиксируется в первом VAC. Что не чисто синтаксически — норма (norm-or-choice, D035/D059);
притворный инвариант не вводится. Перечень классов зон и демонстрирующее правило уточняются
спайком в первом VAC.

## Expected benefit

Один набор дисциплины качества переносится на любое приложение без переписывания правил под
домен: интенсивность каждого правила берётся из класса зоны модуля.
