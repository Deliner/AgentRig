# B006 — Единый каталог компонентов и конструктор окружений

## Context

Пользователь хранит и версионирует общие компоненты в Git, затем собирает из них окружения разработчиков, ревьюверов, советников и делегированных агентов. Развиваются существующие композиция YAML, установка и обновление.

## Proposal

Выбор компонентов, роли и клиента → разрешение состава и настроек → проверка совместимости → предварительный просмотр → применение.

Явное обновление → выбор новых версий → просмотр изменений → проверка и применение.

**К1. Компоненты имеют один канонический источник.**
Каталог содержит skills, хуки, настройки линтера, инструменты, MCP, инструкции и применимые требования к ответам и доступу. Модули объединяют компоненты одной смысловой задачи.

Приёмка: один компонент используется несколькими окружениями с общим происхождением и версией. Установка ресурсов в окружение не создаёт отдельную каноническую копию, которую нужно поддерживать вручную.

**К2. Пользователь определяет состав окружения через YAML.**
Пользователь выбирает модули, компоненты, роль, harness, настройки модели и права доступа. Конструктор подготавливает окружения Codex и Claude Code для разработчика, ревьювера, советника и делегированного агента.

Приёмка: выбранный состав отражён в работающем окружении. Сохраняются различия в выполнении ролей и проверке их результатов.

**К3. Состав и происхождение настроек доступны для просмотра.**
Через файлы каталога и существующие команды пользователь регистрирует и находит компоненты, видит выбранные версии, объявленные зависимости и использующие их сборки. До применения доступны итоговая конфигурация и источники значений.

Приёмка: каждое показанное включение и переопределение объясняется содержимым выбранных файлов. Отдельная база или вручную синхронизируемый реестр не требуются.

**К4. Несовместимая композиция отклоняется до применения.**
Проверяются зависимости, циклы, несовместимые объявления и конфликтующие значения. Переопределения задаются явно. Согласование требований хуков следует [B002](002.md).

Приёмка: корректная сборка принимается; конфликтующая отклоняется с указанием причины и источников. Неподдерживаемая возможность не исчезает молча из применяемого окружения.

**К5. Закреплённое окружение меняется только при явном обновлении.**
Выбранные компоненты связаны с точными Git-ревизиями и хешами ресурсов. Одинаковые входные данные восстанавливают одинаковую конфигурацию и ресурсы.

Приёмка: изменение каталога не меняет закреплённую сборку. Новая версия применяется после явного обновления с доступным предварительным просмотром. Одинаковые ответы моделей не обещаются.

**К6. Среда исполнения обеспечивает права роли.**

- Разработчик выполняет разрешённые изменения.
- Ревьювер читает исходники без возможности их изменять.
- Архитектурный советник получает задачу, критерии приёмки и `architecture.yaml`, без прямого доступа к остальным исходникам.

Приёмка: разрешённый доступ работает, запрещённые операции отклоняются. Подключение общего модуля не расширяет права незаметно. Если среда не обеспечивает заданное ограничение, окружение не объявляется соответствующим настройке.

Советник оценивает предоставленные описания. Его ответ не доказывает соответствие реализации, не отменяет линтер и не разрешает действия.

**К7. Определения компонентов отделены от секретов и результатов запусков.**
Секреты представлены ссылками, разрешаемыми существующим механизмом учётных данных. Состояние запусков, ответы моделей и отчёты хранятся отдельно.

Приёмка: версионируемые определения не содержат значений секретов; выполнение роли не дописывает результаты в определения компонентов.

**К8. Общий конструктор используется через существующие точки входа.**
Настройка проекта, ревью и делегирование используют общий состав компонентов с сохранением действующего поведения установленных ресурсов.

Приёмка: независимые потребительские проверки подтверждают сборку, закрепление версий, обновление, обработку конфликтов и ограничения доступа. Используются существующие средства проверки в независимых потребительских проектах; недостающие сценарии конструктора добавляются в B006. Параллельный формат и дублирующие канонические skills не вводятся.

**К9. Настройки разделены по смыслу внутри одной директории.**
Корневой `agentrig.yaml` служит точкой входа в общую директорию конфигурации. Содержательные определения компонентов, модулей и сборок находятся внутри неё в отдельных YAML-файлах и поддиректориях.

Разбиение сохраняет единые правила зависимостей, переопределений и версий. Фиксированное внутреннее дерево не навязывается.

Приёмка: два окружения используют общий модуль и собственные настройки. Изменение настройки одного окружения не меняет второе. Конфликт между файлами обнаруживается до применения; просмотр показывает источник значения. Для изменения одного модуля не требуется редактировать общий файл со всеми настройками.

**К10. Чтение назначенного skill открывает серию правок конфигурации.**
Если изменяемый путь известен до операции, перед правкой `agentrig.yaml` или общей директории конфигурации хук проверяет чтение назначенного skill. Без действующего допуска правка блокируется.

Для непрозрачной команды конфигурация сравнивается до и после выполнения. Если она изменилась без действующего допуска, хук требует прочитать назначенный skill и проверить изменённую конфигурацию перед продолжением обычной работы. Действия восстановления остаются доступны.

Чтение → последовательные правки конфигурации → изменение файла вне конфигурации → допуск прекращается → перед возвращением требуется перечитывание.

Чтение других файлов серию не завершает. Состоянием и общей блокировкой управляет [B002, К15](002.md). Остальные требования и восстановление по [B001](001.md) сохраняются. Обычное редактирование не требует `just write`.

Приёмка: вся последовательность проверена по фактическим событиям чтения и изменения. Для известного пути правка без допуска предотвращается; для непрозрачной команды нарушение выявляется по сравнению конфигурации после выполнения, а обычная работа продолжается после чтения skill и успешной проверки конфигурации. Чтение конфигурационного skill перед каждой командой не требуется. Действующий допуск не отменяет блокировку другого хука.

**К11. Scaffold подготавливает проверяемую настройку проекта.**
Риг обнаруживает используемые языки, команды и настройки линтеров и предъявляет их как предложение. Пользователь уточняет языки, окружения и обязательные проверки. Выбор сохраняется в общей конфигурации; существующие команды подключаются через их точки входа.

Приёмка: уточнения пользователя отражены в настройке. Конструктор подключает доступные проверки и показывает фактическое покрытие: подключённые, отключённые, неподдерживаемые и невыполнимые проверки. После изменения настроек повторная проверка обновляет результат. Агент использует согласованное окружение автономно.

**Детерминированные опоры:** явный выбор сборки; проверка композиции; закреплённые версии; применение и обновление; фактический доступ; события чтения и изменения; результаты потребительских проверок.

**Границы.** Для непрозрачной команды К10 обнаруживает нарушение после выполнения, а не предотвращает изменение заранее. Предположение о поведении произвольной shell-команды не считается знанием её изменяемых путей.

Полная реализация [B004](004.md) и [B005](005.md) не требуется до B006. Поддержка всех семи языков и эвалы правил остаются в B004; общая диагностика и расширенные сценарии восстановления — в B005. Необходимые проверки конструктора входят в B006.

Используются существующие Git, YAML, установщик и координатор требований. Веб-сервис, аккаунты, маркетплейс, публикация и обмен окружениями отложены; подготовительная инфраструктура для них не создаётся.

## Expected benefit

Пользователь собирает разные окружения из общих компонентов, видит их состав и управляет обновлениями. Агент получает подготовленные инструменты и ограничения без повторной ручной сборки обвязки.
