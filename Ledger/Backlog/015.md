# B015 — Проверка архитектуры на VAC и перед merge

## Context

Структура проекта может изменяться любыми инструментами. Обвязка должна проверять фактический результат, сохраняя быстрый цикл разработки. Механические нарушения обнаруживаются на VAC; смысловое соответствие проверяется существующим ревью перед merge, если оно включено в конфигурации рига.

## Proposal

Подготовка VAC → проверка фактического снимка линтером и затронутыми тестами → исправление нарушений → коммит.

Подготовка merge → проверки затронутых фичей или модулей → при включённом ревью одна штатная операция ревью совокупных изменений ветки → проверяемый результат допуска.

При выключенном ревью merge не запускает ревьювера и не требует его отчёта. Линтеры и остальные настроенные проверки выполняются.

Полный набор тестов запускается по явному запросу «всё». Области определены в [B016, К10](016.md). Специальные проверки инструментов из [B014](014.md) остаются перед merge.

**К1. Механическая проверка использует фактический снимок изменения.**

Перед коммитом обвязка проверяет снимок, который будет принят в VAC. Учитываются созданные, изменённые и удалённые файлы; перенос может рассматриваться как удаление и создание.

Предварительному хуку не требуется угадывать результат произвольной команды.

Приёмка: при одинаковых снимке, базе сравнения, настройках и версии линтера результат одинаков независимо от способа редактирования. Непроверенные изменения не получают результат проверки другого снимка.

**К2. Архитектурные YAML соответствуют инвентарю проекта.**

Линтер сопоставляет файлы и каталоги с `architecture.yaml`. Отсутствующее обязательное описание, незарегистрированный файл и запись об удалённом элементе считаются нарушениями.

Приёмка: несогласованное изменение инвентаря блокирует коммит. После согласованного изменения файлов и описаний проверка проходит. Наличие YAML без актуального содержимого недостаточно.

**К3. Зависимости проверяются по содержимому файлов.**

Изменение зависимости внутри существующего файла участвует в проверке разрешённых связей, публичных границ и циклов. Анализ включает связанные элементы, необходимые для проверки затронутого отношения.

Приёмка: запрещённая зависимость или созданный цикл обнаруживаются без добавления и переноса файлов. Неподдерживаемые конструкции обозначаются как неполный анализ; отсутствие обнаруженных нарушений в таком случае не объявляется полной успешной проверкой.

**К4. Обнаруженное нарушение направляет агента к конкретному исправлению.**

Нарушение линтера → блокировка коммита → путь, нарушенное правило, skill и команда повторной проверки. Требование skill согласуется с другими хуками через [B002](002.md).

Skill направляет восстановить соответствие ответственности, структуры и зависимостей. Расширение разрешений или описания только ради прохождения проверки не считается исправлением.

Приёмка: корректное исправление устраняет нарушение при повторной проверке. Прочтение skill само по себе блокировку не снимает. При отсутствии нарушений дополнительные объяснения и отчёты от агента не требуются.

**К5. При включённом ревью перед merge выполняется изолированная проверка по фиксированному чек-листу.**

Пользователь включает и выключает ревью через существующую конфигурацию review в риге. При включённом ревью перед merge требуется успешная проверка актуального снимка. При выключенном ревью результат явно сообщает «ревью отключено конфигурацией»; отсутствие проверки не выдаётся за подтверждение качества.

Существующий runner с bubblewrap предоставляет ревьюверу доступ только на чтение к зафиксированному снимку проекта. Проверяются совокупные изменения ветки, включая предыдущие VAC.

Ревьювер получает заранее заданный промпт, ревизию, базу сравнения и ссылки на согласованные карточки. Код, YAML, требования и diff он читает с диска; вызывающий агент их не пересказывает.

Чек-лист:

1. **Назначение:** изменённое поведение соответствует заявленной ответственности.
2. **Владение:** общая часть принадлежит обоснованному владельцу.
3. **Границы:** сохранены заявленные публичные интерфейсы и направления зависимостей.
4. **Размещение:** новые и перенесённые элементы находятся у владельца своей ответственности.
5. **Согласованность:** изменения ответственности отражены в реализации и архитектурных YAML.
6. **Актуальность инструкций:** затронутые инструкции соответствуют итоговому поведению; заменённые сведения отделены от текущих и доступны в истории.

Для инструментов учитываются согласованные требования [B014](014.md) в рамках того же ревью.

Результат содержит оценку каждого пункта: соответствует / нарушение / не проверено. Замечание указывает пункт, путь и конкретное свидетельство. Необязательные улучшения и предпочтения по стилю не блокируют merge.

Приёмка: несколько VAC выполняются без обязательного модельного ревью; перед merge при включённом ревью рассматривается их общий результат. Нарушение чек-листа блокирует merge. Ревьювер не изменяет снимок и обосновывает выводы доступными материалами. Советник, читающий только YAML, не считается проверившим реализацию.

**К6. Допуск относится к проверенному состоянию, повторное ревью сохраняет критерии.**

При включённом ревью исправления замечаний проходят обычные VAC. Перед merge повторная проверка использует исходную базу сравнения, предыдущий отчёт и тот же чек-лист.

Ревьювер проверяет прежние замечания и влияние исправлений. Для нового замечания указывает, внесено ли нарушение исправлением или было пропущено ранее. Новые требования в процессе повторного ревью не добавляются.

Приёмка: изменённое содержимое не допускается по устаревшему успешному отчёту. Результат связан со снимком, базой сравнения и версией проверочного контракта. Прежний пропуск не выдаётся за изменение критерия.

**К7. Сдача на ревью выполняется одной готовой операцией с учётом настройки рига.**

Агент вызывает штатную операцию проверки ветки перед merge. При включённом ревью обвязка автоматически:

- определяет ревизию, базу сравнения и связанные согласованные карточки;
- подготавливает снимок и запускает существующий review MCP и runner;
- подключает настроенные промпт и чек-лист;
- предоставляет материалы для чтения с диска;
- проверяет полноту ответа, сохраняет отчёт;
- возвращает краткий итог, замечания и путь к подробностям.

Повторный запуск использует предыдущий отчёт и исходную базу. Агенту не нужно писать скрипт, составлять промпт или вручную собирать материалы.

Приёмка: первое и повторное ревью выполняются штатной операцией. Переключение настройки меняет поведение следующей проверки перед merge; в выключенном состоянии нет вызовов модели и требований предоставить отчёт. Во включённом состоянии ошибки и нарушения препятствуют merge. Ошибка запуска или неполный ответ не считаются выключенным или успешно пройденным ревью.

**Границы и неизвестное.** Используются существующие gate, линтер, координатор [B002](002.md) и механизм ревью. Обязательное модельное ревью на VAC не вводится.

Bubblewrap ограничивает доступ; фиксация версии проверяемых файлов обеспечивается снимком. Детерминированы исходные материалы, правила механической проверки, чек-лист и проверка отчёта. Одинаковые выводы модели и доказательство смысловой правильности не гарантируются.

До реализации нужно определить реакцию gate на неполный статический анализ.

## Expected benefit

Агент быстро выполняет VAC, исправляет конкретные механические нарушения и при включённом ревью сдаёт общий результат ветки на архитектурную проверку одной операцией. Критерии не меняются между итерациями.
