# B024 — Размещение теста по реально исполняемому коду

## Context

TC1 из [B022](../Archive/Backlog/022.md) (тест лежит рядом с тем, что проверяет; шире —
поднимается к общему владельцу, уже — опускается) остался нормой
([D055](../Decisions/055.md)): ребро импорта не отличает предмет проверки от попутной
общей ссылки (пример — `structural_lint/languages/tests` ссылается на общий тип
`structural_lint/rules/kind.rs`). Покрытие — прямой сигнал «какой код тест реально
исполняет» (формулировка пользователя в [Requests](../Requests.md), ч.3 п.2). Источник:
набор идей улучшений, согласовано пользователем 2026-10-28.

## Proposal

Сначала спайк-исследование осуществимости, затем — при подтверждении — проверка
размещения теста по покрытию.

**K1 — сбор покрытия на тест.** Для теста собирается множество продуктового кода,
которое он реально исполняет (Rust — `llvm-cov`; Python — `coverage.py`).

**K2 — проверка уровня.** Множество покрытия сопоставляется с каталогом-владельцем теста
и его `architecture.yaml`; тест, чья масса покрытия лежит вне поддерева владельца (выше
или ниже), помечается с предложением переместить к владельцу исполняемого поведения.

**Границы и неизвестное.** Явный неизвестный — стоимость и стабильность per-test
покрытия и его интеграция в затронутый-тестами гейт; спайк это измеряет. Приёмка: TC1
становится проверкой, **либо** по итогам спайка фиксируется, что покрытие не
окупается/нестабильно, и TC1 остаётся нормой с записью причины (norm-or-choice), без
«притворного» инварианта — как в [P031](../Archive/Plan/031.md). Проверяется только код
внутри `Project`.

## Expected benefit

Место теста выводится из того, что он реально трогает, а не из текстовых импортов;
«тест судится по коду, который он трогает» становится проверяемым, если покрытие
окупается.
