# P007 — Extensible version control support

## Feature

Support AgentRig delivery with multiple version control systems and an extension boundary usable by private corporate implementations.

## User capability

The user selects a supported VCS for a consumer project, retains verified changes and recovery, and runs isolated review and code delegation against exact revisions. An organization can supply its own VCS integration without publishing proprietary implementation code or modifying each AgentRig workflow.

## Acceptance

- Git remains supported and at least one other real VCS is implemented and demonstrated in an independent consumer. The user delegates selection to the implementing agent: choose an available system with the simplest sufficient integration to exercise the extensible architecture, and record that choice. No further user selection is required.
- A documented integration boundary owns VCS-specific operations used by configuration/setup, revision and change inspection, snapshots, delivery checks, integration, recovery, review and delegated code results. Existing Git assumptions are not left hidden in callers of the new backend.
- Each backend represents its actual semantics. Unsupported operations are explicit actionable capability errors; Git staging or branch concepts are not presented as available where they do not exist. Equivalent supported delivery preserves the exact checked changes, unrelated work and recoverable integration context.
- A consumer can configure a private implementation through the documented extension contract. A separate example exercises this boundary without changing AgentRig's workflow logic or publishing corporate code. Validate data crossing the extension boundary and retain existing snapshot/result restrictions.
- Tests exercise real repositories for Git and the selected second VCS: changes, deletions/renames where supported, exact revision snapshots, failed checks, isolation, recovery and successful integration. Review and code delegation preserve the original workspace and return inspectable, verified results for both.
- Setup, diagnostics, documentation and configuration describe actual backend capabilities. Existing Git consumers remain usable; configured gates and independent consumer acceptance pass.

## Delivery

Requested by the user after P005. The user confirmed VCS support second in delivery priority and authorized the agent to choose the simplest available additional system. The purpose is to prove the extensible architecture. Arc was mentioned as a possible future privately supplied integration; implementing Arc now is outside this delivery. Keep the private extension capability required above without assuming access to Arc. Repository hosting such as GitHub is distinct from the VCS. Full implementation is authorized by the active P006 → P007 → P008 goal.
