# P012 — Cohesive AgentRig ownership and reliable development flows

## Feature

Apply P011 to improve AgentRig around cohesive features, explicit shared owners and reliable consumer flows. Correct the evidenced cross-capability omissions from the audit while preserving supported interfaces and installed-runtime development discipline.

## User capability

The user and agent can find the owner of a change, keep its scope narrow and rely on consistent VCS, configuration, build and verification behavior across consumers. Architecture contracts explain intended placement rather than merely approving existing directories.

## Acceptance

- Reconcile audit findings against live code. Distinguish reproduced defects, architectural choices and unverified risks; do not assume every suggestion is a current bug.
- Establish meaningful owners for mechanisms shared by review, lint, delegation and project workflows. Review must not accidentally own unrelated common capabilities solely because they originated there. Colocate feature-owned implementation, data, adapters and behavior tests. Introduce build packages or interfaces only for actual boundaries; avoid generic shared dumping grounds.
- Directory purpose, file responsibilities, child roles and public/dependency declarations match implementation and consumers. Preserve boundaries and update moved references, exact oracles and decision application links. Do not widen permissions or exclusions just to pass. Standard mod.rs names remain permitted; renaming entries or meeting size limits alone does not establish architecture quality.
- Separate common configuration loading from independent capability readiness. A broken optional review/delegation configuration does not prevent an otherwise independent operation; relevant operations and full checks still diagnose it. Preserve P010 recovery and authorization boundaries.
- Managed commands obtain branch/context from the configured VCS owner instead of assuming Git. Verify Git, Mercurial and the existing private adapter with shared behavioral scenarios, including branch-scoped cleanup. Verify harness session ownership in supported Codex and Claude Code flows and resolve the audited risk from evidence rather than assumed environment variables.
- Candidate freshness accounts for all embedded resources, including review Markdown prompts. Prefer the existing build dependency owner over a divergent handwritten inventory where sufficient. Verify that a resource-only change reaches candidate content; preserve the stable pin until candidate acceptance.
- Maintain affected-test mapping for relocated/shared owners, resources, distribution, entry points and fixtures. Changed executable tests select themselves and targets remain valid. Smoke-only coverage must not conceal unmapped production changes; diagnose missing mappings rather than falling back to all tests on commits. Supported VCS commit flows select affected tests; integration runs the full suite.
- Recovery output stays compact as completed job history grows, with active/relevant results and access to details rather than every record and argv. Report malformed historical records without losing the remaining overview. Preserve ownership protection and explicit detailed inspection.
- Move shared architecture-test construction out of scenario modules imported by sibling tests. Correct obsolete external-VCS documentation and consumer paths affected by ownership changes. Avoid unrelated renames and additional historical registries.
- Add focused behavioral regression evidence for observed failure classes and preserve real consumer compatibility. Verify semantic ownership through review as well as lint. Deliver cohesive changes with affected commit checks and full integration verification; retain the feature branch and truthful memory evidence.
