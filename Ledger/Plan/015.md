# P015 — Git-backed component catalog and shared environment constructor

## Feature

Develop the existing YAML package composition and environment preparation into a shared manager/constructor backed by an ordinary Git catalog. Register, inspect, version and reuse components to assemble developer rigs, reviewers, architectural advisers and delegates. Consolidate existing mechanisms rather than introduce a parallel environment framework.

## User capability

The user keeps environment components and recipes in Git, chooses a recipe and supported harness, inspects the resolved composition and prepares the resulting environment. The same architectural guidance or tool component can serve several roles while each role retains its permissions and execution contract.

## Acceptance

- Store reusable component declarations, resources, module compositions and environment recipes in an ordinary Git directory. Components cover the existing supported skills, hooks, lint configuration, tools/programs, MCP settings, instructions and response/access contracts as applicable; a module groups components with one meaningful purpose. Reuse existing package identities, versions and resource ownership rather than duplicate component bodies across roles.
- Provide the necessary catalog registration and inspection through ordinary files and existing CLI/catalog mechanisms. The user can find a component, its selected version and its declared consumers/dependencies, and inspect a recipe's resolved configuration and value origins. Do not require an independent database, registration daemon or manual registry synchronized with the authoritative declarations.
- Recipes select modules/components, the role, supported harness, model settings and permissions. A shared constructor prepares usable Codex and Claude Code environments for developer, reviewer, adviser and delegate roles. Preserve meaningful differences in how those roles execute and validate results; common environment preparation has one owner.
- Resolve component dependencies, cycles, incompatible declarations and conflicting values before applying a recipe. Preserve explicit override semantics and the hook coordination boundaries from P011. Reuse existing composition, validation, preview and installation mechanisms where sufficient.
- Pin selected catalog contents to exact Git revisions and resource digests; retain enough resolved provenance to reproduce the same environment from the same inputs. Component updates do not silently change already pinned environments. Support explicit inspectable updates through existing setup/update ownership. This promises reproducible configuration/resources, not identical model outputs.
- Access constraints belong to the recipe and are enforced by the actual runtime sandbox. Demonstrate a developer environment with authorized editing, a reviewer with read-only source access, and an architecture adviser whose initial inputs are the task/acceptance and architecture.yaml contracts without direct access to other source files. Sharing a module cannot silently expand a role's permissions; adviser output cannot bypass lint or authorization.
- Secrets remain references resolved through the existing credential mechanism, not committed catalog values. Keep per-run state, model outputs and reports separate from versioned component definitions.
- Migrate or adapt existing project, review and delegation declarations using their current public entry points and installed-resource behavior. Avoid another canonical skill copy or environment format. Verification demonstrates shared component reuse across roles, deterministic resolution, pinned-version stability, conflicts/cycles, explicit update behavior and actual access isolation in independent consumer fixtures.
- Keep delivery small: ordinary Git files, YAML recipes, current composition and one shared preparation path. A web service, hosted registry, accounts, search/marketplace, publication/sharing workflows and infrastructure anticipating those services are explicitly outside the near-term scope. The user deferred those capabilities; do not create follow-up implementation merely to prepare for them.

## Delivery

The user requested one manager/constructor where the resources currently used by AgentRig, reviewers and advisers are registered, stored and versioned, then assembled into environments from modules/components. The user confirmed Git storage now and explicitly deferred a web service and sharing/discovery by other users beyond the near-term plan.

Current composition already resolves local YAML packages with identity/version/digest metadata, provenance, explicit overrides and conflict/cycle validation. Current environment declarations cover skills, programs, MCP and hooks. Extend those owners and consolidate their consumers; do not describe existing capabilities as absent.

Place this outcome after P014 by priority. P004 supplies existing composition and P012 supplies the intended ownership boundaries. P015 is pending: this request records the future constructor, not implementation of it or of a hosted service.
