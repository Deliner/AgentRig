# P016 — Scoped Rust boundary types and named values

## Feature

Add two configurable Rust lint rules: restrictions on types exposed at selected module boundaries, and restrictions on numeric/string literals in selected source. Help agents express project concepts and keep policy values with their feature owners using the existing lint, architecture, skill and hook mechanisms.

## User capability

The user selects the modules, forbidden boundary types, permitted constant declarations and explicit exceptions in YAML. The agent receives actionable findings and can replace an exposed raw type with a meaningful project type or move a policy value to its owning feature without wrapping every standard type or centralizing unrelated constants.

## Acceptance

- Implement both rules for Rust through the existing rule catalog and selection/configuration owners. Embedded agentrig lint and standalone agentrig-lint agree on configuration, findings and exit status. Advertise only implemented language support; this feature does not require extending these two new rules to all seven P013 languages.
- The boundary-type rule checks public fields and function/method parameter and result types in selected modules against configured forbidden types. Define supported visibility and type-expression semantics, including restricted visibility, references and generic containers. With String forbidden, submit(id: String) fails while submit(id: JobId) and Vec<JobId> are permitted when JobId is an actual project type. Internal implementation may use standard types.
- Distinguish an actual newtype from a type alias of a forbidden type; supported qualification or import aliases must not evade the rule. Unsupported resolution is explicitly diagnosed rather than reported as a verified clean boundary. State analysis limits and verify the documented behavior without promising complete semantic analysis of arbitrary Rust.
- The literal rule detects numeric and string literals in selected source outside permitted constant declarations and explicit exceptions. With no applicable exception, attempts < 5 fails and attempts < MAX_ATTEMPTS passes when the constant is defined in a permitted location. Analyze syntax, including documented macro handling, rather than matching source text; comments are not code literals.
- Give tests, diagnostic/format strings and ordinary values such as 0 and 1 precise documented exception semantics. Exceptions and allowed declaration locations are inspectable in configuration/selection explanations and affect only the applicable rule. Do not infer that a literal is a business rule or diagnostic from its text, silently exempt every macro, or impose a repository-wide literal ban.
- Constants and project types retain feature ownership. Permitted constant files are inventoried by architecture.yaml, and consumers obey existing public/private and dependency checks. Reuse those checks instead of adding a second architecture system. A shared constant requires shared meaning and ownership; equal values in independent features do not require deduplication. A constants file/module is sufficient where needed, without another build package.
- Findings identify the rule, path/location, offending type or literal, applicable canonical repair skill and executable rerun guidance. Use the existing skill requirement and P011 aggregation flow when findings overlap; do not add a separate skill-read tracker or hook dispatcher.
- Repair guidance requires the agent to inspect the concept, invariant, owner and consumers before introducing a type or constant. Favor meaningful newtypes/interfaces and names over ProjectString or NUMBER_FIVE, preserve behavior and update affected contracts/imports/tests. Review assesses semantic naming, encapsulation and proposed exception changes; passing lint does not prove those judgments or guarantee migration compatibility.
- Add real CLI evaluations under tooling/worker/evals/ using the P013 runner: violating, valid and repaired boundary/literal cases, aliases, allowed containers, selected/excluded paths, permitted declarations, explicit exceptions, comments and documented macro/unsupported-resolution cases. Assert expected findings and absence of unintended findings; no paid model calls or new evaluation framework.
- Keep commit verification selective through the existing impact map and include these evaluations in full integration verification. Document configuration examples and limits alongside actual capabilities and repair guidance. Do not activate a blanket standard-type ban or mass-rewrite existing code as an incidental part of adding the rules.

## Delivery

The user first proposed wrapping all standard Rust types and extracting every number/string, then accepted the narrower proposal: selected public boundaries, selected literal locations, explicit exceptions, feature ownership and semantic review. The user authorized recording this work in the plan; implementation remains pending. The separately discussed duplicate-filename rule was explicitly dropped and is not included.

Place P016 after P015 by priority. P013 is the prerequisite for its executable evaluation environment and lint coverage foundation; P011 guidance and P012 ownership are transitive prerequisites. No dependency on the P015 environment constructor is required.
