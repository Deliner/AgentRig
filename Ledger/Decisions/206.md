# D206 — Report a match that repeats a classification of enum variants

## Context

B162 under D151. The voxel-rust review at `2304625`, template 3, found one classification of `Status` variants into
`true` and `false` written four times, in `src/core/control/input.rs:119`, `src/core/control/simulation.rs:238, 260`
and `src/host/session/game.rs:136`; one of the places is already the function `accepted`. The card asks for a lint
error at the second and later places of a `match` without guards, bindings or `_`, with explicit paths to three or
more variants and the results `true` and `false`, that repeats anywhere in the project the same set of variant and
result pairs, whatever the arm order, with a reference to the first place, and for a skill that moves the check into a
method of the enum. It leaves open how syntax can tell that equal paths name one enum. Each file is analyzed alone,
and the places of the review lie in three files.

## Chosen

A Rust kind `repeated-classification` in the control-flow family at level error with the repair skill
`classify-in-the-enum`. The analysis of a file measures each `match` whose arms are all unguarded and map a path
`E::V`, alone or joined by `|`, to the literal `true` or `false`, with both results present and three or more paths
named, test code included, unless a `DECISION:` or `INVARIANT:` reference stands on the line directly above. A path
is identified by the last segment of `E` and by `V`, so `crate::protocol::Status::Accepted` and an imported
`Status::Accepted` are one variant. The measurement carries the classification written as the arms of one canonical
`match`: the paths of each result sorted and joined by `|`, the results in a fixed order. Evaluation compares the
classifications one rule measures across the files it selects, in path order and then line order: the first match of
each classification is not reported, and each later one is reported with the path and line of the first in its
message. The kind enters the runtime first, is pinned (D051) and is then enabled in the rig's `lint.yaml`, the
catalog and init with its skill.

## Rejected

- Identify a variant by the full path text: an imported and a qualified spelling of one enum would differ.
- Resolve imports and types to identify the enum: the engine reads syntax only (D035, D059).
- Compare matches only within a file: the reviewed copies lie in three files.
- Report the first match too: the card reports the second and later places and points them to the first.
- Exclude test code, as most control-flow kinds do: the card reports a repeat anywhere in the project; a test that
  restates a classification on purpose as an oracle takes a reference.
- Equate `Self::V` inside an impl of `E` with `E::V`: it needs the type of the impl.

## Rationale

A classification written in several places is one decision with several copies. The compiler makes each copy handle
a new variant, but it cannot tell that the copies must give the same answer, so a new variant or a changed answer is
decided again at each copy and the copies can drift. A method of the enum keeps one answer. Syntax gives the variant
and the result of each arm, and the last segment of the enum path holds across an import and a qualified spelling.

## Consequences

Two enums with one name in different modules, with the same variant names and the same classification, are taken for
one enum; the later match takes a reference. A classification written with `Self::V` is compared as `Self`. A match
whose arm is a block or whose pattern holds a binding is not measured. A justified match is neither a first match nor
a repeat. When the first match is removed or justified, the next one becomes the first and is no longer reported.
