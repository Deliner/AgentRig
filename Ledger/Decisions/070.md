# D070 — Reject placeholder architecture.yaml purposes

## Context

B030 (cluster 5 of the quality set, agreed 2026-10-29) asks that a directory's
`architecture.yaml` purpose read as a real description, so the project structure
is understandable from the tree and its contracts without reading code (5.2). The
contract loader already rejects an empty or multi-line purpose (D028/D043), but a
purpose that is technically nonempty yet conveys nothing — a bare `TODO`,
`Module`, `...` — passes. The structural engine is purely syntactic (D035), and a
whole-purpose placeholder is decidable from the contract text alone.

## Chosen

Tighten the `directory-architecture` contract validation (`architecture/policy.rs`
`load`) to also reject a purpose whose entire meaningful content — the trimmed
value, stripped of surrounding non-alphanumerics and lowercased — is empty or a
member of a small fixed set of placeholder/generic tokens (`todo`, `tbd`,
`module`, `directory`, `code`, `misc`, …). This is a stricter check inside the
existing rule, not a new `Kind`: no `lint.yaml` rule, no `catalog::ALL` entry and
no new skill. The existing error skill `refactor-large-directory` already covers
writing a real one-line purpose from actual ownership. Because the
`directory-architecture` rule kind is already delivered, the stricter binary
ships the check to consumers through the pin; the delivered rule-kind and skill
sets are unchanged (I020).

## Rejected

A new `Kind`/rule for purpose quality: the `directory-architecture` rule already
owns the contract text, so a separate rule is unnecessary indirection. A fuzzy
genericness heuristic (minimum word count, banned substrings inside a phrase):
high false-positive risk against the near-zero-false-positive bar (D035, D067). A
new repair skill: the architecture error skill already addresses stale and
missing descriptions. Shipping structure families (5.1) and one-capability-one-file
(5.3) as rules: they need symbol resolution or are declarative — kept as norms.

## Rationale

A purpose whose whole content is a single placeholder token is an unambiguous
stub, so it meets the high-signal, type-free bar for the gate (D035). A small
fixed set keeps the check decidable and near-zero-false-positive — the repository's
~95 real purposes are multi-word phrases and none match, and a phrase that merely
contains a generic word (`Module loader for the parser`) passes. This mirrors the
fixed-set philosophy of the hardcoded-secret rule (D067). Reusing the existing
rule and skill is the lowest sufficient rung.

## Consequences

A consumer's or this repository's `architecture.yaml` whose purpose is a bare
placeholder token becomes a contract error on `init` and in the gate; real
descriptions, including ones containing a generic word, pass. It extends the
contract validation of D028/D043/D044 and the fixed-set approach of D067. The
delivered rule-kind and skill sets are unchanged (I020); it supersedes nothing.
