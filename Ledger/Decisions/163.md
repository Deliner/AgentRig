# D163 — `ambiguous-option` reports `Option<Option<T>>` where Clippy's `option_option` does not check it

## Context

B113. D162 left `Option<Option<T>>` to the Clippy lint `option_option` alone, so a nested option in a type alias or a
`let` annotation, and a type spelled through such an alias, passed every rig check. D162 rejected keeping the nested
form in `ambiguous-option` where Clippy is silent. On 2026-11-11 the user chose that alternative: the rig rule reports
the nested form in each place Clippy does not check, and only there, so each place keeps one finding.

Five probes with Clippy 1.98.1, `-D clippy::option_option` and the rig's `clippy.toml` (`avoid-breaking-exported-api =
false`, D154, which `init` also writes for a new Rust project) classified the places. Clippy reports the outermost
nested option in parameters and return types of fn items, inherent methods, trait method declarations and default
methods, including fns nested in a trait impl method body; in named, tuple and variant fields, including a union field;
in `const` and `static` items outside a trait impl and an extern block, including those in a fn body; and through a
reference, raw pointer, slice, array, tuple, generic argument or either side of a qualified path `<A as B>::C` around
it. It reports a triple nesting once. It does not report a `type` alias, an associated type, a `let` annotation, a
closure parameter or return type, a `fn` pointer, `dyn` or `impl` trait including its generic arguments and associated
type bindings, a bound, a `where` predicate, a generic default, a turbofish, an impl header, a method or `const` of a
trait impl, or a fn or `static` of an extern block.

## Chosen

`ambiguous-option` reports every `Option<bool>` as before, and an `Option<Option<..>>` whose nearest enclosing place,
looking through references, pointers, slices, arrays, tuples, generic arguments, qualified paths and parameter lists,
is not one Clippy checks: a field, or the parameter list, return type or type of a fn item, fn signature, `const` or
`static` whose direct container is neither a trait impl nor an extern block. A nested option that is itself the sole
argument of an `Option` is skipped, so a triple nesting gives one finding. Test code and a `DECISION:` or `INVARIANT:`
reference on the line directly above stay exempt. The finding keeps the `name-the-states` repair.

## Rejected

A separate rule kind for the nested form: its repair, skill and exemptions are those of `ambiguous-option`, so a second
kind would only add a name. Reporting every nested option as D156 did: Clippy's places would give two findings again.

## Rationale

The rule closes the alias and closure bypass that D162 accepted, while each nested option still yields one finding, from
Clippy or from the rig. The places are a fixed property of the pinned Clippy version; the rule test's fixture is the
source the last probe compiled, so the rig's places and Clippy's places are checked against one text.

## Consequences

When the pinned Clippy starts checking another place, that place reports twice until the rule's list follows; running
Clippy over the rule test's fixture with the new version shows it. A project whose gate lacks the shared Clippy profile, or sets
`avoid-breaking-exported-api = true`, has Clippy's places unchecked. D163 supersedes D162's rejection of reporting the
nested form where Clippy is silent and its consequence that aliases and `let` annotations are not reported; the rest of
D162 remains.
