# D190 — init gives a base without commits an empty first commit

## Context

B145 asks for an empty project to work after `init`. A probe of an empty directory showed that `init` created the
repository with `git init -b <base>` and no commit. The guard rightly refused a commit on the base, and the setup
committed on a feature branch passed the gate. Then `feature-merge` failed with "cannot inspect Git ancestry" because
the base had no commit. A repository made by `git init` before `init` has the same unborn base.

## Chosen

- When `HEAD` has no commit after `init` finds or creates the repository, `init` writes a commit with the empty tree
  and the message `Start the repository`. It creates the base branch at that commit, failing if the base already
  exists, and points `HEAD` at the base. The index and the working tree stay as they were.
- A repository with a commit is unchanged. The generated setup then enters through a feature branch, the gate and
  `feature-merge` like any other change.

## Rejected

| Alternative | Why |
| --- | --- |
| `git commit --allow-empty` | it commits what the user already staged and runs hooks set outside the project |
| `feature-merge` creates a missing base at the feature tip | delivery would need a second path without a merge |
| `init` refuses until the user commits | the empty project would need a manual step the rig can take itself |
| Commit the generated setup on the base | the setup would reach the base without the gate |

## Rationale

`feature-merge` checks the ancestry of the base, so the base needs a commit. An empty-tree commit gives the base a root
without content, so every file still reaches the base through a feature branch and the gate.

## Consequences

In a repository without commits, `init` needs a Git identity, as any commit does. The first change starts with
`git switch -c <prefix><name>`, which keeps the untracked setup, because `feature-start` requires a clean tree.
