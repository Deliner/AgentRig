# D017 — Language-aware structural rules

## Context

The user requests language-specific rule handlers, one named condition per if, function/method size limits, and function/class input limits under complexity-discipline. The harness contains Rust and Python. Existing D016 rules measure entire files/directories, with both numeric severity thresholds required.

## Chosen

Extend D016 with compiled Tree-sitter Rust/Python handlers sharing one syntax-analysis result per file. Add named-if-condition, function-lines and parameter-count with source coordinates and focused repair skills. Preserve structural selectors and ordered numeric overrides. Extend the version 1 schema compatibly: numeric rules may specify either or both thresholds; named conditions use an explicit warning/error level with no numeric thresholds.

Start these new rules as warnings across the existing harness, at 40 function lines and 4 inputs; named-condition findings always warn. The user has not specified thresholds or requested rewriting the existing codebase. Blocking remains configurable and tested. Existing structural blocks remain unchanged. This supersedes only D016's requirement that every rule have two numeric thresholds.

## Rejected

Count syntax with regular expressions, treat extension selection as a parser, add dynamic plugins or a language server, infer types or expand macros, or refactor every historical implementation to introduce the new rules. Do not silently treat malformed source as passing.

## Rationale

Two concrete handlers satisfy the present multi-language need while keeping rule severity and configuration in the existing engine. Syntax trees distinguish declarations, defaults, types, comments and strings. Constructor declarations share function measurements rather than gaining a second rule. A simple Rust if let binds values rather than expressing boolean composition, so it remains allowed; chains are reported. Diagnostics cannot judge the meaning of a variable name or prove Python boolean types.

## Consequences

The guide defines exact counting, receiver exclusions, conditional-expression coverage and parser limitations. Parse errors block with source locations and skills even in warning-only configurations. New defaults expose existing debt without hiding it or forcing unrelated code changes. Explicit declarations are checked; generated constructors and macro expansions are outside parser scope. I015 covers named condition behavior in both languages; companion tests cover signature metrics, syntax failures, thresholds and selectors. Commit and merge gates automatically run the expanded linter on their selected trees.
