# D229 — Signature rules leave a signature that code outside the project sets

## Context

B202. An agent in voxel-rust could not implement the rustls trait `ServerCertVerifier`: its method
`verify_server_cert` takes five parameters besides `self`, `parameter-count` reports more than four as an error and
accepts no exception. Python has the same trap: a project under the rig cannot override `logging.Logger.makeRecord`
with its ten parameters. On 2026-11-21 the user said that a signature declared in someone else's code gets no finding,
neither on its declaration in the project nor on any implementation of it there, since the project cannot repair it;
interfaces the project declares stay under every rule. The user had Python added to the card through
`typing.override`.

## Chosen

- Rust: `parameter-count`, `boolean-parameter` (D062) and `tuple-as-record` (D088) do not measure the signature of a
  function of an `extern` block, nor of a method of `impl Trait for Type` whose trait path leads outside the project.
- A trait path leads outside when it starts with `::` and a crate of the `external.rust` list of the
  directory-architecture settings (default `std`, `core`, `alloc`); when its first segment is bound nowhere in the
  enclosing modules and blocks of the file and names such a crate, or the whole path is one name of a standard
  prelude trait; or when a `use` binds its first segment to a path that leads outside by the same rule, followed
  through at most eight imports, with aliases and `self` in lists.
- The trait is the project's own, and the method is judged, when the first segment is `crate`, `self`, `super` or
  `Self`, an item the file declares in that scope (module, trait, struct, enum, union or type), a name a glob import
  may supply, or an unbound name that is neither a declared crate nor a prelude trait. An explicit binding wins over
  a glob.
- Python: `parameter-count` and `boolean-parameter` do not measure the signature of a method decorated with
  `override` from `typing`, written `@override` after `from typing import override` or `@typing.override`, when no
  class of the project along its base chain declares a method of that name and the chain reaches a class outside the
  project: imported from a module of the `external.python` list or a builtin class, a class without explicit bases
  reaching `object`. A base the analysis cannot trace, such as a name from a star import, makes the method judged.
- A method without that decorator is judged as before, even when it overrides a foreign method, and so is a class
  that implements a foreign `Protocol` without inheriting it.
- The body is measured as before in both languages: length, nesting, branching and every rule over the code inside.
- The language analysis learns which code lies outside the project through an injected view that the rule evaluation
  builds from the first rule carrying directory-architecture settings, or from their defaults.
- Each of the three rule descriptions names the signatures left unmeasured.

## Rejected

- Lint exceptions for `parameter-count`: the rule refuses them by design, and an exception per foreign trait would put
  the cost of the foreign signature on every implementation.
- Exempting every trait implementation, as `same-type-parameters` and `ambiguous-option` do: a trait the project
  declares would escape the budget on each implementation, while its declaration alone would carry the finding.
- Resolving trait paths across files: a single file holds the declaration, imports and items that decide the binding,
  and an unknown binding is judged, which only keeps the earlier behavior.
- Treating a Python method as foreign without `override`: nothing in the code states the intent to follow a foreign
  signature, and mypy can verify the marker where the project runs it.

## Rationale

A project can implement any foreign interface, override a method of a foreign class and declare an external function
without a workaround, while every interface the project declares remains under all rules.

## Consequences

A trait reached through a glob import, an `extern crate` alias or a path the file cannot bind keeps its findings until
the import is written explicitly. The honesty of `@override` rests on mypy; a project that does not run mypy has no
check that the marked method overrides anything. Declaring more external crates widens what the rules leave.
