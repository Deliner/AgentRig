# D139 — lint-baseline lowers from the larger of the working and the HEAD-committed count

## Context

B101. In voxel-rust `lint-baseline` lowered the count of a cycle finding on world/tests.rs to 0 while the finding was
printed on world/metadata.rs. The commit was refused for another reason, the code changed and the finding returned to
world/tests.rs. The next commit was refused with "the lint baseline accepts 0", and a rerun of `lint-baseline` could
not raise the count because D123 only lowers it from the working file. The baseline had to be restored from `HEAD`
with `git checkout` and recorded again. The user's /goal of 2026-11-10 selected B101 with every other Backlog card and
left the choices to the executor.

## Chosen

When a working baseline exists and the lint root is a Git repository whose `HEAD` contains the baseline at the same
path, `lint-baseline` takes for each rule and path pair the larger of the working and the committed count as the limit
and writes the lower of that limit and the current count, dropping pairs at zero. A rerun therefore restores a count
lowered too early up to its committed value, never above it, and adds no pair absent from both files. Without a
committed baseline, outside a Git repository or without a working baseline, recording behaves as D123 states. Lint,
the gate and the standalone `agentrig-lint` are unchanged.

## Rejected

Taking the limit from `HEAD` alone: after deleting the file and recording again to accept new errors, as D123
prescribes, a rerun before the commit would drop the newly accepted pairs. Raising counts to the current findings:
the same run would silently accept growth, which D123 rejects. Reading the staged baseline instead of `HEAD`: staging
the lowered file would make the early lowering permanent before any commit accepted it. Reading `HEAD` through the lint
inventory, which already uses Git: the inventory discovers maintained files and does not own their committed content.

## Rationale

The committed baseline is the count the project has accepted in review; a working-file lowering is a suggestion that
only a commit makes final. Taking the larger of both keeps every acceptance a reviewer can see and still makes the
command a one-way step relative to `HEAD`.

## Consequences

An early lowering is repaired by rerunning `lint-baseline` without Git commands. Once a lowered baseline is committed,
that count becomes the new ceiling, as before. Deleting the file and recording again still accepts new errors.
`structural_lint` becomes the 13th directory depending on `shared/vcs`, so its declared dependents budget rises from
12 to 13, the conscious budget change D079 requires. It refines D123's "never raises a count" to "never raises a count
above the committed one" and supersedes nothing else.
