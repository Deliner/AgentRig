# D123 — Ratchet mode through a per-rule, per-path error baseline beside the lint configuration

## Context

B064 (idea from the research arc; selected by the user's /goal 2026-11-07,
which leaves the baseline format, its granularity and the interaction with
`--staged` to delivery). A project with history cannot enable strict rules at
once: hundreds of existing errors block the gate, so the rules stay off. A
ratchet accepts the existing errors, fails when they grow and lets them
shrink.

## Chosen

Ratchet mode holds while a baseline file lies beside the lint configuration,
named after it: `lint-baseline.yaml` for `lint.yaml`, so
`.agentrig/lint-baseline.yaml` in a delivered project. Its presence is the
mode; deleting it returns to strict lint. The file is strict YAML mapping
rule IDs to paths and their accepted error counts, sorted. Only error
findings count; warnings never fail, and configuration errors are never
accepted.

Lint applies the baseline wherever it runs with that configuration: `lint`,
the gate's lint check and the standalone `agentrig-lint`. Errors of a rule in
a path whose count is within the baseline become warnings marked as accepted
by the baseline. When the count exceeds the baseline, all errors of that rule
in that path stay errors and name the accepted count, because a per-path
count cannot tell which one is new. Rule and path pairs whose counts fell
below the baseline are reported on stderr with the command that lowers it;
that never fails lint.

`lint-baseline`, a worker command with a delivered `just` recipe, records the
current counts when no baseline exists. Afterwards it writes, for each
recorded pair, the lower of the recorded and current count, drops pairs at
zero, never raises a count or adds a pair, and reports the pairs above the
baseline. Accepting new errors means deleting the file and recording again, a
change visible in review. The standalone `agentrig-lint` keeps writing
nothing.

The gate checks an export of the index under `--staged`, so lint reads the
staged baseline like any other staged file; no special case exists. After
installation, when lint is enabled and existing files have errors, `init` and
the interactive wizard print their number and offer `just lint-baseline`;
recording stays the project's decision.

## Rejected

A `baseline` field in `lint.yaml`: the command would have to rewrite a
hand-edited policy file with its comments, and field and file could
disagree. Line granularity: unrelated edits move line numbers. Counts per
rule only: fixing one file would pay for a new error in another. Counting
warnings: they never fail, and the ratchet concerns the gate. A command that
rewrites current counts: lint suggests it after a decrease, and the same run
would silently accept growth elsewhere. Comparing the staged baseline with
`HEAD` in the gate: history machinery where deletion is already a visible
change. Recording the baseline during `init`: adopting strict rules
gradually is a choice, not a default.

## Rationale

Rule and path is the coarsest grain that stays stable under ordinary edits
and still pins errors to where they are. Keeping the mode in the file's
presence leaves the policy file untouched and makes the transition back to
strict lint one deletion. A lowering-only command turns the suggested update
into a one-way step.

## Consequences

A consumer with history enables every default rule at once and records the
baseline; new errors fail the gate, fixed ones lower it. Renaming a file with
accepted errors moves them to an unrecorded path, so the rename needs a fresh
baseline. An empty baseline behaves like strict lint. It ships B064 in full;
it supersedes nothing.
