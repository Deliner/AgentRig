# D217 — Lint the rig with the installed runtime beside the candidate

## Context

The bypass audit of 2026-11-19 (B158, example E6) found that the rig's `lint` check is the catalog command `lint`,
which builds the candidate runtime from the checked sources and lints with it. A change that weakens a rule's detector
together with the tests that pin it therefore judges itself and passes. B158 asks that the installed linter also check
a rig change, so that code it rejects does not pass even when the candidate accepts it. The rig difference list of
D189 is the only record that the rig's `lint` check differs from the one `init` writes, and any change could edit it.

## Chosen

- The rig's `lint` check becomes the native `lint` kind that `init` writes for every project: the installed runtime
  that runs the gate lints the checked tree in process with the rules of the pinned revision.
- A `candidate-lint` check keeps running the catalog command `lint`, so the rig is also linted by the rules it develops.
- The rig difference list no longer names the `lint` check and names `candidate-lint`. It joins the protected files of
  `hooks.yaml`, so returning the rig to candidate-only lint or accepting any new difference needs the user's approval.

## Rejected

- Linting the rig only with the installed runtime: a rule added or repaired in the branch would not check the rig
  before the pin.
- Detecting a weakened rule by comparing its tests with the base: syntax cannot tell a weakened test from a corrected
  one, while the installed runtime already holds the accepted rules.
- Building the runtime of the base revision for each commit: it costs a full build per commit, and the installed
  runtime is already built from a revision that passed the gate.

## Rationale

The installed runtime comes from a revision that passed the gate and is pinned forward only (D051, D213), so the change
under check cannot alter its rules, and its configuration is protected by D214. The native kind already serves every
initialized project, so the rig only stops differing from `init`.

## Consequences

Each rig commit lints twice. A setting the installed runtime does not know, such as a new rule kind in `lint.yaml`,
fails the native check until the revision with it is pinned, so such a rule lands in two phases with a mid-branch pin,
as D117 did. A pin moves the installed rules forward: once `just bootstrap HEAD` installs a weakened rule, later commits
are judged by it, so the guarantee covers code committed together with the weakening or before its pin.
