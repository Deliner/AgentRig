# D226 — Added lint rules and the pins of a consented task need no approval

## Context

B180. Under D214 and D218 every new lint rule took three confirmations by the user: a mid-branch pin, the lint
configuration that enables the rule and the final pin. On 2026-11-20 the user said: «Меня заебало что я постоянно !
just approve делаю. Я же хочу дать тебе задачу и забить нахуй, и потом просто вернуться и увидеть что все сделано».
Of three options shown, one branch for several rules, rule additions without approval and a standing consent for
pins, the user chose the last two: «Давай варианты 2 и 3». The lint rules measure independently: the dependencies of
the directory-architecture rules are joined, the configuration check allows one rule with `pairs`, and an exception
names a configured rule ID, so a rule added beside the others only adds findings.

## Chosen

- The lint configuration named by `paths.lint` stays protected, but the agent hook no longer refuses its edits and
  `just write` operands. Without approval the feature commit guard accepts its staged content only when the committed
  file exists, every committed rule stays unchanged and in order among the staged rules and the other settings are
  equal; anything else, a removed or disabled rule, a threshold, an exclusion or an unreadable file, needs the user's
  approval as before.
- The user gives a standing consent with `just consent`, which the agent hook refuses like `just approve`. It records
  in the runtime state path `consent` the Plan items that are pending or active at that moment and holds while any of
  them is still pending or active, until `just revoke-consent` ends it. The path joins the protected runtime state.
- Under consent `propose-pin` accepts only `HEAD` with a working tree clean apart from State, runs the branch gate of
  `feature-merge`, and when it passes installs the revision with `git.install`, writes the pin, records that content as
  approved for the commit guard, which still requires it to descend from the committed pin, and appends the revision
  with the source files changed since the pinned revision to the consent record. Without consent it prepares the
  proposal for `just approve` as before.
- `just consented-pins` lists every pin set under consent with its changed source files. `init` delivers the three
  recipes.

## Rejected

- One branch for several rules: it lowers the number of confirmations but keeps them, and the user wants none.
- Comparing the text of the lint configuration: a line inserted into an existing rule, such as `enabled: false`, is
  also an addition of text, while the parsed rules tell an added rule from a changed one.
- Accepting only rules of new kinds: added rules of known kinds measure independently too.
- A consent without an end or for every protected file: hooks, recipes, configuration modules and lint weakenings keep
  their per-change approval, and a consent bound to the selected Plan items ends with that task.
- Letting the agent run `just approve`: approval is the step the agent cannot take, and consent keeps it so.

## Rationale

An added rule can only make lint stricter, the same reason a lowered baseline needs no approval under D214. A pin set
under consent passes the same gate as a merge and the same descent check as an approved pin, and the user reviews it
afterwards from the list instead of before each pin.

## Consequences

A new rule commits as soon as the pinned runtime knows its kind; reformatting or comments in the lint configuration
also pass when its settings are equal. While consent holds, the agent installs runtimes and moves the pin without
asking, so a consent is given for a selected task only. The consent and its list live in local runtime state and are
not committed.
