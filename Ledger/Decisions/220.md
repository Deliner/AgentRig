# D220 — A new lint exception commits only with the user's approval

## Context

Since D219 an exception names its rule and its decision lists it, but the agent writes both the exception and the
decision, so the list does not show that the user agreed to lift the rule. B174 AC4 asks that a new exception pass a
commit only after the user's `! just approve`, that the user see its rule, file, line and decision first, and that
an exception count as new again once the line beneath it changes or it moves to another line. On 2026-11-20 the user
chose this variant: «Да, Б».

## Chosen

- An exception is identified by its file, decision, rule and the trimmed text of the line beneath it. The exceptions
  of a file are counted as a multiset, and those of one content beyond those of another are new.
- The commit guard of a feature branch compares each staged file with `HEAD`. It refuses a commit whose new
  exceptions exceed the approved ones, lists each as file:line, decision, rule and the text of the line beneath, and
  names the protected change skill. Deleting an exception needs no approval.
- `just approve` also records the new exceptions of the working tree against `HEAD`, together with the protected
  content, and prints them. Each approval replaces the record.
- Contents are read as Git objects of the index, of the working tree staged into a temporary index and of `HEAD`, so a
  symlink or a submodule carries no exception, and a content that is not UTF-8 carries none, as lint reads none.
- The approval record holds the protected files and the exceptions; a record of the earlier form reads as empty (D185).

## Rejected

- Identifying an exception by its line number: an edit above it would ask for approval again while neither the
  exception nor its line changed, and the line number does not show what the user agreed to lift.
- A protected list of approved exceptions in a configuration file: it would repeat the decision's list of D219 and
  separate the exception from the reason recorded in its decision.
- A confirmation prompt inside the approve command: the user confirms by running it after the refusal showed the
  list, as for protected files.

## Rationale

An exception changes what lint enforces, like an edit of a protected file, so it reuses the approval that already
carries the user's confirmation. Tying it to the line beneath keeps an approval from covering code the user has not
seen.

## Consequences

Each new or moved exception, and each edit of the line beneath one, waits for the user; the rig's move to named
exceptions needs one approval. Tests and `just candidate` still run project code unconfined and could write the
record, the residual D213 accepted. Until a pin moves, the installed runtime does not yet apply this guard.
