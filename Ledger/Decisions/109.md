# D109 — Deny `print_stdout`/`print_stderr` outside the console owner, which prints under a justified `allow`

## Context

B061 (research arc; the user's /goal of 2026-11-04), delivered as P067. D060 chose the panic-risk deny profile
for this repository's clippy gate and excluded `print_stdout`/`print_stderr`: AgentRig is a CLI whose output is
the product, and the two lints would have fired on about 73 legitimate output sites spread over 24 files. D060
also recorded that the print lints do not return without revisiting that decision. P067 VAC-A (`92a4703`) gave
the output one owner: `Project/shared/console` exposes `stdout`, `stderr` and `prompt`, and the 73 production
sites print through it, so outside one file the lints no longer describe legitimate product output. The owner
is a function surface rather than `macro_rules!`: the architecture analyzer of the structural linter (D059)
does not analyze `#[macro_export]` or any local-crate macro invocation, and a macro-based owner would have
stopped the dogfood analysis of the whole crate.

## Chosen

The `clippy` command in `.agentrig/commands.yaml` gains `-D clippy::print_stdout` and `-D clippy::print_stderr`.
`Project/shared/console/mod.rs` opens with `// DECISION: D109` followed by
`#![allow(clippy::print_stdout, clippy::print_stderr)]` (the justification form of D080), so the three print
macros inside the owner stay legal and any `print!`/`println!`/`eprint!`/`eprintln!` elsewhere in library or
binary code fails the gate. Output is the product; the owner prints. The lints name only those macros: the raw
byte relay of child output in `command_runner/jobs/streams.rs` (`io::stdout().write_all`) and the owner's
`io::stdout().flush()` are outside both the lints and this record. Test code is unchanged because the gate runs
clippy without `--all-targets` (D060, D107).

## Rejected

Keeping the exclusion: its reason — legitimate output sites spread over the crate — no longer holds, and a new
print site outside the owner would silently reopen the spread. Per-site `allow`s: D060 rejected blanket
`allow`s, and one module-level `allow` at the owner is the owner's contract, not a blanket. A `macro_rules!`
owner surface: not analyzable by the architecture analyzer, so the dogfood gate would stop analyzing the crate
(D059). `-F` (forbid) instead of `-D`: forbid cannot be overridden by the owner's `allow` and would deny the
owner itself. Denying the print lints in the delivered `init` profile: clippy is this repository's dev-gate,
not an `init` capability (D060).

## Rationale

With one owner, the two lints become the cheapest falsifiable guard that the owner stays the only printer. The
probe for B061 AC2 inserted a `println!` and an `eprintln!` into `command_runner/summary.rs`:
`tooling/worker/run run clippy` failed naming `clippy::print_stdout` and `clippy::print_stderr`, and restoring
the file returned the gate to green. D060 excluded the lints for lack of an owner; that exclusion is superseded,
while the rest of D060 — the panic-risk deny set, no `--all-targets`, dev-gate only — stays in force.

## Consequences

Supersedes the print-lint exclusion of D060 and nothing else of it. New product output goes through
`console::stdout`, `console::stderr` or `console::prompt`, or amends the owner; a print macro anywhere else in
library or binary code fails the commit gate. The owner's `allow` is bound to this record by D080 and
`memory-check`; `.agentrig/commands.yaml` and the owner carry the application links. Closes B061 AC2 and AC3;
with AC1 delivered on VAC-A, B061 is complete.
