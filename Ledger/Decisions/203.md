# D203 — Write programs change only the project, and a sandboxed process cannot start a program outside it

## Context

B155 AC1–AC2, from the audit of 2026-11-19. `just write` ran its programs without a sandbox, so `cp x ~/.zshenv`
changed a file outside the project. The macOS profile of `just read` starts from `(allow default)`: inside it,
`open -g -j -n APP` and AppleScript's `launch` had LaunchServices start an application outside the sandbox, which wrote
a file the sandbox refused. A command's `read_only` boolean could not name a third mode. In a probe, `uv run` inside a
sandbox that writes only the project failed to open its cache in the home directory. The rig's gate runs uv and cargo
from the Git hooks that `just write -- git commit` starts.

## Chosen

`access` replaces `read_only` in commands and job records:

| Value | Run |
| --- | --- |
| `read-only` | platform sandbox without network, writing only its temporary directory and terminal devices |
| `project` | the same sandbox, writing also the project root |
| `unconfined` | directly, the default |

On macOS the sandbox refuses `lsopen` and `appleevent-send`, so a process cannot have LaunchServices or another
application start a program outside it. On Linux a `project` run binds the root writable over the read-only system.

A listed program may set its own `access`, which replaces the command's for runs of that program. Init's `write` is
`project` and its `git` is `unconfined`: Git's hooks run the project's gate, whose tools write caches outside the
project, while Git itself writes only the repository through the listed subcommands. Doctor checks the sandbox backend
when any command is sandboxed. The rig's `write` follows once its pinned runtime reads `access`.

## Rejected

| Alternative | Why |
| --- | --- |
| Confine Git and its hooks as well | the gate's tools write their caches outside the project, so every commit would fail |
| Allow the gate's cache directories | each tool and platform keeps its cache elsewhere, so the list would follow each project |
| Run Git through a separate catalog command | agents and guides use `just write -- git`, and a program setting states the exception |
| Keep `read_only` and add a project boolean | the pair has an undefined combination |
| Refuse Apple Events only | `open` asks LaunchServices without an Apple Event |

## Rationale

The agent chooses the programs and paths of `just write`, so the sandbox, not the program list, keeps their writes in
the project. Git differs because its hooks run the project's own checks, which need the caches that make them usable.
Refusing LaunchServices and Apple Events closes the way a sandboxed process asks a process outside to act for it.

## Consequences

A write program that targets a path outside the project fails with the operating system's permission error. Git keeps
running hooks and programs from its configuration outside the sandbox; B157 governs changes to `.git` settings. The test
covers launches through `open` and AppleScript; an Apple Event to a running application needs the user's Automation
consent, so no test sends one. The Linux form awaits a Linux run (B112). Job records written before read as
`unconfined`.

D203 supersedes D154's choice that commands and job records keep the boolean `read_only` field; the rest of D154
remains. It extends D034's platform sandbox to project-confined commands.
