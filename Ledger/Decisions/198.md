# D198 — Allowed program languages are a lint rule

## Context

B151: the rig's lint rules, tests and agent guidance cover Rust and Python, yet nothing stopped an agent from adding a
program in another language, such as a `.js` tool in a Rust project, which then escapes every rule. The card asks for
a project setting that lists the allowed program languages, filled by `init --language` and in the rig by its current
languages, and for a lint error that blocks the commit when a program is in another language. The error names the
file, its language, the allowed list and the absolute path of a skill that explains the rewrite. YAML, JSON, TOML and
Markdown are not programs, and vendored code stays excluded as under D112. The card left open how a file's language
is found and which languages the rig allows besides Rust. The rig's own programs are Rust, its shell launchers, hooks
and distribution scripts, and one Python file of the test example project.

## Chosen

A `program-language` lint rule kind, target file, level error, with a required nonempty `allowed_languages` list.
Its names come from one table of 16 known program languages; configuration check rejects an unknown name, an empty
list, a rule of this kind without the list and the list on another kind. A file's language is the one its extension
names. A file without an extension is a program when its first line starts with `#!`; its language is the interpreter
named there, after `env` and its options, without a version suffix. A file whose extension or interpreter the table
does not name is not a program. The finding names the language and the allowed list and points to the new skill
rewrite-in-allowed-language. `init` adds the rule over `**` with its `--language` value and excludes the hooks and
the launcher it generates under the service directory; the rig allows rust, shell and python with the same excludes.
`just write` also runs `ln`, since a new skill lives in its group behind a flat link and, after D197 removed scratch,
no listed program could make one.

## Rejected

| Alternative | Why |
| --- | --- |
| A list of forbidden languages | a language missing from the list would pass; an allowed list closes the set |
| Find the language from content for every file | an extension already names it; content decides only without one |
| Reuse the lint handlers' language registry | handlers cover only languages with syntax rules, Rust and Python; shell and the languages to reject have none |
| Keep the list in project.yaml | the rule that enforces it would read another module; a lint rule owns its settings, like pairs |
| Allow only Rust in the rig | its launchers and hooks must run before any runtime exists, and rewriting them is outside B151 |
| Leave the skill directory flat at the skills root | the root would hold 16 entries against the limit of 15 |

## Rationale

An allowed list fails closed for a language nobody anticipated, and a single table owns every language name, so
validation, the catalog and evaluation cannot disagree on which names exist. Excluding the generated hooks and
launcher keeps a Rust or Python project's list to the language its own code uses.

## Consequences

A language unknown to the table is not reported until a row names it; a new row is a product change. Widening a
project's list is a policy change that the skill sends to the user. The rig's rule can only follow the pin of the
runtime that knows the kind, because the installed runtime validates the rig's lint configuration.
