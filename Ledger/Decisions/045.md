# D045 — Configuration repair stays available while the configuration is invalid

## Context

B001 requires that a configuration error not lock the agent out of repairing
it in the same session. Hooks loaded the configuration on every event and
denied every tool call when loading failed, including edits of the broken file
and `just config-check`; the user had to restore .agentrig/lint.yaml outside
the session. The denial kept only the top-level error context, and a corrupt
project.yaml was reported as required.

## Chosen

When the configuration fails to load, hooks answer from the error alone.
SessionStart reports the diagnostic. Edits are allowed only when every target
is a configuration source: .agentrig/project.yaml, its module files, and the
lint and reminder files named by project.yaml and hooks.yaml while those stay
readable. The only shell command allowed is `just config-check`. Other tool
calls are denied with the full error chain, the configuration repair skill and
the permitted actions. Every event reloads the configuration, so a passing
check restores normal behavior. Validation errors name their module file, and
a missing file is reported as unreadable rather than required.

## Rejected

Disable hooks on configuration errors; store a repair mode or a fallback
configuration; allow arbitrary shell commands or source edits during repair;
require reverting configuration from Git.

## Rationale

Allowing exactly the configuration sources and their check gives a repair path
without letting a broken configuration bypass edit guidance, command routes or
the commit gate.

## Consequences

Commit and merge gates still fail while the configuration is invalid. The
agent's own file reading stays available; `just read` depends on the command
catalog and is unavailable until the repair passes.
