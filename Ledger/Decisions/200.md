# D200 — The hook sees every tool and refuses what it cannot check

## Context

B152 AC1 and AC2: Claude Code and Codex called the hook only for tools matching
`Bash|Shell|exec_command|apply_patch|Edit|Write`, and the dispatcher let every other name through. Monitor runs shell
commands, NotebookEdit writes files, a Skill can run its own shell commands, EnterWorktree and an Agent with worktree
isolation create a checkout and an MCP tool may do anything, all without the shell guard or edit routes. The hook
command ended in `exec` of the launcher, so a missing or non-executable launcher exited 126 or 127, which both agents
treat as a non-blocking error, and the call ran unchecked. Claude Code and Codex match every tool with `*`, block on
exit 2 and show its stderr to the agent (code.claude.com/docs/en/hooks, learn.chatgpt.com/docs/hooks).

## Chosen

Both registrations match `*` for PreToolUse. One classifier in `agent_hooks/tools.rs` gives each call one of four
outcomes. Shell: Bash, Shell, exec_command and a Monitor with a command, checked by the shell guard. Edit:
apply_patch, Edit, Write and NotebookEdit, whose `notebook_path` gets the edit routes. Passive: a fixed list of Claude
Code and Codex tools documented to neither run commands nor write files, an Agent without worktree isolation and a
Monitor WebSocket watch, which pass as before. Refused: every other call, denied with a reason that names the tool;
configuration recovery keeps the same classification. The hook command no longer uses `exec`: when resolving the root,
starting the launcher or running the hook fails, it prints that the AgentRig hook could not run and exits 2.

## Rejected

| Alternative | Why |
| --- | --- |
| A list of refused tools, passing the rest | a tool nobody listed, such as a new MCP server, would pass unchecked |
| Map each refused tool to the checks it needs | Skill shell, worktree creation and MCP effects have no input the hook can read before they run |
| Disable skill shell execution in Claude Code settings | it covers one tool, and Codex and MCP tools still need the refusal |
| Keep `exec` and rely on the launcher's exit 2 | a missing or non-executable launcher never runs, so its exit code cannot apply |

## Rationale

Matching every tool and passing only a known list makes an unknown tool fail closed, while the list keeps reading,
searching, planning and messaging tools working as before. The exit-2 fallback lives in the registration because only
the shell that starts the launcher can observe that it failed to start.

## Consequences

A new tool of either agent is refused until a release adds it to a class; widening the passive list is a product
change. Every tool call now starts the hook process, adding its start-up time to reads and searches. A hook that
times out is still a non-blocking error for both agents.
