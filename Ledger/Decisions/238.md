# D238 — A cargo oracle is bound to the module path of its file

## Decision

`memory-check` accepts a cargo invariant oracle only when its target equals a module path of the linked file joined
by `::` with the file-local qualified name of exactly one function that carries the invariant marker. The module
paths come from the `mod`, `#[path]` and literal `include!` declarations followed from the crate roots of the
manifest that the oracle's check command names. A target that leads to another file, or that matches no marked
function or several, fails as a missing or ambiguous marked function; a linked file that no crate root reaches fails
and names the command. Discovery still requires cargo to list the target, and pytest matching is unchanged. The
Cargo manifest reader and the module walk move to `structural_lint/architecture/cargo_crates.rs`, which
`memory-check` shares with `config-check` (D144), and `shared/fs_with_context` takes it as its 25th dependent. The
I002 oracle expects a cargo target outside the module paths of its file to fail as a missing marked function.

## Reasons

- B109 requires that a cargo oracle pass only when its target leads to a function in the linked file (AC1) and fail
  when its target leads to another file (AC2).
- Under D157 a marked function with the target's local name in a file other than the one cargo runs passed
  `memory-check`, as D157's Consequences state.
- A file's module path is a prefix of each test path inside it (D157), so the target equals that path plus the
  file-local name exactly when the test lies in that file.
- `config-check` already takes a cargo test file's module path from the crate roots of the manifest its command
  names (D144), so `memory-check` reuses that walk instead of writing a second one.
- `project_setup` depends on `project_memory`, so the walk had to leave `project_setup` for an owner both use
  (D157); `structural_lint/architecture` already holds the module walk of D144.

## Alternatives

- Keep the match by trailing segments of D157: no manifest walk in `memory-check`. Not applied: a same-named marked
  test in another file passes, which B109 AC2 refuses.
- Keep the manifest reader in `project_setup` and call it from `project_memory`: no move of code. Not applied:
  `project_setup` depends on `project_memory`, so the call would close a cycle.
