# D204 — A commit through `just write` runs its hooks, and a catalog command cannot change the base

## Context

B156 AC1–AC2, from the audit of 2026-11-19. `just write -- git commit --no-verify` or `-n` skipped pre-commit, so the
commit escaped the gate and the refusal of commits on the base. `git branch -f`, `checkout -B`, `switch -C`,
`branch -D`, and a rebase or cherry-pick on the base moved the base without a merge, and `feature-merge` would then
push it. An empty `.git/MERGE_HEAD` let a commit on the base pass `guard-commit`, which accepts merge commits there.
Since D203 Git under `just write` runs outside the sandbox with its hooks. The agent reaches Git only through catalog
commands; the user's own Git and `feature-merge` run outside them.

## Chosen

Init's and the rig's `write` deny Git's `--no-verify` and `-n`, `git commit`'s short form of it, in every spelling D202
reads.

The runner gives every catalog process `WORKER_CATALOG_ROOT`, the canonical project root. The reference-transaction
guard refuses a prepared update of `refs/heads/<base>` when that variable names the repository's root, so creating,
moving, rewriting, deleting or committing to the base fails inside a catalog command, whichever Git command causes it.
`feature-merge` removes the variable from its own Git processes, so it merges into the base also inside a catalog
command.

## Rejected

| Alternative | Why |
| --- | --- |
| Recognize base-changing arguments of `write`'s Git | subcommands have many spellings and implicit targets, such as a commit or rebase on the checked-out base |
| Refuse every base update outside `feature-merge` | the user's own pull or merge on the base would fail |
| Drop the `MERGE_HEAD` exemption of `guard-commit` | the reference guard already refuses the agent's commit, and the user's own conflicting merge on the base needs it |
| Mark catalog runs with a file in `.git` | `just write` writes `.git`, and the file would outlive the process |
| A marker that does not name the root | the gate's tests create repositories that inherit it and would refuse their own base changes |

## Rationale

Git reports every reference update to the reference-transaction hook before applying it, so one check there covers
each command that changes the base. The marker states who started the process, not which arguments it used, so a new
Git spelling cannot pass it.

## Consequences

Git's `-n` means a dry run or no commit in other `write` subcommands, and these are refused too. Rebase and cherry-pick
still create commits on a feature without pre-commit; `feature-merge` passes the whole branch through the gate. A
catalog command the agent defines can remove the variable; B157 governs changes to `.agentrig` and `.git` settings.
The user's own Git outside catalog commands changes the base as before.
