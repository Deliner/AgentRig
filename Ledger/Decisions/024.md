# D024

## Context

The user requested one adjacent-version upgrade with visible local conflicts, preserved project settings and memory, stale-plan checks, resumable application and rollback. Existing init provides stock release assets; runtime pins otherwise prevent operation in a mixed installation.

## Chosen

Support the explicit 0.1.0 to 0.2.0 transition from a local executable exported through init. Keep schema version 1 and migrate only the runtime TOML value. Preserve configuration and memory contents. Compare installed receipts, reconstructing legacy stock content from the old executable when needed. Conflicts require an explicit keep or replace resolution. Record kept hashes separately from stock hashes; doctor accepts reviewed Git adapter content while retaining registration and permission checks.

Freeze the resolved plan and verified preimages before writing. Store atomic file progress, check results and recovery instructions in a technical operation journal outside agent State. Resume or roll back against recorded before/after states, preserving later user edits. Retain a restored operation when another apply begins. Use the supplied new executable for recovery; allow existing navigation and command hooks to validate the supported old pin only while an upgrade is active. Keep ordinary config validation strict and block delivery until application or rollback finishes.

## Rejected

Automatic conflict merging, a general migration framework, rebuilding configuration from defaults, rewriting product memory, Git reset for rollback, and weakening ordinary version validation.

## Rationale

The existing package exporter and project checks provide the required release and validation boundaries. Explicit resolutions preserve local intent. A small durable journal and retained preimages cover interruption without introducing another agent task registry.

## Consequences

Users review a concrete plan, retain the new executable for recovery, and resolve incompatible local files or failing project checks before completion. Only the named transition is implemented; other transitions require their own actual migrations. Runtime recovery artifacts should remain ignored by the consumer repository.
