# D029 — Consistent size applicability for flat memory registries

## Context

The configured memory validator requires each plan detail at exactly Plan/NNN.md and rejects a detail link that does not match its ID. P015 adds the sixteenth immediate entry including architecture.yaml, conflicting with the general directory-entry limit of fifteen. Ledger/Decisions and Ledger/Invariants already have exact-directory exemptions from this numeric rule for the same flat indexed representation.

## Chosen

Apply the existing numeric directory-size exemption to Ledger/Plan as well. Keep this limited to the exact flat registry directory, with a reference to this decision in the lint configuration. Preserve the memory schema and complete architecture inventory validation.

## Rejected

Raise general limits; exclude the entire Ledger from lint; move detail files into unsupported nested paths; hide entries through symlinks; combine independent product outcomes solely to fit the file limit; or change the installed memory format merely to record another authorized feature.

## Rationale

The representation is fixed by an authoritative runtime contract and has one responsibility: storing indexed feature details. Its entry count measures the number of planned outcomes, not production-code cohesion. Consistent applicability with the other flat memory registries resolves a genuine contract conflict without changing source-directory discipline or inventing a hierarchy the validator cannot consume.

## Consequences

Adding a valid indexed Plan detail is no longer blocked solely by registry length. Every detail remains subject to memory indexing, required sections, status/dependency validation, file-size policy and architecture registration. Source directories retain the existing numeric limits. Reassess this exception if the authoritative memory format later permits a meaningful different layout.
