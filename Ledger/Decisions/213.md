# D213 — Let the user approve changes of enforcement files

## Context

The bypass audit of 2026-11-19 (B157, group B) traced how an agent switches off the rig's checks from inside its own
session: it replaces the launcher, edits or unmarks the Git hooks, removes the agent hook registrations, adds a shell to
the `just write` programs, adds a recipe that runs any shell text, sets `core.hooksPath` in `.git/config`, moves the pin
back to an old installed runtime, or forges the route state so that required skills only advise. The same agent
legitimately develops these files in the rig and adds catalog commands by the develop-tools skill. On 2026-11-19 the
user was offered two ways to bring an intended change in: only the user changes these files, or the agent prepares the
change and the user confirms it with `! just approve`, a command the agent cannot run. The user chose the second.

## Chosen

- A protection set is built once with the configuration: `.git`, `justfile`, `.agentrig/just`, `.claude/settings.json`,
  `.codex/hooks.json` and `.codex/config.toml`, the modules `project.yaml`, `git.yaml`, `commands.yaml` and
  `hooks.yaml`, `bin` and `hooks` in the service directory, `reminders` and `approved` in the runtime directory, every
  path in the new setting `hooks.protected` and the pin named by the new setting `git.pin`. A path touches the set when
  it lies in an entry or contains one.
- The agent hook refuses an edit whose target touches the set, and a catalog command with project access, such as
  `just write`, whose operand does. Git is checked only for the operands of `rm`, `mv`, `restore` and `checkout`, so
  approved files can be staged and committed. For other programs every word and the value after `=` is cut before its
  first glob or expansion character, or entirely when it starts with `~`, and resolved; a word that cannot be resolved
  refuses with its cause. Both refusals carry one text that names the paths and the absolute path of the
  `propose-protected-change` skill.
- With invalid configuration the protected modules can be read but not edited, and the agent asks the user to correct
  them.
- The agent writes proposed content under `proposal/` in the runtime directory. The user runs `just approve`, which the
  hook refuses to agents: it applies the proposal, restores the previous files when the configuration then fails to
  load, records the content of every protected path that differs from the last commit, prints it and removes the
  proposal. `init` records the protected files it writes.
- On a feature branch the commit gate refuses a staged change of a protected path whose content was not approved. The
  pin needs no approval; the gate refuses a staged pin whose revision does not descend from the committed one.
- Unavailable or corrupt route state blocks a call like an unapplied required skill.

## Rejected

- Only the user changes the files: the rig develops them as product work, and catalog commands are routine tool work.
- Approving every pin: D051 lets the agent write the pin at the end of each branch without asking; a pin that only
  moves forward cannot bring an older runtime back.
- Protecting the whole runtime directory: proposals, jobs and check evidence live there and are written by the agent and
  the recipes.
- Checking every Git word: `git add` and `git commit` must stage and commit the approved files.
- Approving paths instead of content: an approved path could then be changed again without the user.

## Rationale

The approval is the one step the agent cannot perform, and the gate compares staged content with what the user
approved, so a change made around the hook still fails at the commit. The hook gives the agent the reason and the way
forward at the first attempt instead of at the commit. Settings for extra paths and the pin keep the mechanism portable:
the rig protects its development launcher and installer, while a consumer needs no setting.

## Consequences

Residual risks remain and are accepted: tests and `just candidate` run project code; unconfined Git commands such as
`switch`, `stash`, `rebase` or `cherry-pick` can bring a tree with other enforcement files; a write program can write a
path it does not name; a worktree shares the common Git directory; in the rig the agent develops the runtime that
enforces these checks. The rig sets `hooks.protected` and `git.pin` through `just approve` after the runtime that
knows these settings is installed, because the installed runtime rejects unknown settings.
