# D105 — A disallowed-path policy in the directory-architecture settings

## Context

B057 (research arc, `coverage-map.md` step 6 "fs-context"/disallowed-path; the r0 critique named
it the main Tier 1 candidate), selected as P064 under the user's /goal of 2026-11-04. A bare
`std::fs::x(..)?` returns an `io::Error` without the path, so an agent reading "os error 2" has to
hunt for the file; AgentRig itself had 43 such production sites. The directory-architecture rule
(D044, D076) already resolves every reference through aliases, local crates and `use` bindings to a
full external path, and the pure zone (D078, D083, D104) classifies such paths, but a project had no
way to declare that a path is forbidden outside its owner directory.

## Chosen

The rule settings accept `disallowed`: entries of `path`, `reason`, `replacement` and `allow` file
globs. During dependency analysis a reference whose resolved external path equals an entry's path
or lies under it at a `::` boundary (the D078 matching, shared `bounded` helper) from a file that
no `allow` glob covers becomes a finding at the reference line: "`<resolved path>` is disallowed
here: <reason>; use <replacement>". The policy sees only the resolver's external result, so an
unresolvable reference stays an incomplete-analysis finding and a local target, including a local
module named like the path, never matches. `lint-config-check` rejects a path that is not
`::`-separated identifiers, an empty reason or replacement and an invalid allow glob; `lint-rules`
describes the field, which is optional and empty by default.
The finding keeps the rule's level and repair skill because the message names the repair.
Delivery is two-phase (D051): the field and the check first, pinned, then AgentRig's own entries
once the `shared/fs` owner exists (B057 AC2–AC3).

## Rejected

A separate rule kind: the check is a policy over the resolver's output and belongs to the rule
that already owns external classification (D076, D078, D104). Matching source text instead of
resolved paths: aliases and `use` bindings would evade it. Python dotted paths: no current consumer
needs them, and a literal `::` path is rejected at configuration time instead of silently never
matching. Whole-crate denial or wildcards in paths: entries are exact namespaces matched at `::`
boundaries like D078. A per-reference `DECISION:` escape: the owner and the tests are exempted by
`allow` globs, not by syntax. A dedicated finding level or skill: the message carries the repair.

## Rationale

The resolver already produces the one fact the policy needs, the external path of each reference,
so the check adds a table lookup and a glob match rather than a second analysis (D059 syntactic
engine; D035 near-zero false positives, since an exact namespace matched at a boundary cannot fire
on a look-alike). Keeping the policy in the settings makes it project-declared, portable to
consumers and empty by default.

## Consequences

A project declares which paths are forbidden outside their owner and the gate holds it with a
message naming the reason and replacement. Delivered consumer configuration is unchanged; the
settings validation makes `rules` the thirteenth dependent of `shared/paths` (D079 budget 13).
AgentRig's own `lint.yaml` gains entries for `std::fs` and `std::os::unix::fs` together with
the `shared/fs` owner in the same card. Supersedes nothing.
