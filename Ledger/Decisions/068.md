# D068 — Deny ignored must-use results on the development gate

## Context

B028 (cluster 3 of the quality set, agreed 2026-10-29) asks that an ignored
result not be dropped silently (3.2) and that a swallowed error be caught (3.1).
In Rust both surface as an unused `#[must_use]` value and as `let _ = <Result>`.
An unused `#[must_use]` value is already a gate error through `-D warnings` in the
clippy profile (D060, the rustc `unused_must_use` lint), but `let _ = <Result>`
deliberately sidesteps it and the clippy lint that catches it is allow by
default. On 2026-10-30 the user chose to catch the Rust half of 3.1
(`let _ = <Result>`) on the development gate rather than ship it to init: the
syntactic engine infers no types and cannot prove the bound expression is a
`Result` (the D059/D035 barrier).

## Chosen

The clippy profile (D060) gains `-D clippy::let_underscore_must_use`: a
non-binding `let _` on a `#[must_use]` value, `Result` included, is a gate error,
so the author must consciously use the value — handle it, propagate it, or
discard it explicitly with `.ok()`. This is a development-gate profile extending
D060, not an init capability. The resource-handle discipline of 3.3 (a context
manager or RAII, ruff `SIM115`) is already provided by the enabled `SIM` group
in the ruff profile, so it needs no further change.

## Rejected

Shipping Rust `let _ = <Result>` to init as its own structural rule: it needs
type inference the engine omits by design (D059), or a syntactic flag on every
`let _ = <call>` that is false-positive-prone on deliberate drops of non-`Result`
values. Leaving `let _ = <Result>` unflagged, which contradicts 3.2. Also denying
`let_underscore_drop`, which catches dropping `Drop` values unrelated to error
discipline and is noisy.

## Rationale

`unused_must_use` (through `-D warnings`) and `let_underscore_must_use` together
close both ways to silently drop a `Result` in Rust without any type inference:
clippy reads `#[must_use]` from the signature syntactically. The development gate
is the right owner because clippy is already type-aware, whereas the rule that
ships to init (3.1) stays purely syntactic and high-signal (D035). `SIM` is
already selected, so 3.3 holds with no new code.

## Consequences

`let _ = <Result>` in AgentRig's own code is a gate error; its one occurrence
(`command_runner/jobs/process.rs`, best-effort teardown after a failed attach)
now uses `.ok()`. The check does not ship to init, unlike the 3.1 structural
rule. It extends D060 and supersedes nothing.
