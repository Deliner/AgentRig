# D099 — Extend discarded-result to a bare `.status()?;` or `.output()?;` statement

## Context

B059 (research arc, "discarded-outcome (b)", agreed 2026-11-02; implementation of the arc's
findings authorized by the user on 2026-11-04 via /goal) observes that a statement
`cmd.status()?;` or `cmd.output()?;` propagates only the error of launching the command and
drops the `ExitStatus` or `Output` it returns, so a command that ran and failed looks like a
success. `discarded-result` (D090) flags the bare `.ok();` statement and deliberately leaves
`expr.ok()?;` alone because there the `?` propagates the outcome; for `status()` and `output()`
the propagated part is not the outcome. The form is decidable from syntax alone (D035, D059):
an `expression_statement` whose expression is a `try_expression` over a `call_expression` whose
method is `status` or `output` with no arguments, the arity of `Command::status` and
`Command::output`. The repository's own calls (`shared/vcs/git.rs`, `shared/vcs/directories.rs`)
bind the value with `let`.

## Chosen

Extend the existing kind instead of adding one. `discarded_result` resolves the method under an
optional `try_expression`: `ok` keeps matching only the bare call, as D090 chose; `status` and
`output` match only under `?` and only with an empty argument list, outside test code, without a
`DECISION:` or `INVARIANT:` reference on the line directly above the statement, with the method
name as the finding's symbol. The descriptor and the `handle-discarded` skill name the form and
its repair (bind the value and check `status.success()` or `output.status`). No rule kind, skill,
configuration or oracle changes, so the I020 sets are unchanged and only the final pin applies
(D051).

## Rejected

A new rule kind: the violation (a silently dropped outcome) and the repair are the same as for
`.ok();`, so a second kind would multiply configuration and skills without a behavioral
difference. Matching `.status()?` or `.output()?` in any position: a `let` binding, an
assignment, a `.success()` chain and an argument keep or use the outcome. Matching any method
under `?`: for a method returning `Result<()>` the `?` already keeps everything that matters.
Matching a call with arguments: a user-defined `writer.output(data)?;` returning `Result<()>`
would be a false positive against the near-zero-false-positive bar (D035). Matching a call
without `?`: a bare `cmd.status();` drops a `Result` the compiler already reports as unused.
Resolving the receiver's type to `Command`: outside the syntactic, single-file engine (D059).

## Rationale

The bare `….status()?;`/`….output()?;` statement is the same decision as `.ok();` — throw the
outcome away — spelled with a `?`, so one kind with one repair skill is the lowest sufficient
mechanism. Keying on the method name, the empty argument list and the `?` keeps the check
near-zero-false-positive without a type frontend, and the change adds one helper on the existing
`expression_statement` dispatch.

## Consequences

A consumer's or this repository's bare `….status()?;` or `….output()?;` statement in non-test
Rust becomes a gate error on `init` and before commit; binding the value and checking it, or
recording a reference on the line directly above, passes. The `discarded-result` descriptor and
`just lint-rule discarded-result` name the new form. D090 keeps its statement and owners. It
ships B059 in full; it supersedes nothing.
