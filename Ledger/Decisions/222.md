# D222 — Lint lifts only the rule an exception names on the line below and reports an exception that lifts nothing

## Context

Under D065 and the rule decisions that reuse its mechanism, every detector checked on its own whether a `DECISION:` or
`INVARIANT:` reference stood above its site, each with its own adjacency: above the attributes of an item (D103),
above a macro for a static on its first line (D096), above an `#[expect]` covering a panic (D147). D219 gave an
exception the form `DECISION: DNNN RULE`, but a named exception still lifted every rule and a bare reference still
lifted any. B174 asks that an exception lift only the rule it names on the line under it, that a bare reference lift
nothing, and that an exception under which its rule no longer fires be a lint error.

## Chosen

- Lint parses the exceptions of each analyzed file once. A finding of a rule that accepts exceptions is lifted when
  the exception directly above the finding's reported line names that rule's ID. A bare `DECISION:` or `INVARIANT:`
  reference lifts nothing.
- Each rule kind declares whether it accepts an exception. The rules that read a reference before keep accepting one;
  threshold, structure and size rules, `hardcoded-secret`, `debug-artifact`, `cargo-rustflags` and the comment rule
  accept none. `lint-rule` shows this for each rule, and the finding of a rule that accepts one names the form.
- After all rules run, each comment rule reports every exception in its parsed files that lifted no finding, naming
  the decision and rule, at the comment rule's level and with its repair skill.
- Detectors no longer read references.

## Rejected

- A rule-aware reference check inside each detector: about fifty copies with their own adjacency rules could drift
  apart, and finding an exception that lifts nothing would need each detector to report what it lifted.
- Keeping the adjacency across attributes and macros: one line directly above the reported line is the only place a
  reader and the check agree on which finding a comment covers.
- Letting every rule accept an exception: a threshold or structure finding would become negotiable line by line.
- Reporting an exception that lifts nothing through the rule it names: the comment rule already owns comments, and an
  exception that justifies nothing is a comment without a purpose.
- Several rules in one exception: no current exception needs it, and it would add a list syntax.

## Rationale

The lift now has one owner that matches the rule ID, so a reference written for another reason cannot hide a finding,
and the same owner knows which exceptions lifted something, so a leftover exception is found when its line is fixed or
moved.

## Consequences

- An item's exception goes directly above the item's own line, below its attributes. A Python `except` is excepted
  above the `except` line, a crossed field above that field, and a static inside `lazy_static!` or `thread_local!`
  above its own line, which for a static on the macro's first line is the line above the macro.
- An enclosing `#[allow]` or `#[expect]` of a panic's Clippy lint covers the panic without a reference above it; the
  attribute itself is an `allow-justification` finding that needs its own exception.
- Only one rule can be lifted on a line.
- An exception in a file the comment rule does not select, such as a YAML or TOML file in the rig, is not reported when
  it lifts nothing.
