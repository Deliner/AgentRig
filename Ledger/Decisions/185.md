# D185 — The rig keeps no backward compatibility with projects set up by its older versions

## Context

On 2026-11-13, while discussing how the rig should catch a `-D` item removed from a project's Clippy command, the
draft showed that comparing the command with the profile of the installed rig breaks the gate of a project set up by
an older rig until the project adds the new lints. The user answered: «давай на старые проекты не обращать внимания.
То есть мы сейчас себе можем позволить вносить изменения, которые будут ломать старые. И им надо типа жестко
обновляться», «без обратной совместимости», «Пока у нас ни перед кем обязательств иметь вот обратную поддержку,
обратную совместимость и апгрейда нету и не будет. Пока я тебе явно не скажу». `init` already refuses a configured
project, and D033 retired the upgrade command.

## Chosen

- A change to the rig may break projects, configurations, command lists and runtimes created by an older rig. Such a
  project is updated by hand when it moves to the new rig, guided by the errors the new rig reports.
- No migration, upgrade path, transition period or compatibility shim is required for such a change.
- The choice holds until the user explicitly asks the rig to support older projects.

## Rejected

| Alternative | Why |
| --- | --- |
| Keeping older projects working through each change | no user of the rig is owed it; it would shape every check by past versions |
| Supporting the previous rig version for a transition period | the user states that no such obligation exists |

## Rationale

The rig's standard (D151) configures every project completely. Holding changes to what older projects already contain
would keep them on an older standard and add machinery that serves no current user.

## Consequences

A project set up by an older rig may fail the gate after the rig changes, and its owner repairs it. AGENTS.md states the rule for agents. Existing
compatibility behavior is not removed by this decision.
