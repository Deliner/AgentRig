# D080 — Flag a broad Rust allow attribute without a justifying reference

## Context

B036 (Набор II cluster C9, local consistency and self-description, agreed
2026-10-31) asks that a lint be silenced only with a recorded reason. A Rust
`#[allow(...)]` or crate/module `#![allow(...)]` attribute switches a compiler or
Clippy lint off for its scope: the gate stays green while the finding it would
raise goes unaddressed — a strong agent anti-pattern, since an agent can quiet a
rule instead of fixing the code. Whether an attribute is an `allow`, and whether
a reference sits on the line directly above it, is decidable from syntax alone
with no symbol or type resolution (D035). The `justified` reference-escape
mechanism already serves unsafe (D065), except-pass (D069) and disabled-test
(D074); an `#[allow]` is an attribute node, not a comment, so the comment ban
(D037) does not reach it.

## Chosen

Add an `allow-justification` rule kind (target file, error level), Rust-only: a
`#[allow(...)]` (`attribute_item`) or `#![allow(...)]` (`inner_attribute_item`)
whose attribute path is `allow`, without a `DECISION:` or `INVARIANT:` reference
comment on the line directly above it, is a finding. The Rust detector unifies
`#[ignore]` (D074) and `#[allow]` into one attribute dispatch keyed on the
attribute name, covering both outer and inner attributes, and reuses the existing
`justified` helper. The kind ships to consumers through `catalog::ALL` and the
delivered per-kind config template, with a repository rule over `.rs`. A new
repair skill `justify-allow` joins the `references` group — remove the allow and
fix the finding, or justify the suppression with a reference — and ships through
`project_setup/assets.rs`, so the delivered and live skill sets both grow by one
and stay equal (I020); the rule-kind set grows too.

## Rejected

Reusing an existing repair skill: `justify-unsafe`/`handle-error`/`justify-skip`
are construct-specific and the justification-rule family each owns a tailored
skill (D065/D069/D074). Flagging every attribute, or including `derive`, `cfg`
or `test`: only `allow` silences a lint, the others carry unrelated meaning and
`#[ignore]` is its own rule (D074), so keying on the `allow` name keeps the check
near-zero-false-positive (D035). A separate Python `# type: ignore`/`# noqa`
rule: those are comments already flagged by the comment ban (D037), so a rule
would double-cover. A regex over source text: a `#[allow(...)]` inside a string
literal would false-positive, whereas the AST dispatch distinguishes an attribute
node from a string.

## Rationale

The attribute is unambiguous and syntactic, meeting the high-signal, type-free
bar for the gate (D035). Keying on the `allow` name keeps false positives near
zero, mirroring the fixed-set philosophy of hardcoded-secret (D067) and dump-name
(D072); reusing `justified` (D065/D069/D074) is the lowest sufficient mechanism,
and folding the `#[ignore]` and `#[allow]` dispatch together consolidates two
attribute checks without changing D074's behavior. The repository's sole existing
`#[allow]` (a deprecated-FFI suppression in the macOS identity job) is resolved on
delivery — removed or carrying a reference — so the rule is green.

## Consequences

A consumer's or this repository's Rust `#[allow(...)]` or `#![allow(...)]`
without a reference on the line directly above becomes a gate error on `init` and
before commit; removing the allow and fixing the finding, or adding a `DECISION:`
or `INVARIANT:` reference on the line above, passes. The rule-kind set and the
skill set both grow by one and stay equal across delivery and repository (I020).
It extends the reference-escape family (D065/D069/D074) and the fixed-set
approach (D067/D072). B036's other points remain covered or norms: Python
`# noqa`/`# type: ignore`, commented-out code and bare `TODO`/`FIXME` stay under
the comment ban (D037), `println!`/`eprintln!` remain the D060 choice, and
directory self-description stays under D070. The second C9 core, a `dbg!`
debug-artifact rule, is recorded separately. It supersedes nothing.
