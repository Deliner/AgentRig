# D134 — A rule kind name is parsed by its family enum

## Context

D133 parsed a configured rule kind name only among `catalog::ALL`. On 2026-11-07 the first phase of P089 kept
`unchecked-deserialize` out of `catalog::ALL`, as D051 prescribes, and after the mid-branch pin to `84aba7f` the
installed runtime rejected the rule added to `.agentrig/lint.yaml`: "unknown variant `unchecked-deserialize`". The hook
then allowed only configuration edits until the rule was removed. Before D133 the derived `Deserialize` of the flat
enum accepted every variant.

## Chosen

Each family enum derives `Deserialize` with its kebab-case names. `Kind` parses a name in `catalog/mod.rs` by trying
the five families in order, and an unknown name still fails with "unknown variant `x`, expected one of" and the names
of `catalog::ALL`. A kind of a family that is not yet in `catalog::ALL` is accepted in configuration.

## Rejected

Adding the kind to `catalog::ALL` in the first phase: `catalog::ALL` ships the rule and its skill through `init`, and
the skill arrives in the second phase (I020). A derived untagged `Deserialize` on `Kind`: D133 rejected its message,
which names no accepted kind. Listing inert kinds in the message: no list of every variant exists besides the enums,
and a second list would drift from them.

## Rationale

The mid-branch pin of D051 exists so that the installed runtime reads the new kind before the repository
configuration names it.

## Consequences

It supersedes D133's parsing among `catalog::ALL` and its consequence that a kind outside `catalog::ALL` cannot be
named in configuration; the family split and the rest of D133 remain. An inert kind parses without appearing in the
message.
