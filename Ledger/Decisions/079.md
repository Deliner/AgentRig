# D079 — A directory may declare a dependents budget bounding its blast radius

## Context

D078 extended the architecture.yaml contract with an optional `zone` field. On
2026-10-31 the user agreed B035 (Набор II, C4 «локальность/радиус поражения»):
the agent-native core question is whether a module can change without reading
the whole world. Four of the cluster's five sub-points are already covered or
remain norms — cycles and back-edges are caught by the dependency graph, file
and function size by the `file-size`/`function-lines` rules, and a public
contract change without updating consumers needs tests or the rejected
type-frontend (D059). The one new statically checkable core is high incoming
coupling, which the user tagged as a contract check on the graph we already
build.

## Chosen

The architecture.yaml contract takes an optional `dependents` field: the maximum
number of distinct other directories allowed to depend on this directory. The
directory-architecture engine counts each contracted directory's distinct
dependents on the cross-directory dependency graph it already builds for cycle
detection, and reports a directory whose incoming coupling exceeds its budget at
error level, naming the actual count and the budget. A directory without the
field uses a default budget of 6. Same-directory references and
module-declaration edges are not coupling. This extends D078's contract field
set; D078's zone field and D044's type classification remain.

## Rejected

A boolean hub opt-out that disables the cap entirely, which would leave the
most-depended-on directories with no recorded or bounded radius; a global cap
with no per-directory override, which would false-positive the designed shared
hubs against the near-zero-FP bar (D035); counting coupling at the feature
boundary instead of the exact directory, an extra granularity the requirement
does not need; excluding test directories from the count, unnecessary because a
test depending on code is real incoming coupling and the hubs declare their
budget regardless; a new rule kind or skill, since the check extends the
existing directory-architecture rule (like D070/D076/D078), leaving I020
unchanged; a pretend invariant for the norm sub-points (norm-or-choice, D059).

## Rationale

Incoming coupling (fan-in) is the blast radius of a change: the number of
directories that must be understood when a directory's contract changes. It is a
syntactic property of the dependency graph the engine already computes, so it is
a genuine rule, not a norm. The default of 6 is the tightest threshold that
keeps every ordinary module in this repository green while the designed shared
hubs declare their real radius, so the discipline bites without churn and every
finding is actionable (D035). Declaring a hub's budget records its sanctioned
radius in the contract, which is exactly the agent-native goal: the blast radius
is visible and bounded where an agent reads it.

## Consequences

A directory bounds its blast radius by declaring `dependents`, or accepts the
default of 6. The field ships to consumers through `init` with no new rule kind
or skill, so the I020 delivery sets are unchanged. The repository declares the
radius of its six shared hubs (`shared/paths` and `shared/vcs` at 12,
`project_config` at 11, `shared/testing` and `shared/diagnostics` at 10,
`shared/yaml` at 9) and stays green. A later consumer that pushes a hub past its
declared budget is a finding, forcing a conscious budget change. Further zone
classes, coupling metrics or the action-at-a-distance and public-contract
sub-points are separate work.
