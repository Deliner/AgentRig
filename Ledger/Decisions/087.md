# D087 — Anti-over-complication ships as a coverage map, not a new rule

## Context

C8 (final cluster of Набор II, agreed 2026-10-31 for autonomous delivery) targets
over-complication: an agent adds a distinction, mode, layer of indirection,
speculative abstraction or dead branch that no current requirement supports. Of
the ten clusters this is the area AgentRig already covers most densely — the
shipped complexity-rule suite and the delivered `complexity-discipline` norm were
built precisely to hold the line against unnecessary complexity. The honest C8
task is to separate what is already enforced from what a new rule could add, and
to avoid the self-contradiction of shipping a redundant rule, which would itself
be the over-complication C8 warns against.

## Chosen

C8 ships as a coverage map recorded in this decision, backed by the existing
`complexity-discipline` norm. No init rule, rule kind, skill-for-a-rule or
invariant is added. Each decidable over-complication dimension already has an
owner that ships through `init`:

- function length → `function-lines`;
- nesting depth → `nesting-depth` (D061);
- branch budget → `branch-budget` (D063);
- parameter count → `parameter-count`;
- boolean flag parameters → `boolean-parameter` (D062);
- unnamed compound conditions → `named-if-condition`;
- oversized files and directories → `file-size` / `directory-entries`;
- junk-drawer catch-all directories → `dump-name` (D072);
- god-object fan-in, feature-type limits, dependency cycles and
  purpose-quality → `directory-architecture` (D070/D079).

Design discipline — choosing the lowest sufficient mechanism and rejecting
unsupported indirection, variability, lifecycle and machinery — rides the
`complexity-discipline` norm that `init` already delivers.

## Rejected

A new C8 rule. It would duplicate behavior the suite above already owns, and
adding redundant machinery is itself over-complication, so a C8 rule contradicts
its own purpose. One-variant-enum detection is syntactically reachable but
false-positive-prone (`#[non_exhaustive]`, FFI shims and forward-declared variants
are legitimate) against the near-zero-FP bar (D035). The residual smells —
speculative generality, single-implementation traits, needless wrappers and
layers, dead code — are semantic or need the type/data-flow frontend rejected in
D059, so they cannot be a near-zero-FP static rule. A pretend invariant is
forbidden by norm-or-choice.

## Rationale

Norm-or-choice: a rule fits a decidable, high-signal, near-zero-FP check; a norm
fits a behavior not statically checkable without false positives or
disproportionate machinery. The decidable surface of over-complication is already
covered by the suite listed above; the residual is semantic and is already
embodied by `complexity-discipline`'s "Reject changes that only appear to improve
the result" section and its lowest-sufficient-mechanism ladder. Mapping the
coverage is the minimal change that satisfies C8 without adding complexity, which
is itself the discipline C8 asks for.

## Consequences

C8 adds no rule kind, no skill-for-a-rule and no invariant, so the I020 delivery
sets stay balanced; no Project code or skill changes, so no stable.txt pin is
required (D051 applies only to branches that change Project). The coverage map
makes it explicit, for any application, that over-complication is caught out of
the box by the complexity-rule suite plus the `complexity-discipline` norm. With
this, Набор II (C1–C10) is complete. It supersedes nothing.
