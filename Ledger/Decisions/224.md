# D224 — Rule kind `test-in-code-file` keeps Rust test code out of code files

## Context

B177. On 2026-11-20 the user said that tests must check code only through what it opens and selected B177 with B175,
B176, B178 and B179 for autonomous delivery. D223 places test files in `tests/`, but test code inside a code file, an
inline `#[cfg(test)] mod tests { .. }` or a `#[path = "tests/x.rs"]` declaration in that file, stays a child module of
the file and sees all of its private items. The rig had such test code in four code files and in one example project.
The lint measurement reads one file's syntax, and `Code` carried only its text, so a detector could not tell a
directory entry from another file.

## Chosen

- A Rust policy kind `test-in-code-file` with default level error, repair skill `move-test-code-out`, the shipped
  exclude `**/tests/**` and no exception. Each outermost item marked by `#[cfg(test)]`, including `all(test, ..)`, or
  by an attribute whose last path segment is `test` yields one finding at the item's line, naming the item or, when
  it has no name, its syntax kind. Items nested in a marked item and further markers on the same item are not
  reported again.
- The only accepted item is a module declaration without a body in a directory entry `mod.rs`, `lib.rs` or
  `main.rs`, such as `#[cfg(test)] mod tests;`.
- `Code` carries the file path with the text; the entry file names are one constant shared with the lint-structure
  units.
- `relocate-tests` declares moved test files from `tests/mod.rs` under the entry, and `testing-discipline` lists the
  rule for its public-surface and back-door points.
- Delivery takes two phases with a mid-branch pin (D218); until the repository configuration names the kind, `init`
  leaves it out so its output matches the rig (I023).

## Rejected

- Accepting a test declaration with a `tests` path in any file: the test module stays a child of that file and sees
  its private items, which is what B177 removes.
- Accepting an inline test module in a directory entry: its tests still read the entry's internals in place, and the
  test code grows inside the file that names the directory's parts.
- Accepting an exception: a test that needs a private item signals a missing open function or dead code, and opening
  an item only for a test is the defect the skill forbids.
- Reporting every test function inside a reported module: one move repairs the whole module, so one finding per
  outermost item names the cause once.

## Rationale

A test module declared in the entry is a child of the directory module: it sees the entry's items and what each file
opens to the directory with `pub(super)` or wider, the same surface the other files of the directory use. Tests
written against that surface survive renaming, splitting and inlining inside a file, and the one accepted form keeps
the module tree and `tests/` in agreement.

## Consequences

A project gets one error per outermost test item in a code file, and tests that read private items are rewritten
through open functions. A file gated by an inner `#![cfg(test)]`, an attribute under `cfg_attr` and the `cfg!(test)`
macro are not measured. Other rules keep exempting the test context of a code file, which this rule now reports.
