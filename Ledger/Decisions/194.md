# D194 — `feature-start` carries uncommitted changes to the new branch

## Context

B147: after `init` the generated setup is not committed, and `feature-start NAME` refused with `working tree must be
clean`, so D190 told the first change to start with `git switch -c <prefix><name>`. The first branch thus needed a
different command from every later one. `feature-start` creates the branch at the tip of the base it runs on, so Git
changes no file when it switches, and the refused changes could not have been lost.

## Chosen

On the base without a pending merge or rebase, `feature-start NAME` creates the feature branch at the base tip and keeps
uncommitted and untracked changes in the working tree and index, so they continue on the new branch. A branch other
than the base, a pending operation, an invalid name and an existing branch are still refused, and nothing changes.

## Rejected

| Alternative | Why |
| --- | --- |
| Keep the clean-tree refusal and document `git switch -c` | the first branch keeps needing a different command |
| Allow pending changes only when they are the `init` setup | a second case with the same safe behavior |
| Stash the changes, switch and apply them back | switching at the same commit already keeps them; a stash adds a failure point |
| Commit the setup on the base first | the setup would reach the base without the gate, as D190 rejects |

## Rationale

The refusal protected nothing: the new branch starts at the commit the changes are based on. Carrying them puts work
done on the base on a feature branch, where the gate and `feature-merge` take it to the base.

## Consequences

The first change after `init` starts with `just feature-start NAME`; D190's consequence naming `git switch -c` is
superseded and the rest of D190 remains. `feature-merge` still requires a clean tree except State (D191).
