# D125 — A disallowed entry lists methods whose propagated errors are findings

## Context

B078 (from the agent-error research, class C3; selected by the user 2026-11-07, which leaves the VAC order to
delivery). The D105 policy matches resolved paths, so `std::fs::read_to_string(path)?` outside the owner is a
finding, but the method form `path.canonicalize()?` resolves to a method of a local value and passes. After the move
to `shared::fs` in 324326e a `root.join(value).canonicalize()?` remained whose error "No such file or directory (os
error 2)" named no path; only the B065 critique found it. On the research HEAD `ff23ad9` 15 lines with 16 calls
outside `Project/shared/fs` propagated such an `io::Error`, four of them inside `ensure!` arguments. voxel-rust has
about 25 domain calls `world.metadata()`, none of them under `?`.

## Chosen

A `disallowed` entry accepts optional `methods`, a list of Rust identifiers. The Rust source extraction records
every method call without arguments whose result goes directly to `?`, or whose result is converted by
`.map_err(Into::into)`, at the line of the method name. Inside the token tree of a macro invocation the same token
shapes, `. name ( ) ?` and `. name ( ) . map_err ( Into::into )`, are recorded too. Python sources record none.

During dependency analysis the first entry that lists the method name and whose allow globs do not cover the file
gives the finding "`.<method>()` with its error propagated is disallowed here: <reason>; use <replacement>". The
receiver type is not resolved: the match is by name. `lint-config-check` rejects a method that is not a nonempty
Rust identifier; `lint-rules` describes the field, which is empty by default.

Delivery is two-phase (D051): the field and the check first, pinned; then AgentRig's `std::fs` entry lists
`canonicalize`, `read_dir`, `metadata`, `symlink_metadata`, `read_link` and `try_exists`, the `shared/fs` owner gains
the missing wrappers, and every site calls the owner.

## Rejected

Resolving the receiver type: the engine is syntactic (D059) and has no types; the propagation condition alone kept
both trees free of false positives. Flagging every call of a listed name: the voxel-rust domain calls would all fire,
while the path is lost only where the error propagates unchanged. Handle methods such as `write_all`, `sync_all` and
`read_to_end`: they serve stdin and stdout too, and no repair concerned them. A separate rule kind: the D105 entry
already owns the reason, replacement and allow globs per namespace. Ignoring macro arguments: a quarter of the
AgentRig sites sit in `ensure!`. Other converters such as `map_err(Error::from)`: no site used them, and an unknown
function may add the path.

## Rationale

The error loses its path exactly where it propagates unchanged; a result that is matched, discarded with `.ok()` or
mapped by a named function stays with the caller's context. Matching a syntactic shape keeps the check one walk over
the parse tree that the analysis already performs.

## Consequences

An agent cannot bypass the filesystem owner by rewriting a function call as a method call. A domain method with a
listed name under `?` becomes a finding too; allow globs or a different method name resolve it. The delivered
consumer configuration is unchanged. It extends D105 and supersedes nothing.
