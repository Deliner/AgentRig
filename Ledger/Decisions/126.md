# D126 — A returned `.success()` of a process status that never reads `.code()` is a silent error

## Context

B076 (from the agent-error research, class C1; selected by the user 2026-11-07, which leaves the rule shape to
delivery). `git merge-base --is-ancestor` exits 0 for yes, 1 for no and 128 for an error. `Ok(Command…status()?
.success())` in a function returning `Result<bool>` turns the error into the answer no, and that no allowed a branch
deletion: fixed in 50853e0, returned in fff5e18 and fixed again in 04e7200. `discarded-result` (D099) flags only a
bare `.status()?;`, and its skill advised checking `status.success()`, the incomplete repair; `silent-error` (D097)
flags only the `Err(_) => Ok(bool)` arm; clippy, Ruff and the compiler do not see the form. On the current HEAD of
AgentRig and voxel-rust the form does not occur: `shared/vcs` reads `status.code()` first. Three AgentRig files
outside the process owners build `std::process::Command` directly.

## Chosen

The `silent-error` kind gains a Rust form. A `function_item` whose literal return type is `Result<bool, …>` and whose
body reads no `.code()`, neither as a method call nor as the same token shape inside a macro argument, reports every
`Ok(<status>.success())` it returns as its tail or with `return`. `<status>` is `….status()?` or
`….output()?.status` over zero-argument calls, or an identifier bound by a `let` to one of them. A closure or a
nested function ends the search for returns. The finding sits on the line of the return or of the `Ok`, with the
symbol `success`; a
`DECISION:` or `INVARIANT:` reference on the line directly above, or test context, keeps it. The shared descriptor
names the form and its repair: compare `code()` with the codes the command documents as answers and refuse the
others, or call an owner that does. The `handle-error` skill describes the form, and the `handle-discarded` skill no
longer presents `.success()` as a complete repair. On a scratch copy the candidate reports
`src/change_delivery_git.rs:151` at `04e7200^` and `src/scaffold_git.rs:15` at `50853e0^`, and nothing on the
current HEAD.

AgentRig's `disallowed` policy gains `std::process::Command` outside `Project/shared/vcs`, `Project/command_runner`
and tests. The integration callback takes VCS arguments, and the merge runs them through `Repository::command` and
`jobs::process::execute`; the doctor runs the installed binary through `sandbox::tracked` without a sandbox. No
configuration field changes, so only the final pin applies (D051).

## Rejected

A separate rule kind: the defect class, a failure turned into a verdict in a `Result<bool>` function, is the one D097
owns, and the Rust language directory already holds its 15 entries. Flagging every `.success()`: a plain `bool`
function, a `Result<()>` guard under `ensure!` and a command whose nonzero codes all mean failure keep the error or
answer no verdict. Resolving types: the engine is syntactic (D059). Requiring one specific comparison of `code()`: a
read of `.code()` in the body shows the author handled the codes, and neither tree needs anything finer. The form
where a process-launching call is collapsed by `.unwrap_or_default()`, `.ok()` or `.is_err()`: matching by function
name reached 25 % precision, and the single process owner replaces it for AgentRig. Python `returncode` forms: Python
here runs only in tests.

## Rationale

The detector matches the exact shape that recurred, and its exception is the evidence that removes the defect. Only
the two historical findings are confirmed; precision outside the two trees is not measured against the 90 % bar of
D110, so the form stays narrow: a launched status, a declared `Result<bool>` and no `.code()`.

## Consequences

The incomplete repair of the form is a finding, and the skills name the complete one. A `.success()` answer for a
command whose every nonzero code means failure needs a reference or a `.code()` read. In AgentRig a new process
launch outside the owners is a finding. It extends D097 and D099 and supersedes nothing.
