# D209 — Report a MAX fallback that is added to or multiplied

## Context

B165 under D151. The voxel-rust review at `2304625`, template 7, found an operand of `+` or `*` of the form
`unwrap_or(Int::MAX)` in three places: `src/core/world/edits.rs:285` and `src/host/scenarios/journey.rs:74, 75`. In
the two scenario coordinates the fallback is unreachable; in the queue byte count the fallback is reachable and the
addition loses the meaning of saturation, since `MAX + n` overflows, panicking in debug builds and wrapping in release.
The review warns that a ban on the whole syntax gives false findings. The card asks for a lint error on
`x.unwrap_or(T::MAX) + …` and the same with `*`, and a skill that handles the missing value or computes with
saturation. The rig's own code has one `unwrap_or(i32::MAX)`, under unary minus.

## Chosen

A Rust kind `max-fallback` at level error with the repair skill `saturate-or-handle`. It reports a binary `+` or `*`
whose left or right operand is a `.unwrap_or(..)` method call whose sole argument is `MAX` or a path whose last
segment is `MAX`. Test code is skipped, and a `DECISION:` or `INVARIANT:` reference on the line directly above lifts a
finding. The kind enters the runtime first, is pinned (D051) and is then enabled in the rig's `lint.yaml`, the catalog
and init with its skill.

The operand must be the call itself: `x.unwrap_or(MAX) * 4 + 1` is one finding, at the multiplication. The receiver's
type is not resolved, so a float `MAX` is reported like an integer one.

## Rejected

- Only the left operand, as the review writes it: `+` and `*` commute, so `1 + x.unwrap_or(MAX)` is the same overflow
  and a swap of operands would evade the rule.
- The compound `+=` and `*=`: the card names the binary operators; the compound forms are left to review.
- Every `unwrap_or(MAX)`: the review warns of false findings; a fallback that is compared, passed on, narrowed by
  `.min(..)` or added with `saturating_add` keeps its meaning as a bound.
- Subtraction and `MIN`: `MAX - n` does not overflow, and a fallback to `MIN` under `-` is not in the card.
- `unwrap_or_else(|| MAX)` and `map_or(MAX, ..)`: other spellings the card does not name.
- Include test code: an overflow in a test panics in a debug test build and shows itself, as D155 holds for a
  subtraction from a length.

## Rationale

`MAX` as a fallback says "no bound" or "too large to count". Arithmetic on it either overflows or produces a number
that is neither the bound nor a real count, so the code after it works with a value that means nothing. Handling the
missing value first, or saturating explicitly, keeps the meaning visible at the place it is decided.

## Consequences

In voxel-rust the kind reports the review's three sites, now at `src/core/world/edits.rs:309` and
`src/host/scenarios/journey.rs:74, 75`; the many other `unwrap_or(T::MAX)` sites, compared, passed on or narrowed,
stay unreported. A parenthesized operand, a compound assignment and a lazy fallback evade the kind and are left to
review.
