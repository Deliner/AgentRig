# D094 — Scan well-formed Rust macro bodies for the call-pattern rules

## Context

B045 AC1 (medium re-review finding, agreed 2026-11-01). The `panic-path` (D082),
`eager-fallback` (D089) and `disabled-raii` (D092) rules dispatch on real
`call_expression` and `macro_invocation` nodes. But tree-sitter parses a macro
invocation's argument list as an opaque `token_tree` and builds no expression
nodes inside it, so a flagged pattern written inside `json!`, `format!`, `vec!`,
`println!`, `assert!` and the like is invisible to the gate. The re-review found
`command_runner/jobs/mod.rs` computing `record.finished.unwrap_or(now()?)` inside
`json!(...)` — a genuine eager-fallback latent bug (the `?` propagates even when
`finished` is present) that the gate silently passed.

## Chosen

On the existing `macro_invocation` dispatch add `macro_body`: take the macro's
`token_tree` inner source text, wrap it as a call-argument list
(`fn probe(){call(<inner>)}`), re-parse it with the same tree-sitter Rust parser,
and only when the fragment parses without error run the three call/macro pattern
detectors — `panic_call` and `panic_macro` (panic-path), `eager_fallback` and
`disabled_raii` — over the re-parsed subtree, mapping each finding's line back to
the original source by adding the `token_tree`'s start row. The wrapping call
tolerates the comma-separated argument lists macros carry. The macro invocation's
`in_test_context` (D082) is checked once at entry, so a macro inside test-only
code is exempt; a `DECISION:`/`INVARIANT:` reference on the line directly above
the call inside the macro justifies it through the normal mechanism (the comment
is part of the `token_tree` and survives the re-parse). This adds no new rule
kind, repair skill, oracle or `lint.yaml` entry: the existing rules simply see
more, so the I020 delivery sets stay balanced.

## Rejected

Textual or regular-expression scanning of the `token_tree` for the patterns:
fragile, false-positive-prone and abandons the syntactic tree-sitter basis the
engine is built on (D059). Expanding the macro to inspect its real expansion:
that needs a compiler or macro engine and breaks the syntactic no-expansion
boundary (D059) — re-parsing the literal token text as Rust syntax is not
expansion. Scanning a macro body that does not parse as Rust (a DSL such as
`html!`): skipped, because a parse error means the tokens are not Rust
expressions and any node structure recovered from them would be unreliable, so
scanning them would breach the near-zero-FP bar (D035). Running the full
`inspect` dispatch over the re-parsed fragment (comments, credentials,
if-conditions, declarations, nesting): outside AC1's scope and a large
false-positive surface — only the three named rules apply inside macro bodies.
Recursively re-parsing nested macro bodies within a fragment: rare, out of scope
and it compounds the line-offset mapping, so a missed deeply nested pattern is
preferred to the added complexity and FP risk (D035). A mid-branch bootstrap pin
for this change: unnecessary, because it introduces no new rule kind for the
stable binary to deserialize from `lint.yaml`; the single final D051 pin carries
it.

## Rationale

The change stays inside the syntactic engine (D059): the macro body is re-parsed
as Rust syntax, never expanded. The parse-clean gate together with the existing
`in_test_context` and justification machinery keep it near-zero false positive
(D035) — measured across this repository the only finding the capability surfaces
is the genuine `jobs/mod.rs` eager-fallback bug. It reuses the three existing
detectors unchanged, adding one bounded traversal and an offset remap, so no new
rule kind or repair skill ships.

## Consequences

A `panic-path`, `eager-fallback` or `disabled-raii` pattern written inside a
well-formed Rust macro body in non-test code becomes a gate finding exactly as
the same pattern outside a macro would; a `DECISION:`/`INVARIANT:` reference on
the line directly above the call inside the macro, or test context, exempts it; a
macro body that is not valid Rust is not scanned. `command_runner/jobs/mod.rs` is
corrected during delivery to compute the `now()?` fallback lazily (via a `match`
on `record.finished`) so it no longer propagates on the value-present path. The
rule-kind and skill sets are unchanged, so the I020 delivery sets stay balanced.
It ships part of B045 (medium re-review); it supersedes nothing.
