# D090 — Flag a bare `.ok()` statement that discards a Result

## Context

B043 (Tier A of the workflow Rust-review, agreed 2026-11-01). A bare
`expr.ok();` statement converts a `Result` to `Option` and immediately drops it,
so a failure passes with no handling and no trace — the same silent swallow that
`silent-error` (D069) catches for a Python `except: pass`, but which
`silent-error` (Python only) and the strict Clippy dev gate (D060, which flags
`let _ = ...` but not `.ok();`) both miss for Rust. Whether a statement is a
discarded `.ok()` is decidable from syntax — an `expression_statement` whose
expression is a `call_expression` whose method is `ok` — with no type resolution
(D035), and `.ok()` exists as `Result::ok`, so the receiver is a `Result` with
near certainty. The review found `command_runner/jobs/process.rs` dropping
`child.kill()` and `child.wait()` this way.

## Chosen

Add a `discarded-result` rule kind (target file, error level), Rust only, on a
new `expression_statement` dispatch. The detector `discarded_result` fires when
the statement's expression is a `call_expression` whose `field` method is `ok`.
A `DECISION:`/`INVARIANT:` reference on the line directly above removes the
finding (justification mechanism, D065/D069/D082); test code is excluded by
`in_test_context` (D082) and the delivered rule's `**/tests/**` and `tests.rs`
excludes. Only the bare-statement form is matched: `let x = expr.ok();`,
`field = expr.ok();` and `expr.ok()?;` keep or propagate the outcome and are not
statements that discard it, so they are not flagged. Ships through
`catalog::ALL` with a new `handle-discarded` repair skill, so the rule-kind and
skill sets both grow by one and stay equal (I020).

## Rejected

Flagging an `Err(_) =>` match arm that collapses an error into a determinate
value (for example `change_delivery/git/mod.rs`'s `Err(_) => return Ok(false)`):
`Err(_)` legitimately means the error value is not needed in the vast majority
of arms, so flagging all of them is false-positive-prone against the near-zero-FP
bar (D035), and distinguishing a collapse-to-success from a genuine don't-care
needs data-flow (D059). The arm form is left a norm, and the one real instance
is reviewed by hand during delivery. Flagging `let _ = expr;` or `drop(expr)`:
the strict Clippy dev gate (D060) already covers `let _ =` on the development
side, and `drop` is an explicit, searchable choice; `.ok();` is the portable
form that neither catches. Flagging any `.ok()` as a value (`let x = foo.ok()`):
converting to `Option` and keeping it is a legitimate choice; only discarding it
as a statement is the smell. Removing the justification escape: a deliberate
best-effort call (a cleanup `kill().ok()` on an already-failing path) is
legitimate and can be justified, keeping the rule near-zero false positive.

## Rationale

The bare `.ok();` statement is a fixed, syntactic signal meeting the type-free
bar (D035). It closes the Rust gap in `silent-error` (D069) and the Clippy
`let _` gap, reusing the justification and `in_test_context` machinery and
adding only the `expression_statement` dispatch.

## Consequences

A bare `expr.ok();` statement in non-test Rust becomes a gate error on `init`
and before commit; handling the error, propagating it with `?`, or recording a
reference on the line directly above, passes. The `child.kill().ok();` and
`child.wait().ok();` statements in `command_runner/jobs/process.rs` are justified
or handled as part of delivery, and `change_delivery/git/mod.rs`'s
`Err(_) => Ok(false)` is reviewed for fail-open versus fail-closed direction. The
rule-kind set and the skill set both grow by one and stay equal across delivery
and repository (I020). It ships part of B043 (Tier A); the `Err(_) =>` arm form
stays a norm; it supersedes nothing.
