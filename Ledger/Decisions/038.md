# D038 — Keep project configuration in single-responsibility modules under .agentrig

## Context

The user stated on 2026-10-26 that configuration stays YAML but, instead of one
agentrig.yaml, lives in a `.agentrig/` directory of modular files, each with a
clear responsibility (Requests.md, part 1, item 8). Installation must stay
maximally simple, without backward compatibility, configuration updates or
migration (item 9). The configuration already had distinct sections: project
identity and paths, Git, command catalog, checks, hook routes and invariant
oracles. Lint policy was already a separate file.

## Chosen

The configuration directory is `.agentrig/` at the project root. The required
`project.yaml` holds version, runtime, frontend, config_skill, paths and
capabilities. Each optional module holds one section as its whole content:
`git.yaml`, `commands.yaml`, `checks.yaml`, `hooks.yaml` and `oracles.yaml`.
An absent module means the section's default; `project.yaml` cannot contain a
module's section. Schema errors name the module that holds the field. Lint
policy stays a separate file selected by paths.lint, by default
`.agentrig/lint.yaml`. init writes the modules; agentrig.yaml is neither read,
detected nor migrated.

## Rejected

Keep agentrig.yaml as a fallback or beside the directory; let any module hold
any section and merge them; repeat each section's key inside its module; make
the configuration directory configurable; tie it to paths.service.

## Rationale

A file name states its responsibility, so an agent reads and edits only the
module it needs, and the module does not repeat its own name inside. The
directory is fixed because the configuration cannot say where it is. One
representation without fallback leaves one thing to validate.

## Consequences

Consumer fixtures, guides and skills refer to the modules. This repository
switches its own configuration in a separate step: the installed runtime must
know the modules first, so the switch, the runtime pin and bootstrap happen
together. paths.service still locates the binary, hooks and runtime data.
