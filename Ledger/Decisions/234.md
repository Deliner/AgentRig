# D234 — AGENTS.md states the rig's purpose, and a rig mechanism binds to a point every project has

## Context

On 2026-11-22 the user asked whether the project's description is stored anywhere and asked to put it into AGENTS.md
and CLAUDE.md, so that every new session knows what is being built and why. The user gave two texts: a description
of the rig as a universal deterministic harness whose agent is free in engineering choices while the rig controls
the process and the acceptance of changes through quality gates bound to observable events, and a brief for finding
rig mechanisms, each with a binding point, a mechanism inside the harness, a part the project configures and its
enforcement, selected by one criterion: an idea that needs one project's domain is a project check, not a rig
mechanism. AGENTS.md held the code standard of D151 but not the purpose; README.md calls AgentRig a structural linter
plus the environment that applies it.

## Chosen

AGENTS.md and CLAUDE.md open with the purpose as the rig stands today. AgentRig is a deterministic harness in which AI
agents (Claude Code, Codex) develop a project autonomously for long without losing code quality or architecture, with
handlers for Rust and Python projects. The agent chooses the engineering and the rig owns the process: Plan, feature
branch, verified atomic changes, merge. Its hooks route agent edits and commands, its gate blocks a failing commit or
merge, and its protected files and runtime pin change only with the user's approval; VAC boundaries and acceptance
remain the agent's.

A rig mechanism binds to a point every project has, such as a Git event, an agent hook event or a configured path,
takes project rules from the `.agentrig/` modules and holds without the agent's cooperation. An idea that needs one
project's domain is a project check, not a rig mechanism.

## Rejected

The description as given: it states as facts what the rig does not do today. The agent still judges VAC atomicity
and acceptance, merge runs the tests the branch affects rather than a full run, archiving a completed card is the
agent's step rather than a gate, and handlers exist for Rust and Python only. An agent taking these as facts would
leave verification it owns undone.

The brief as a standing instruction: asking every session to propose mechanisms turns it from the selected Plan to
new ideas, while ideas reach Backlog only with the user's agreement and maintenance does not authorize product work.

The description only in README.md: agents read AGENTS.md at every start and README.md only when they look for it.

An invariant: the criterion selects ideas and has no observable predicate to test.

## Rationale

A session that knows what the rig is for weighs a change against that purpose from its first step. Binding each
mechanism to a point every project has and leaving project rules to configuration keeps the rig portable across
languages, frameworks and architectures, which a mechanism built on one project's domain would break.

## Consequences

A proposed rig mechanism is judged by the criterion; an idea that fails it belongs in a project's `.agentrig/`
configuration, such as a catalog command, a check or a hook route.

To keep AGENTS.md within its 70-line limit, its other sections drop details owned elsewhere: the discovery commands,
the summary of testing-discipline, the specific hook routes in `.agentrig/hooks.yaml`, Plan's reference to Backlog
acceptance kept by the memory skills and the launcher path described in `tooling/distribution/README.md`.
