# D227 — Rule kind `entry-use` reports uses of a directory entry by the directory's own code

## Context

B176. On 2026-11-20 the user chose that a directory entry is its table of contents: its parts, its API and its
wiring, while types live in files. The repair skill `refactor-large-directory` and the architecture README allowed
keeping types in the entry, and 17 directories looped through their `mod.rs`. A measurement of the rig found 26 of 83
entries used from inside, by 76 working files. The user selected B176 with B175, B177, B178 and B179 for autonomous
delivery and bounded it: the entry may hold wiring and API functions and need not be empty. The Python resolver
returned every package `__init__.py` an import passes as a target of the import, so `from jobs.job import Job` looked
like a use of `jobs/__init__.py`.

## Chosen

- A policy kind `entry-use` with target `directory`, default level error, repair skill `move-out-of-entry` and no
  exception. Like `file-cycle` (D225) it reads the dependencies that the enabled directory-architecture rules of the
  same configuration resolve, and the configuration check refuses an enabled `entry-use` without one.
- A use counts when its source lies in a selected directory outside test code and its target is the entry `mod.rs`,
  `lib.rs`, `main.rs` or a file with the stem `__init__` of the source's directory or of a directory above it, other
  than the source itself. A name re-exported by the entry resolves to the entry, so the re-export counts. Module
  declarations are not uses.
- A Python import resolves to the imported module and records each package `__init__.py` it executes on its way as a
  dependency of a third relation, initialization. The new rules do not count it as a use; the other rules count it as
  they counted these targets before.
- The finding stands at the using line and names the entry.
- `init` delivers the rule and the skill to Rust and Python projects. Delivery takes two phases with a mid-branch pin
  under the user's consent (D226); until the repository configuration names the kind, `init` leaves it out so its
  output matches the rig (I023).

## Rejected

- Keeping types in the entry, as the skill and README allowed: the entry becomes one more file of the implementation,
  and cycles among files pass through it unseen, since `file-cycle` leaves entries out (D225).
- Counting test code: a test may use the directory surface (B176 AC2).
- Counting the packages an import initializes: `from jobs.job import Job` runs `jobs/__init__.py` but takes nothing
  from it, so every import of a submodule would report each package on its way.
- Requiring an empty entry: the user bounded the rule to own uses of the entry.

## Rationale

Every entry reads the same way: what the directory holds and what it gives. Together with `file-cycle`, no cycle of
uses among the files of one directory remains, through the entry or around it.

## Consequences

Each own use of an entry blocks the commit until the use names the file that defines the item or the item moves out
of the entry into a file named by its meaning. A subdirectory that needs an item the entry would share takes it from
a sibling part, which keeps the directory graph acyclic.
