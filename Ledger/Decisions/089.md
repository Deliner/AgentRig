# D089 — Flag a `?` inside an eager fallback argument

## Context

B043 (Tier A of the workflow Rust-review, agreed 2026-11-01). The fallback
argument of `.unwrap_or`, `.ok_or` and `.map_or` is evaluated unconditionally,
before the receiver is known to be empty. When that argument contains a `?` (a
`try_expression`), the error propagates even on the common path where the value
is present: the function returns early or errors although a value was available
— a latent bug. Whether the eager argument propagates is decidable from syntax
(a `try_expression` inside the first argument subtree) with no type resolution
(D035). The review found `command_line/main.rs` and `structural_lint/cli.rs`
both writing `.unwrap_or(env::current_dir()?)`, which fails even when the user
passed an explicit `--root`.

## Chosen

Add an `eager-fallback` rule kind (target file, error level), Rust only,
extending the existing `call_expression` dispatch (D082). The detector
`eager_fallback` fires when the call's method (a `field_identifier`) is
`unwrap_or`, `ok_or` or `map_or` and the first argument subtree contains a
`try_expression`, stopping the search at a nested `closure_expression` — a `?`
inside a closure is deferred, not eager, so `map_or`'s second argument and the
lazy `*_else` closures are not matched. A `DECISION:`/`INVARIANT:` reference on
the line directly above removes the finding (justification mechanism, D065/D082);
test code is excluded by `in_test_context` (D082) and the delivered rule's
`**/tests/**` and `tests.rs` excludes. Ships through `catalog::ALL` with a new
`eager-to-lazy` repair skill (move the fallback into the lazy `unwrap_or_else`,
`ok_or_else` or `map_or_else` closure), so the rule-kind and skill sets both
grow by one and stay equal (I020).

## Rejected

Flagging any side-effecting or expensive eager argument, not just `?`: deciding
what is expensive or side-effecting needs type and effect information (D059) and
false-positives on cheap constructors, so only the syntactic `?`-propagation,
which is an outright latent bug, is flagged; the broader "prefer lazy"
preference stays a norm. Matching the lazy `*_else` closures or `map_or`'s
second argument: those defer evaluation, so a `?` there is correct, and the
search stops at the closure boundary. Removing the justification escape: a
fallback whose `?` is genuinely intended (the value-present path is unreachable)
can be justified, keeping the rule near-zero false positive, consistent with the
justification family.

## Rationale

The `?`-in-eager-argument node is a fixed, syntactic signal meeting the
type-free bar (D035). It catches a class of latent bugs — an error propagated on
the value-present path — that neither the strict Clippy profile (D060) nor any
size or structure rule sees, and it fixed two real bugs in this repository. It
reuses the `call_expression` dispatch and the justification and `in_test_context`
machinery, adding none.

## Consequences

A `?` inside the eager first argument of `.unwrap_or`, `.ok_or` or `.map_or`
becomes a gate error on `init` and before commit; moving the fallback into the
lazy `*_else` closure, or recording a reference on the line directly above,
passes. The two bugs in `command_line/main.rs` and `structural_lint/cli.rs` are
fixed as part of delivery. The rule-kind set and the skill set both grow by one
and stay equal across delivery and repository (I020). It ships part of B043
(Tier A); it supersedes nothing.
