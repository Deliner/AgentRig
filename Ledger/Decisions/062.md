# D062 — Ban boolean parameters; name the two modes

## Context

The user selected the code-quality set (clusters 1–8, B026–B033) on 2026-10-29
for dogfooded delivery. Backlog B029 sub-rule 4.2 asks that boolean parameters
be caught by the gate before review, purely syntactically, only on Project, as a
capability that ships to `init` (D053/I020). Rust and Python are the supported
languages. When the blanket rule was shown to flag 33 real boolean parameters
across the worker — mostly single flags on process, signal, sandbox, memory and
lint plumbing, plus parametrized tests — the user chose on 2026-10-30 the full
ban ("Полный бан, чиню все 33") over narrowing it to signatures with two or more
boolean parameters.

## Chosen

Lint gains the boolean-parameter rule kind for Rust and Python at error level. A
Rust parameter whose type is the primitive `bool` (not `Option<bool>`, `&bool` or
a named wrapper) and a Python parameter annotated `bool` or defaulting to `True`
or `False` are findings; struct fields, `self` and untyped parameters are not,
and closures are measured like functions when their parameters are typed. The
rule ships to consumers through `rules::ALL`, routed to the split-boolean-parameter
skill. Every flagged parameter in this repository is converted to a named type
whose variants state the two modes — an enum in Rust, a descriptive string label
in parametrized tests — built at the call site, never through a boolean-parameter
constructor.

## Rejected

Narrow the rule to signatures with two or more boolean parameters; keep a single
flag where it "reads fine"; drop a type annotation to silence the rule; model the
modes with a `bool`-parameter constructor or `From<bool>` helper, which would
itself be a finding.

## Rationale

A boolean argument is unreadable at the call site — `execute(cmd, true, false)`
hides what each flag selects — and a named type or label moves that meaning to the
declaration where the reader needs it. The blanket ban is principled, not weakened
to pass: each of the worker's 33 sites had a nameable pair of modes. Building the
mode inline (`if cond { Mode::A } else { Mode::B }`) rather than through a helper
that takes the banned `bool` keeps the rule self-consistent. The metric stays
syntactic, so it needs no type inference and keeps the gate fast (D035).

## Consequences

A boolean parameter becomes a delivery finding routed to split-boolean-parameter,
in the worker repository and in every consumer. The worker's process-execution,
signal, sandbox, memory-evidence, gate-selection, lint-mode, architecture-inventory,
agent-hook and template plumbing now carry named mode enums, and parametrized
tests name their modes with string labels. `Capture` lives in `command_runner::jobs`
with the executor that owns it, keeping the directory dependency graph acyclic.
Each named predicate bound to satisfy the rule stays compatible with the
named-if-condition rule (D017). Record and configuration struct fields remain
boolean for serde. Sub-rule 4.3 of B029 remains a separate later decision.
