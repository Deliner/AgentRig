# D151 — The rig sets the code standard and selects checks by the quality they produce

## Context

On 2026-11-10, after the assessment of two lists of Rust bans against AgentRig, the user stated how the rig and its
rules are developed. Earlier selections also weighed how much rig code a check matched and how much repair it needed:
D127 rejected zero-hit lints because they have no target code, D132 left existing consumer configurations alone
because `init` has no update path, and D137 refused to have `init` write and own a `clippy.toml` a project may
already have.

## Chosen

AgentRig sets the code standard. The standard is code kept for 20 years, AI-first and agent-native: clear at once,
well structured, with an architecture that minimizes corner cases, undefined states and places where errors can
appear. Lint rules, the Clippy profile and their repair skills derive from it. Code that does not conform to the rig
does not conform to the standard and is repaired.

A check is adopted and kept when it raises code quality, also when the rig has no code with the construct it
targets. Refactoring volume is no reason to reject a check that raises quality. The rig runs its checks on itself
and improves its code while it is developed. Earlier decisions are revised through successors when a better choice
appears.

The rig's main task is to configure any project completely as a controlled, deterministic environment in which an
agent cannot write code that the built-in linter rejects.

## Rejected

Selecting checks by their current hits in the rig: a construct the rig lacks today may appear later or in a
consumer, and the check then prevents it.

Rejecting a check that raises quality because the repair is large.

Recording the standard only in Requests: agents read AGENTS.md at every start, so the standard stands there.

An invariant with an executable oracle: the standard is a selection criterion without a predicate to test.

## Rationale

The rig's rules define what good code is for every project it configures, so its own code must pass them, and a
rule is judged by the quality of the code it requires, not by how much of the rig it touches today.

## Consequences

A check whose required form makes code worse still fails the standard, for example a syntactic rule below the
precision bar of D059 and D110 or a lint that turns ordinary operations into noise.

The rejection grounds of D127 that zero-hit lints have no target code, of D132 that `init` does not rewrite
existing configurations and of D137 that `init` would own a project's `clippy.toml` no longer reject a check. Their
alternatives are reopened and are re-decided by successors; until then the chosen behavior of each remains.

New rule kinds still pass through Backlog before Plan and need measurements, capability declarations, behavioral
verification and repair guidance.
