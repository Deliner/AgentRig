# D150 — Commit one runtime per platform behind a launcher

## Context

B086. A consumer project carried one AgentRig executable at `{service}/bin/agentrig`, and its Git hooks and Just
recipes run it from the working tree. voxel-rust had a Linux x86_64 executable on main and a macOS arm64 one on its
migration branch, so each machine ran a foreign executable on one side and `feature-merge` could not pass without
bypassing hooks. The card left to the user whether the executables are stored in Git or fetched at bootstrap; the
user's /goal of 2026-11-10 selected B086 with every other Backlog card and delegated such decisions to the executor.

Git 2.50 runs the reference-transaction hook for the HEAD update of `git switch` after checking out the target tree;
a scratch repository logged `prepared:0000… ref:refs/heads/master HEAD` for one switch. `feature-merge` switches to
the base before `git merge --no-ff`, so that hook runs whatever runtime the base tree carries.

## Chosen

- Store the runtimes in Git, one per platform, at `{service}/bin/PLATFORM/agentrig`.
- `{service}/bin/agentrig` is a constant POSIX launcher. It maps `uname -sm` to PLATFORM: Darwin becomes `macos`,
  Linux becomes `linux`, and the machine name follows as `uname` prints it, giving `macos-arm64` and `linux-x86_64`,
  the names of the release archives. It executes that runtime, or exits 2 and names the platform, the `bin`
  directory and the command `agentrig runtime-add`.
- `init` installs the launcher and its own executable as the current platform's runtime. The runtime derives the
  same name from the Rust target, reporting `aarch64` on macOS as `arm64`.
- `agentrig runtime-add` takes no arguments, loads the project and writes the launcher and its own executable as the
  current platform's runtime. Each file is replaced by renaming a 0755 temporary file. The same command converts a
  project installed with a single executable.
- The generated `tools.locations` and `tools.entries` cover `{service}/bin/**`, so the tools check accepts the
  nested runtimes.

## Rejected

Fetching the runtimes at bootstrap. It needs the network and a published artifact for every pinned revision, and a
revision would no longer run by itself on every platform it supports.

Creating the merge commit before switching to the base, with `commit-tree` and `update-ref`, so that a platform the
base lacks can integrate its own runtime. It replaces `git merge` in integration, loses its merge message and signing
configuration, can move a base checked out in another worktree, and still fails when the feature must first be
rebased onto the base, because the rebase checks out the base tree too.

A launcher generated per service with a relative path to the project root. `$0` already locates the launcher.

## Rationale

Committed runtimes keep one revision runnable offline on every platform it carries, which is what AC1 and AC2 ask.
The launcher is the only platform-dependent part, so a fake `uname` tests both platforms on one machine. Overwriting
an executed binary in place fails on Linux with ETXTBSY and can get the replaced binary killed on macOS, so
`runtime-add` replaces by rename.

## Consequences

- Each carried platform adds one executable to the repository history per runtime update.
- The first merge that brings a platform's runtime to the base runs on a platform the base already supports. After
  that, every carried platform commits and merges through hooks. voxel-rust's migration branch reaches main from
  Linux once its Linux runtime is added there.
- An existing project keeps `bin/*` in its tools module until it changes the pattern to `bin/**`; the tools check
  names the unregistered runtime until then.
- A system whose `uname -s` is neither Darwin nor Linux is named as `uname` prints it, which may differ from the
  Rust target name; supporting such a platform needs a mapping in both places.
- The fixtures run on macOS arm64 with a fake `uname`. A run on real Linux x86_64 is pending: the CI matrix or the
  user.
