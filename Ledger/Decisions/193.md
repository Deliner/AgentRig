# D193 — a read-only command runs directly where its directory refuses writes

## Context

B146: Codex with `-s read-only` in a project after `init` could not run `just read`, because creating the run directory
under the runtime `jobs` directory failed with `Operation not permitted`, so it could not read a required skill. Inside
such an agent sandbox the platform sandbox of D034 cannot start either: macOS refuses a nested `sandbox_apply`, and its
private temporary directory cannot be created. `lint`, `config-check` and `resume` write nothing and already ran there.
The read programs include `sed` and `find`, whose argument forms can write, so the platform sandbox is what keeps
`read` from writing; running without it is safe only where the environment itself refuses writes.

## Chosen

When a catalog command cannot create its job directory, a read-only command probes its working directory by creating
and removing a temporary file. Only when the operating system refuses that file with a permission error or a read-only
file system does the command run directly in that environment, without the platform sandbox, job record or run log,
with the rig's compiler flags; a summary view then reports the log as not kept. Every other outcome, a writable
directory, another probe error or a writable command, returns the job directory error and runs nothing.

## Rejected

| Alternative | Why |
| --- | --- |
| Run read-only commands unrecorded whenever the job directory fails | a runtime directory without permissions in a writable project would let `sed -i` write there unsandboxed |
| Detect an agent sandbox from variables such as `CODEX_SANDBOX` | agent-specific, and it does not say whether writes are refused |
| Run without the platform sandbox whenever it fails to start | a failed start does not show that writes are refused, as in a sandbox with a writable project |
| Keep the run log in a temporary directory | an agent sandbox without write access refuses writes there too |

## Rationale

The unsandboxed path follows only from the positive observation that the command's directory refuses writes, which is
the protection the platform sandbox adds; everywhere else behavior stays the same, so outside such an environment
every run keeps its record and log.

## Consequences

In a write-refusing environment `just read` follows that environment's network policy, and its runs appear neither in
`jobs` nor in `report`. Writable commands there still fail on the job directory. An environment that refuses writes in
the command's directory but allows them elsewhere lets a read program write those other places.
