# D101 — Flag an unnamed record nested in a generic or slice type of a signature

## Context

B054 (research arc, `coverage-map.md` step 4; the user's decision of 2026-11-02, item 2;
implementation of the arc's findings authorized on 2026-11-04 via /goal) observes that D088
catches a tuple only as the top-level type of a parameter or return, while the same unnamed record
wrapped in `Vec<(…)>`, `Option<(…)>`, `Result<(…), E>` or `&[(…)]` passes. D088 rejected reaching
into a generic because an unqualified nested tuple (a pair, a purely domain tuple) false-positives;
the agreed form narrows it to tuples of three or more elements with at least one primitive,
`String` or `&str` element — a row of a table, not a pair — which is decidable from syntax alone
(D035, D059): a tree-sitter `tuple_type` below a `generic_type` or `array_type` in the annotation
subtree, counted by its named children and their node kinds. The repository has no such tuple in a
production signature; its only one sits in a test module.

## Chosen

Extend the `tuple-as-record` kind (D088), without a new kind, skill or configuration change:
`record_signature` in `languages/rust.rs` now runs for `function_item`, `function_signature_item`
and `closure_expression`, and reports the declaration when a parameter type or the return type
is a top-level tuple (named functions only, as in D088) or nests, through a `generic_type` or
`array_type` container at any depth (a reference such as `&`, `&mut` or `Option<&mut Vec<…>>`
may sit in between), a `tuple_type` with at least three named children of which at least one is a
`primitive_type`, a `type_identifier` spelled `String`, or a `reference_type` over a
`primitive_type` (`&str`). A `DECISION:` or `INVARIANT:` reference on the line directly above the
declaration removes the finding (D065/D082); test code is excluded by `in_test_context` (D082) and
by the delivered rule's `tests` excludes; one finding per declaration, as before. The descriptor
text and the `name-the-record` skill describe the nested form. The rule's `lint.yaml` entry is
untouched, so only the final D051 pin is needed.

## Rejected

Flagging every nested tuple: pairs such as `Option<(A, B)>` and domain tuples such as
`(PathBuf, Config)` are idiomatic and would false-positive (D088, D035). Flagging a bare reference
`&(A, B, u8)`: D088 rejected unwrapping a reference, and the agreed form concerns a tuple hidden
inside a container type; a bare tuple reference remains unflagged. Flagging tuples in `type`
aliases and struct fields: outside the signature positions that carry the record-evasion smell
(D088). An arity or element-kind knob: a configuration dimension with no second required behavior.
A second finding for a tuple nested inside a flagged top-level tuple: one finding per declaration
already names the site.

## Rationale

The container-and-arity form keeps the near-zero false-positive bar (D035) while closing the
evasion D088 left open; it reuses the `declaration` dispatch, the justification escape and the
test-context walk, adding only a subtree walk of the annotation. Closures join the nested form
because a closure parameter typed `Vec<(…)>` hides the same record, while D088's top-level
exclusion for closures stays as decided.

## Consequences

A consumer's or this repository's non-test Rust function, signature or closure with a parameter or
return type that nests a three-or-more-element tuple with a scalar element inside a generic or
slice becomes a gate error on `init` and before commit; naming the record with a struct, or a
reference on the line directly above the declaration, passes. The rule-kind and skill sets are
unchanged (I020). It ships B054 in full; it extends D088 and supersedes nothing.
