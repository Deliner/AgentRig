# D214 — Let the user approve changes of check settings and the lint baseline

## Context

The bypass audit of 2026-11-19 (B158, group E) traced how one change weakens the checks that judge it: the gate reads
its settings from the staged change, so a catalog command whose argv becomes `--version`, a check whose `include`
becomes empty or whose `warning` becomes true, or a test map without the group that selects the affected tests passes
together with the code it should stop (E1); the same change can remove the test map entry that runs the rig's
difference test or add any entry to the differences it accepts (E2); and a hand-written lint baseline raises the
accepted error counts (E4). D213 lets the user approve changes of enforcement files with `! just approve`, a command the
agent cannot run, and protects the modules `project.yaml`, `git.yaml`, `commands.yaml` and `hooks.yaml`. Asked how an
intended weakening or a growing baseline should pass, the user answered «B 1» on 2026-11-19: the agent prepares it,
the user confirms it with `! just approve`, and the gate accepts only confirmed changes.

## Chosen

- The protected set of D213 also holds the modules `checks.yaml`, `tools.yaml` and `rust.yaml`, the lint configuration
  named by `paths.lint` and its baseline `<stem>-baseline.yaml` beside it. The agent hook refuses their edits and
  `just write` operands, and the commit gate on a feature branch refuses their staged change unless its content is the
  one the user approved.
- Without approval the commit gate accepts a staged lint baseline only when every pair's count stays within the
  committed count after renames, adding no pair, or when the change removes the baseline. A baseline that cannot be
  read is refused. `just lint-baseline` keeps writing the file; recording new errors needs the user's approval.
- `init` offers `just lint-baseline` together with `just approve` for the recorded baseline.

## Rejected

- Running the gate with the settings of the base or of the last commit: a stricter setting would not run until the
  merge, the gate would combine two configurations, and the weakened settings would become the base after the merge.
- Approving only the changes that weaken a setting: telling a weakening apart needs a comparison for every setting kind
  and every future one, while approving any content covers them all.
- Approving every baseline change: `just lint-baseline` lowers the counts after each repair, and a lower count only makes
  lint stricter.
- Protecting `oracles.yaml`: an oracle belongs to its invariant, whose change B158 lets pass with the decision that
  introduces it, so the memory history check owns it.

## Rationale

These settings decide what the gate runs and how strictly, so the change they judge must not be able to set them. The
approval of D213 is the one step the agent cannot take, and widening its set closes E1, E2 and E4 without a second
mechanism. A lowered baseline needs no approval for the same reason a forward pin needs none: it cannot weaken lint.

## Consequences

Every change of these settings, a stricter one too, waits for `! just approve`, and a lint rule enabled in a project is
a proposal. With invalid configuration the agent still repairs the lint configuration as D045 allows, and commits the
repair only with approval. The installed runtime enforces the wider set, so the rig's own settings follow it only after
the revision with it is pinned.
