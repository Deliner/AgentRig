# D108 — Acquire-before-poll on the reader's `exited` flag, published with Release

## Context

B062 AC5 (research arc; the user's /goal of 2026-11-04), delivered as P066 VAC-H. D095 introduced the shared
`exited` flag in `command_runner/jobs/streams.rs`: `execute` sets it through `Readers::mark_exited` the moment
`child.wait()` returns, and each reader thread's `wait_readable` consults it to end the drain once `poll` reports
no data. D095 records why the flag exists and what the drain does, not why the store is `Ordering::Release` and
the load `Ordering::Acquire`; the two sites carried no reference, so the choice was unreadable at the site (D037).
Writing this record exposed a second gap: `wait_readable` polled first and read the flag afterwards, so a tail
the child wrote and sealed with its exit between a timed-out `poll` and the load was never read — a narrow
scheduling window, but one in which D095's "every byte it produced is captured" did not hold.

## Chosen

`wait_readable` loads the flag with `Acquire` at the top of each iteration, then polls, and returns "stop" only
when that `poll` reported no data and the flag was already set before it; `mark_exited` stores `true` with
`Release` right after `child.wait()` returns. Release pairs with Acquire, so a load that observes `true` happens
after the parent observed the exit, and the `poll` that follows the load in program order is evaluated against a
child that has already written everything it will ever write; an empty `poll` then means the pipe holds nothing
of the child's. The flag is the only state published through the pair. Both sites carry `// DECISION: D108`.
D095's statement and detail are unchanged; this record extends them.

## Rejected

`Relaxed` on both sides: the flag would still become visible, but without the happens-before edge the stop would
rest on the `wait` and `poll` system calls acting as fences, which the Rust memory model does not promise.
`SeqCst`: no second atomic has an order relative to this flag, so a total order adds nothing and hides which
direction of synchronization is meant. A mutex or condition variable: heavier than one flag load per poll
interval by a thread that already blocks in `poll`. Keeping the poll-then-load order and polling once more after
a `true` load: the same guarantee with a second system call per stop. Leaving the sites unreferenced: the
choice stays unreadable where it is made.

## Rationale

Release/Acquire is the weakest pair under which D095's argument — the child has exited, so no more of its bytes
can arrive — holds in the language rather than by platform accident, and loading before polling is what lets
the pair carry that argument: the poll that decides the stop must come after the exit became a settled fact for
the reader. The cost is one fence per store and per load on weakly ordered hardware, once per job and once per
200 ms poll interval. The window is too narrow to reproduce deterministically, so the change is verified by the
existing behavioral drain test and by the ordering argument above, not by a new test.

## Consequences

The drain stops only after a `poll` that followed the observed exit, closing the tail-loss window; no other
behavior changes. The two `Ordering` sites in `streams.rs` carry `// DECISION: D108` and `memory-check` binds
them to this record, so changing the ordering or the load/poll order requires a successor decision. It closes
B062 AC5; with AC2–AC6 delivered on P066 and AC1 on P056, B062 is complete. Supersedes nothing.
