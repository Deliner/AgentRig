# D088 — Flag a tuple in a function signature as an unnamed record

## Context

B043 (Tier A of the workflow Rust-review, agreed 2026-11-01) asks that a
function signature not smuggle an unnamed multi-field record past the
`parameter-count` and `boolean-parameter` (D062) budgets by packing arguments
into a tuple. A tuple type in a parameter or return position is an anonymous
record: the positions carry no names, and several fields packed into one tuple
parameter count as a single parameter, evading `parameter-count`. Whether a
signature element is a tuple is decidable from syntax alone — a tree-sitter
`tuple_type` node in a parameter `type` field or in the function `return_type`
field — with no type resolution (D035). Test code legitimately returns or takes
a small tuple (a fixture pair), so Rust test code is excluded. The review found
`command_runner/sandbox.rs` and `change_delivery/gate/mod.rs` packing a flag and
data into a tuple parameter.

## Chosen

Add a `tuple-as-record` rule kind (target file, error level), Rust only. The
detector runs inside the existing `declaration` dispatch for `function_item` and
`function_signature_item` (not closures) and reports one finding per function
whose `parameters` include a tuple-typed parameter or whose `return_type` is a
tuple, through `record_signature`. A `DECISION:`/`INVARIANT:` reference on the
line directly above the function removes the finding, reusing the justification
mechanism (D065/D082); test code is excluded by the same ancestor
`#[cfg(test)]`/`#[test]` walk (`in_test_context`, D082) plus the delivered
rule's `**/tests/**` and `tests.rs` excludes. Only a top-level `tuple_type` is
matched: a unit `()` (a `unit_type`) and a tuple nested in a generic such as
`Option<(A, B)>` or `Result<(A, B), E>` are not flagged. The kind ships to
consumers through `catalog::ALL` and the delivered per-kind config template,
with a new `name-the-record` repair skill joining the `references` group through
`project_setup/assets.rs`, so the delivered and live rule-kind and skill sets
both grow by one and stay equal (I020).

## Rejected

Flagging a tuple anywhere (a `let` binding, struct field, type alias or generic
argument): a local `let (a, b) = ...` destructuring or a short-lived tuple
expression is idiomatic and not an API record, so it would false-positive; only
the signature positions carry the record-evasion smell. Unwrapping a reference
`&(A, B)` or reaching into a tuple nested in a generic: rare, and reaching inside
a generic needs more than the top-level node kind, raising false positives
without a clear smell. A threshold on tuple arity (flag only tuples of at least
N elements): a two-element tuple parameter already evades `boolean-parameter`
and `parameter-count` naming, and an arity knob is a configuration dimension
with no second required behavior. Removing the justification escape: a genuine
coordinate pair or a deliberate small tuple return is a recognized legitimate
case, so the reference escape keeps the finding near-zero false positive,
consistent with the justification family.

## Rationale

The tuple-in-signature node is a fixed, syntactic signal meeting the
high-signal, type-free bar for the gate (D035) and mirroring the fixed-set
philosophy of panic-path (D082). It closes a real evasion of `parameter-count`
and `boolean-parameter` (D062). Reusing the `declaration` dispatch, the
justification escape and the `in_test_context` walk adds no new mechanism.

## Consequences

A consumer's or this repository's non-test Rust function with a tuple parameter
or tuple return becomes a gate error on `init` and before commit; giving the
tuple a named struct, or recording a `DECISION:`/`INVARIANT:` reference on the
line directly above the function, passes. The rule-kind set and the skill set
both grow by one and stay equal across delivery and repository (I020). It ships
part of B043 (Tier A); it supersedes nothing.
