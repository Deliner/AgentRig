# D233 — A merge removes what Git ignores except the rig's state and the project's keep list

## Context

B204. Uncommitted files in the rig's repository took about 52 GiB and filled the disk to 99 %: Cargo builds, Python
environments, lint and test caches, about 220 old runtime revisions in `.cache/development` and the records of 65
thousand finished runs. The user removed them by hand and asked that every project with the rig do this after each
merged branch, keeping only what is marked explicitly. On 2026-11-22 the user selected the card: «Бери B204 в работу».
Before this choice `feature-merge` only stopped the merged branch's runs after the merge and removed no files.

## Chosen

- After a successful merge, push and the branch's run cleanup, and before the compaction instruction that stays last,
  `feature-merge` removes the entries that `git ls-files -z --others --ignored --exclude-standard --directory` lists.
  Git's own ignore semantics decide what is ignored, so tracked files and paths outside the root never appear.
- Kept at any depth of the walk: the approval record, the consent, the proposal mirror, the compaction requirement and
  the jobs directory, each at the location its owner gives; any entry named by the revision that `HEAD` commits in the
  configured pin, the installed pinned runtime; and the root-relative globs of the `git.yaml` setting `keep`, empty by
  default and changed like the module, through the user's approval.
- Finished run records, completed, interrupted or cancelled after the interrupted state is observed again, are removed
  and reported as one line; running, orphaned, starting, finishing and stopping records stay, so `just jobs` keeps
  showing live runs.
- Files are removed one by one, symbolic links without following them, and a directory only once it is empty; nothing
  is removed recursively. A `.gitignore` goes only together with its directory, so kept content does not become
  untracked.
- The output lists `removed ignored files, freeing SIZE:` and one line per removed entry with its size in binary units.
- An error while planning, such as an unreadable pin, an invalid glob or a failing Git or run query, removes nothing,
  says `merge succeeded; ignored files were kept: CAUSE; the next merge retries` and exits 1. A path that cannot be
  removed is named with its cause in `merge succeeded; could not remove PATH: CAUSE; the next merge retries` and the
  command exits 1. The merge stays done in both cases, and the next merge tries again.

## Rejected

- `git clean -X`: its exclusions are ignore patterns, so the rig's state and the pinned revision would be restated as
  patterns beside their owners, and it reports neither freed sizes nor per-path causes.
- Recursive removal of ignored directories: it would delete kept paths nested in them, such as the runtime state under
  `.cache/runtime` or the pinned runtime under `.cache/development`, and `recursive-deletion` (D102) reports it.
- A separate cleanup command: the card asks for removal after every merge without another command.
- A default keep list: the card keeps the list empty, so nothing survives without being marked.
- Keeping finished run records: their logs were part of the volume, and live runs are the ones a later task reads.
- Undoing the merge when a removal fails: the card keeps the merge done and retries on the next merge.

## Rationale

Git owns ignore semantics and each runtime record's owner owns its location, so the kept set follows them instead of
copies. Walking file by file lets a kept path survive at any depth and attributes each failure to its path, while a
plan that cannot be built removes nothing.

## Consequences

The first build and checks after a merge start from scratch unless the build directory is listed in `keep`. In projects
installed earlier, the first merge on the new runtime removes `.env` and other local ignored files that are not listed.
A merge whose removal fails exits 1 after merging, so an autonomous run reads the cause before the next card.
