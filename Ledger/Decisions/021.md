# D021 — Blocking language discipline

## Context

The user explicitly requires named-if-condition, function-lines and parameter-count to block delivery and all existing violations to be repaired. D017 introduced these rules with an advisory initial rollout.

## Chosen

Supersede D017's warning-only rollout in this repository and newly initialized consumers: named-if-condition uses error severity, function-lines allows at most 40 nonblank lines, and parameter-count allows at most 4 declared inputs under the existing counting semantics. Preserve selectors and repair skills. Refactor production code, tests and the benchmark without suppressions, new exclusions or raised limits.

## Rejected

Increasing limits, excluding tests, retaining warning-only enforcement, rewriting the analyzer to overlook violations, or compressing source lines to disguise oversized responsibilities.

## Rationale

Hard limits make the requested discipline enforceable at commit and integration. Cohesive functions, named branch reasons and explicit test cases preserve behavior while satisfying the same rules applied to consumer code.

## Consequences

The runtime retains configurable warning/error capabilities for explicit consumer policy, but ships blocking language defaults. Existing installed configurations are not silently rewritten. I017 exercises blocking defaults and accepted boundaries in Python and Rust; the repository gate checks all selected current source. Literal source snippets used to test invalid syntax and violations remain test data, as before.
