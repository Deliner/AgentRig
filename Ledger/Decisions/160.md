# D160 — Staged checks reuse cargo builds through recorded modification times and a dedicated target

## Context

P115 moved the rig's tests from Python to Rust. `check --staged` runs checks in a fresh `git checkout-index` export,
whose files all carry the export time. Cargo decides freshness by modification time, so every staged gate rebuilt the
test binary for memory-check discovery and for the test check, and Clippy checked the crate again: a commit that changed
only Ledger notes took 18.7 to 18.8 s against 14.2 to 14.8 s before the migration (B110). Old modification times alone
are unsafe in a cargo target that worktree builds share: cargo then takes a staged file as fresh against artifacts built
from different worktree content. Cargo's checksum freshness is unstable in Rust 1.98.1.

## Chosen

After loading the staged configuration, the gate takes the exclusive lock `<runtime>/staged/lock` until the run ends,
reads `<runtime>/staged/stamps.json`, which maps each path to its Git object and modification time, and gives each
exported regular or executable index entry its recorded time when the object is unchanged and the current time
otherwise; it then writes the new record. A missing or unreadable record reuses nothing. Commands of the staged run
receive `CARGO_TARGET_DIR=<runtime>/staged/target`, a target that only staged runs build into. The development
launchers and the test helper read the standard `CARGO_TARGET_DIR` instead of `WORKER_TARGET_DIR`, so the candidate
build inside the export lands in the same dedicated target. Worktree and `--revision` checks are unchanged.

## Rejected

A persistent export tree updated in place: it needs removal of stray files and detection of edits, and a cleanup of it
risks user data. A target inside the export: the gate's file inventory would walk it. Modification times borrowed from
the worktree or from index stat data: a staged file can differ from a worktree file with the same time. Cargo checksum
freshness: unstable. `WORKER_TARGET_DIR` set by the runtime: it names this repository's launchers, not a consumer's
build.

## Rationale

A file keeps an old time only while its staged object equals the object recorded with that time, and the dedicated
target holds only builds of staged content stamped this way, so cargo's time comparison stays a content comparison.
The lock keeps two staged runs from interleaving stamps and builds in one target.

## Consequences

The first staged run, and any run after the record is lost, builds from scratch. The dedicated target takes disk space
beside `.cache/worker`. A `git add` made by hand during a manual `check --staged` can race with the export; the
pre-commit hook runs under Git's index lock. The launchers honor a `CARGO_TARGET_DIR` already set in the environment.
