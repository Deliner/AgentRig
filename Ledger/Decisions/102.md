# D102 — Flag a recursive directory deletion without an owner's reference

## Context

B055 (research arc, `coverage-map.md` step 4; the user's decision of 2026-11-02, item 1;
implementation of the arc's findings authorized on 2026-11-04 via /goal) observes that a recursive
directory deletion is the most destructive file-system operation, and an agent writes it as easily as
`remove_file`: a wrong argument erases a working tree. The call is recognizable from syntax alone by
its name (D035, D059), like `.unwrap()` (D082) and `mem::forget` (D092): a tree-sitter
`call_expression` whose function is a `scoped_identifier` named `remove_dir_all`, a bare
`identifier` `remove_dir_all` or a `field_expression` whose field is `remove_dir_all`, so
`std::fs`, `tokio::fs`, a local wrapper and a method are all covered; macro bodies get the same
review through the D094 fragment scan. The repository has two production sites in
`command_runner/scratch.rs::cleanup`: it removes the disposable entries of the branch task area under
the runtime's `scratch/<branch>` directory (keeping `results`) and the directories of the branch's
finished scratch jobs under the runtime's jobs directory; both paths are built by that owner from the
runtime root.

## Chosen

Add the rule kind `recursive-deletion` (target `file`, level policy, Rust): the detector
`languages/recursive_deletion.rs`, called from the `call_expression` dispatch in `rust.rs` and from
the macro-body fragment scan (D094), reports every call whose callee name is `remove_dir_all` — the
`field` of a method call, the `name` of a scoped path or the bare identifier — outside test code
(`in_test_context`, D082) without a `DECISION:` or `INVARIANT:` reference on the line directly above
the call (D065); one finding per call, symbol `remove_dir_all`. The repair skill
`contain-the-deletion` says to delete through an owner that checks the path lies inside its own
area, or to justify the call with a reference. The two `scratch.rs` sites are that bounded owner's
deletions and carry a `DECISION: D102` reference. A new `kind:` ships in two phases with a
mid-branch pin (D051); the repository rule excludes `tests` paths like its siblings.

## Rejected

Flagging `remove_file` and `remove_dir`: each removes one entry and `remove_dir` fails on a non-empty
directory, so an argument mistake stays bounded; the agreed form concerns recursion. Resolving the
callee's origin and flagging only `std::fs`: D059 has no type frontend, and a wrapper or `tokio::fs`
deletes just as recursively. Checking the path prefix syntactically: not decidable from syntax; the
reference names the owner that checks it. Covering `rm -rf` inside shell strings: a different
surface (commands), not a Rust call.

## Rationale

Name-based detection keeps the near-zero false-positive bar (D035): every `remove_dir_all` call is
a recursive deletion, and the only open question is whether its owner is recorded. The
justification escape reuses the D065/D082 mechanics and the macro-body review reuses D094; the
detector is a separate module because `rust.rs` is at its size limit and the dispatch stays there.
The scratch cleanup is this repository's one owner, so the reference documents its boundary once.

## Consequences

A consumer's or this repository's non-test Rust `remove_dir_all` call, by path, bare name or method,
in source or in a macro body, becomes a gate error on `init` and before commit unless a reference on
the line directly above names the decision or invariant that bounds it. The rule-kind and skill sets
grow by one each (I020: `recursive-deletion`, `contain-the-deletion`). It ships B055 in full; it
supersedes nothing.
