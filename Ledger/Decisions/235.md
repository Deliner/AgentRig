# D235 — The rig has no ratchet mode: lint errors are repaired, not accepted

## Context

On 2026-11-22 the user proposed a card to remove the ratchet, «Он пока не нужен», approved B205 and selected it. Ratchet
mode (D123, refined by D139 and D140) let a `<config stem>-baseline.yaml` beside the lint configuration turn errors
within recorded counts per rule and path into warnings; `lint-baseline` recorded the counts, later only lowered them
and moved them across Git renames. D214 protected the baseline and let the commit gate accept it without approval only
when it lowered counts; `init` and the wizard offered it when existing files had errors; D197 let the hook pass
`just lint-baseline`. The rig had no baseline file of its own. D151 holds that code not conforming to the rig is
repaired, and D234 that the rig owns the standard projects follow.

## Chosen

- The runtime, the rig and the `init` template have no `lint-baseline` command, recipe or help entry; the runtime
  answers it as an unknown command, and the hook no longer passes `just lint-baseline`.
- Lint, the gate's lint check and the standalone `agentrig-lint` read no baseline: a `<stem>-baseline.yaml` left beside
  the configuration is an ordinary file, and every error stays an error.
- The protected set no longer holds the baseline and the commit gate has no case for it, so changing or deleting a
  leftover baseline commits without approval.
- After installation `init` and the wizard print the number of lint errors in existing files and that the gate refuses
  a commit while lint reports an error; they offer no way to accept the errors.
- This supersedes D123, D139 and D140, the baseline part of D214 (its protection, the lowering-only admission and the
  approval named in the `init` offer) and D197's passing of `just lint-baseline`.

## Rejected

- Keeping the mode unused: its code, the gate's special case and a protected path need maintenance, and a mode that
  accepts errors contradicts D151.
- Deleting or refusing a leftover baseline: D185 requires no migration, and a check of a file nothing reads adds a
  mechanism without a requirement.

## Rationale

The rig sets the standard and projects are brought to it; a mode that accepts a project's errors instead adapts the
standard to the project's state. Removing it removes code, a special case of the gate and a protected path.

## Consequences

A project with existing lint errors repairs them before the gate accepts a commit, or the user approves an exception
with its decision (D220). A project with a baseline deletes it and repairs the errors itself. `Repository::renames`,
used only by recording, is removed. A return of the ratchet needs its own card.
