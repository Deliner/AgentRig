# D118 — Warn on thread::sleep and block_on inside async code

## Context

B070 (idea from the 2026-11-06 interview; selected by the user's /goal
2026-11-07, which leaves the card's open questions to measurement at
delivery). `std::thread::sleep` inside async code stalls an executor thread,
freezing every task on a single-threaded runtime; a nested `block_on` panics
inside a tokio runtime and blocks the thread under futures. The compiler and
clippy accept both. The plan requires the async context to be decided by the
same mechanism as `guard-across-await` (D117). On the r8 corpus, 565 Rust files
mentioning `async` and `sleep` or `block_on` yield 6 findings, all matching the
criterion: 4 blocking sleeps in async functions of rustdesk and zed, and 2
deliberate cases, a test-support `block_on` and a debug action that hangs a
background executor on purpose.

## Chosen

A new rule kind `blocking-in-async` with the repair skill `await-not-block`,
shipped at `warning` through the descriptor's default severity (D117). A call
whose path ends in `thread::sleep`, a bare `sleep` imported in the same file
from a `thread` module, or a function, turbofish function or method named
`block_on`, is a finding when its nearest enclosing scope boundary is an
`async fn` or an `async` block. Closures, including async closures, and plain
functions are boundaries that end the async context, so
`spawn_blocking(|| thread::sleep(..))` and a nested helper `fn` are not
flagged. Test code is excluded like the neighboring rules, and a `DECISION:`
or `INVARIANT:` reference on the line directly above the call justifies a
deliberate case. The symbol is `sleep` or `block_on`.

One module `async_context.rs` owns the scope boundary used by both rules:
`guard-across-await` stops its `.await` search at a boundary, and this rule
reads the nearest boundary above the call. Their tests share one file. The
kind and the skill grow together (I020) through a two-phase delivery with a
mid-branch pin (D051).

## Rejected

Error level: a type's own `block_on` method that does not block cannot be told
apart without symbol resolution (D059). Treating an async closure body as async
context: the card names closures as boundaries without exception. Python
`time.sleep` in `async def`: ruff's ASYNC251 already covers it. Calls inside
macro bodies: not named by the card. Resolving aliases such as
`use std::thread::sleep as nap`: the card names a bare `sleep`.

## Rationale

Every element is visible in syntax: the callee's name and path, the file's
`use` declarations and the enclosing function or block. The corpus shows
near-zero noise, so a warning with a line-above justification fits the
remaining ambiguity. One boundary owner keeps the two async rules from
drifting apart.

## Consequences

A consumer's non-test async Rust that sleeps a thread or nests `block_on`
gets a warning on `init` and before commit, visible with `--warnings` (D049),
unless justified by a reference on the line directly above. D117 keeps its
statement; its `.await` search now uses the shared boundary. It ships B070 in
full; it supersedes nothing.
