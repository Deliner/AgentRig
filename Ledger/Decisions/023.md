# D023: Installation ownership receipt

## Context

The requested upgrade MVP must replace a release's stock runtime/assets, preserve project configuration settings and memory, and expose conflicts with local skill or adapter edits. Existing installations record no shipped-file baseline.

## Chosen

New installations include .worker/manifest.json with manifest format version, package version, project config schema and each shipped path's SHA-256, ownership and executable flag. Ownership distinguishes runtime, stock assets, project configuration, editable skills/adapters and memory. The receipt excludes its own checksum. File creation and receipt metadata share the existing executable classification.

## Rejected

Inferring that every existing file is still stock, treating project configuration or memory as disposable templates, and recording task lifecycle in the installation receipt. A checksum cannot supply missing historical contents by itself.

## Rationale

A compact baseline supports concrete upgrade comparisons while retaining one owner for installed metadata. The installer validates generated paths and existing-file collisions before mutation, including the manifest path.

## Consequences

A user's later edits leave the shipped checksum unchanged. New user files remain outside the receipt. Earlier installations without a receipt require an explicit trustworthy baseline reconstruction before upgrade; the absence of a manifest does not authorize replacement. I020 verifies the receipt against a real native installation.
