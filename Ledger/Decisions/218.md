# D218 — Move the runtime pin only at the user's approval

## Context

The installed runtime runs the agent hooks and the commit gate and, since D217, lints every rig change with the rules of
the pinned revision. D051 let the agent pin its own branch head without asking, and D197 made `just bootstrap HEAD`
install that revision and then write the pin; D213 let the gate accept a staged pin without approval when it descends
from the committed one. An agent could therefore move the judge of its later commits to code it had just written. B173
asks that every pin move wait for the user's approval, that the user see the source files the new runtime changes, and
that `just bootstrap` after a clone keep installing the pinned revision without approval.

## Chosen

- The setting `git.install` names the catalog command that installs a runtime revision; for the rig it is `bootstrap`.
  It must name a catalog command. The agent hook refuses that command with arguments, so an agent installs only the
  pinned revision, and names the protected change skill.
- `propose-pin REVISION` resolves the revision, requires it to descend from the pinned one, writes it as the proposal of
  the pin file and lists the source files changed since the pinned revision.
- `just approve` first runs the installer with a proposed pin; only after the install succeeds does it apply the
  proposal, which writes the pin, and record the approved content. A failed install leaves the pin and the proposal.
- The commit gate accepts a changed pin only with the content the user approved, and only when it descends from the
  committed pin.
- `bootstrap.sh` with a revision only installs it; without one it installs the pinned revision. The texts that told
  agents to pin without asking now tell them to run `propose-pin` and ask for the user's approval.

## Rejected

- Keeping the forward pin acceptable without approval and only refusing the installer in the hook: a pin written by
  any other route would still commit unseen.
- Approving the pin as content without installing it: the launcher fails when the pinned revision is not installed,
  so the pin must not move before the install succeeds.
- A separate install command for the user after the approval: one confirmation would become two, and the pin could
  point at a revision that is not installed between them.
- Letting the agent install a revision ahead of the approval: the install writes the protected runtime cache from code
  the user has not approved.

## Rationale

Moving the pin changes which rules judge later commits, so it is a change of enforcement like an edit of a protected
file (D213), and the existing proposal and approval already carry the user's confirmation. Running the install inside
the approval keeps the pin and the installed revisions consistent without a second command.

## Consequences

Each pin move waits for the user. A branch that changes Project ends with `propose-pin HEAD` and the user's approval
before `just feature-merge`, and a change that needs an earlier one in the installed runtime waits for an approval
mid-branch. The approval lasts as long as the install, a release build of minutes, so the user may run `just approve`
in a terminal. A project without `git.install` approves its pin as content. Tests and `just candidate` still run project
code unconfined, the residual D213 accepted. The rig adopts this in two phases: the user pins the revision that adds
`propose-pin` with the previous `just bootstrap HEAD`, then approves the protected settings and the installer script.
