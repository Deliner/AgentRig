# D112 — Ship a fork of tree-sitter-rust 0.24.2 inside AgentRig

## Context

B069 (research rounds 9 to 11; selected by the user's /goal 2026-11-07).
tree-sitter-rust 0.24.2, the last release of 2026-03-27, does not know part
of valid Rust. Such a file compiles but gets one `syntax` finding and no rule
findings. Of the 18,627 Rust files of the r8 research corpus, 838 are lost
this way. Three forms give 87% of the lost lines: `safe fn` and `safe static`
inside `unsafe extern` (42%), a macro named after a primitive type such as
snapbox's `str![…]` (33%) and a lifetime first after `dyn`, as in
`dyn 'static + Trait` (11%). Upstream has no fix in sight: issue #250 and
PR #256, which handles `safe`, have been open since February 2025;
`dyn 'static` is only mentioned in issue #229; `str!` was never raised.
AgentRig's own code has none of these forms; consumers gain.

## Chosen

A copy of the published crate tree-sitter-rust 0.24.2, tag `v0.24.2`, commit
`77a3747266f4d621d0757825e6b11edcbf991ca5`, crate checksum
`439e577dbe07423ec2582ac62c7531120dbfccfa6e5f92406f93dd271a120e45`, lives in
`Project/shared/syntax/tree-sitter-rust` beside its only consumer
`shared/syntax/mod.rs`. Its original manifest is kept, so the crate name,
version, authors, MIT license and `tree_sitter_rust::LANGUAGE` do not change;
`Project/Cargo.toml` takes it as a path dependency and it is not a workspace
member. The first commit holds the published files unchanged; the next one
holds our edit of `grammar.js` and the regenerated `src`. The edit takes the
`grammar.js` part of PR #256 unchanged for `safe` and `unsafe` items of
`unsafe extern` blocks, lets a macro invocation be named by a primitive type
as an `identifier`, and lets `dyn` take lifetimes joined by `+` before its
trait. The generator is tree-sitter CLI 0.26.13, the version of the runtime
crate, producing ABI 15; regenerating the unchanged grammar with it
reproduces the published `parser.c` except the metadata patch version, which
becomes 2 as in `tree-sitter.json`, and `src/tree_sitter/array.h`, which
neither `parser.c` nor `scanner.c` includes. The directory is excluded from
lint and typos as a whole. Clean clones, bootstrap, the gate, release and CI
build the committed `parser.c` without network access to any fork and
without the generator; only someone changing the grammar installs the CLI.

A new upstream release is taken only by copying it unchanged, repeating our
`grammar.js` edit, regenerating with the recorded CLI and repeating B069 AC2:
on the corpus, lint output for every file that parses with the release equals
the output with the release, and the lost files that our edit repairs stay
repaired.

## Rejected

Waiting for upstream: no release date, and PR #256 has waited since February
2025. Repairing the text before parsing: a workaround that shifts positions
and hides real syntax. Switching to rust-analyzer: every rule would be
rewritten. A Git dependency on a fork repository: builds would need network
access to it. A workspace member: the gate's Clippy denial of `unwrap` would
fail on upstream's `build.rs`. Generating the parser at build time: every
build would need the generator. A directory outside `Project`: bootstrap
archives only `Project`. The other 125 lost files, 14 small classes: B066.

## Rationale

The three forms are grammar gaps, not rule gaps, so the parser is the owner
to fix them. A vendored path dependency keeps the change reviewable as a
`grammar.js` diff and needs nothing new from builds. Lint output of parsed
files does not depend on the edit, which the corpus check makes measurable.

## Consequences

`syntax` disappears from most files with the three forms and their rules
apply as anywhere else; an `unsafe fn` in an `unsafe extern` block still
needs a justification, a `safe fn` does not. The repository carries 6.5 MB
of generated C. Grammar updates follow the rule above. Upstreaming the edits
is possible but not an obligation. It ships B069 in full; it supersedes
nothing.
