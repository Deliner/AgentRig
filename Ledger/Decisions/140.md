# D140 — lint-baseline moves accepted counts along renames Git detects against HEAD

## Context

B092. The lint baseline keys accepted error counts by path. Moving a file with accepted findings left its counts on
the old path, so `lint-baseline` treated the moved findings as new and the baseline had to be deleted and recorded
again, which D123 named as a consequence. The voxel-rust migration moved many files with accepted findings. The
user's /goal of 2026-11-10 selected B092 with every other Backlog card and left the choices to the executor.

## Chosen

When `lint-baseline` lowers an existing baseline in a Git repository with a commit, it asks Git for renames between
`HEAD` and the working tree with rename detection (`git diff -M HEAD`). Each count of the D139 limit, from the working
or the committed baseline, whose path Git reports as a rename source is moved to the rename target, keeping the larger
count when two limits meet on one path. The usual lowering then applies: a renamed file keeps its accepted counts, and
a finding added in the same change exceeds them and stays an error. Only file renames Git reports are followed;
directory pairs keep their paths. Lint, the gate and `agentrig-lint` read the baseline as before, so the move becomes
effective once the recorded file is staged.

## Rejected

Following renames in lint itself: every run would query history, and the standalone assessment and the gate's exported
trees would need the same history. Matching moved files by their findings: two files with equal counts would be
indistinguishable. Including untracked files in detection: Git reports renames only for paths it knows, and staging
the new path is the ordinary step of a move. Moving directory pairs by the renames of their files: a directory's count
does not follow any single file.

## Rationale

Git's rename detection is the project's own record that a path continued as another; reusing it moves exactly the
counts the reviewer sees moved in the diff. Moving the limit rather than the current counts keeps D123's rule that
recording never accepts growth.

## Consequences

A `git mv` of a file with accepted errors followed by `lint-baseline` records them under the new path. A move Git does
not detect, such as one with heavy edits below its similarity threshold, still needs a fresh baseline. It supersedes
D123's consequence that a rename needs a fresh baseline and extends D139's limit; the rest of D123 and D139 remains.
