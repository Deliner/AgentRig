# D120 — Error on boolean expressions of more than three operands

## Context

B071 (idea from the interview of 2026-11-07; selected by the user's /goal
2026-11-07, which leaves the threshold and the counting of parentheses and
`if let … &&` chains to delivery). The named-if rule (D017) requires one named
value in an `if` condition but not what stands behind the name, so
`let ready = …` can hold five operands; `while` conditions and `match` guards
are not checked at all. pylint and ruff (PLR0916) allow up to five operands
and only in `if`; checkstyle allows up to three operators; clippy has no
counting rule. On the r8 corpus, 18,627 Rust files, the bun tree, translated
by machine, gives 2,561 of the 3,918 expressions above three operands.
Outside bun, 21,136 expressions have two or more operands, 1,357 of them
(6.4%, about one per 4,700 lines) more than three and 240 more than five.
Counting every `let` binding of a let chain as an operand adds 250 findings
outside bun, nearly all chains of sequential bindings, the flattened nesting
that let chains exist for. AgentRig itself has 12 Rust expressions above
three and none in Python.

## Chosen

A new rule kind `boolean-expression` with the repair skill
`split-boolean-expression` in the `control-flow` skill group, a threshold rule
with error above 3 and no warning. One measurement per maximal expression of
Rust `&&` and `||` or Python `and` and `or`, wherever it stands: an `if` or
`while` condition, a `match` guard, a `let`, a return value, a call argument
or a comprehension filter. It sits on the expression's first line with the
symbol `expression`. Parentheses group operands without ending the
expression. A negation, comparison, call, closure or macro is one operand,
and an expression inside it is measured on its own. A `let` binding of a Rust
let chain is not an operand, while the chain's boolean conditions are. Macro
bodies are token trees and stay unmeasured. The measurement is
language-neutral in the shared measure module beside the named condition. Test
code is included, as for the other size limits. Two-phase delivery with a
mid-branch pin (D051); the repository's own 12 expressions are repaired in
the activation VAC.

## Rejected

Threshold five, as in pylint: the card's four-operand `while` must be found.
Warning level: the sibling limits on parameters, nesting and branches are
errors, and a hidden warning (D049) would leave the bypass of named-if
through a name open. Counting let bindings: 250 more findings whose repair
pushes back to nesting, and a binding cannot be named, which is why named-if
exempts it. Counting only mixed `&&` and `||`: the card's `while` example
uses one operator. Parentheses ending the expression: `(a && b) || (c && d)`
would read as three expressions of two and hide a four-part condition.
Separate Rust and Python detectors: the operator nodes differ only in kind
names, as for named conditions.

## Rationale

The operand count is visible in the syntax of both languages, and the
repair, naming groups of operands, is local and mechanical. The threshold
matches the card and the sibling limits of four parameters and four nesting
levels.

## Consequences

A consumer's Rust or Python expression of more than three operands fails lint
on `init` and before commit; a project can raise the threshold or override it
per path through configuration. Conditions inside macro bodies stay unseen.
named-if keeps its own requirement. It ships B071 in full; it supersedes
nothing.
