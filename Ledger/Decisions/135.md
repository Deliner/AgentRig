# D135 — A local bound by let from a parameter counts as testing it

## Context

D131 counted a constructor parameter as tested only when the refusing `if` condition, the `ensure!` condition or the
`then` receiver named the parameter itself. On 2026-11-07 a consumer probe set up by `init` for P089 wrote its checks
the way the shipped `named-if-condition` rule requires, `let reversed = start > end; if reversed { return Err(...) }`,
and `unchecked-deserialize` reported nothing. The same file with the conditions inline reported `Interval::new` and
`Port::try_from`. A project that follows the shipped configuration would never receive the finding.

## Chosen

A parameter is tested when the condition names it or names a local bound by a `let` with an identifier pattern whose
value names the parameter or an earlier such local, in source order within the constructor body. The refusal forms,
the stored-field requirement, the symbol, the level and the exemptions of D131 stay.

## Rejected

Leaving the detector unchanged: the rule would stay silent under its own shipped configuration. Data flow through
assignments, tuple or struct patterns and helper functions: the `named-if-condition` repair produces one plain `let`
per condition, and the other forms need wider analysis without a measured case.

## Rationale

`named-if-condition` moves every compound condition into a named local, so in conforming code the test of a parameter
passes through a `let`. Following those bindings keeps the measurement syntactic within one file (D059).

## Consequences

It supersedes D131's clause that the refusing condition names the parameter itself; the rest of D131 remains. A check
through a helper function stays unseen.
