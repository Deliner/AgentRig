# P017 — Последовательный аудит карточек по якорям и сложности

## Feature

По прямому поручению пользователя разобрать [B001–B016](../../Backlog.md)
по одной карточке за раз, используя обсуждённые детерминированные якоря.
Это аудит существующих требований и подготовка согласованных уточнений;
реализация перечисленных фич не выбрана.

Источник текущей работы — поручение в чате от 2026-09-10:
«по одной карточке за раз», проверить привязку к детерминированным ситуациям
и переусложнение. Цель рига — высокое качество разработки, при котором агент
занят продуктовыми задачами и не расходует время и токены на лишние процедуры.

## User capability

Пользователь видит, какую проблему качества решает каждая карточка,
что контролируется механически, где остаётся смысловая оценка и какие
обязанности агента можно убрать без потери требуемого результата.

## Acceptance

- Для текущей карточки разобраны её критерии: наблюдаемое событие или
  состояние, доступные факты, правило, действие обвязки, проверяемый
  результат и условие снятия блокировки, если она предусмотрена.
- Указано, от какой реальной проблемы защищает требование. Формальный
  контроль отделён от оценки смысла; чтение skill и наличие отчёта
  не объявляются доказательством качества.
- Проверены необходимость механизмов, повторное использование существующих
  владельцев, дублирование правил и затраты агента. Приоритет — самый
  простой достаточный путь с сохранением согласованных ограничений.
- Пользователь получает один компактный разбор: вывод, рабочую цепочку,
  конкретные пробелы и возможное упрощение. Поправки сначала показываются
  в чате; утверждённые изменения сохраняются по edit-backlog.
- Следующая карточка разбирается только после явного ОК пользователя по текущей.
  Если предложенные правки не подходят, обсуждение и доработка той же карточки
  продолжаются до ОК; отказ от варианта не означает пропуск карточки.
  Завершённый пункт списка означает завершение разбора, а не реализацию фичи.

**Порядок разбора**

Для каждой карточки: прочитать актуальный текст → сопоставить критерии
с якорями → проверить пользу и лишнюю сложность → предложить правки
→ дорабатывать их с пользователем до ОК → сохранить согласованный результат
→ перейти к следующей карточке.
Исходники читать лишь для проверки существенного предположения, а не
проводить полный аудит реализации каждой будущей фичи.

## Delivery

Работа начата в feature/backlog-card-review на a129830. Аудируются актуальные
тексты рабочей копии; предыдущие согласованные правки Backlog ещё не
закоммичены. Их содержание и идентификаторы критериев сохраняются.

Обновлённые B001–B016 показаны целиком в чате, утверждены пользователем
и сохранены с исходными идентификаторами критериев. B004 включает отдельно
согласованное уточнение К9 о параметрах правила для разных языков.
B006 сохраняет открытый вопрос контроля операций с неизвестными до выполнения
изменяемыми путями; его нужно разрешить перед реализацией.
B007 сохраняет открытые вопросы видимости, разрешения типов, макросов,
исключений по умолчанию и допуска при неполном анализе перед реализацией.
B008 сохраняет открытый вопрос языков первой поставки и распознаваемых
документационных форм перед реализацией.
B009 сохраняет достаточные инструкции существующего skill; приёмка его
применения на реальных условиях не выполнялась в рамках аудита.
B010 включает согласованное уточнение К4: сложную Bash-логику переносить
на Python, JavaScript или TypeScript с учётом языков и правил проекта;
ненужное подключение можно удалить. Формы косвенного подключения нужно
определить перед реализацией.
B011 сохраняет открытый вопрос регистра и составных расширений
перед реализацией.
B012 сохраняет необходимость проверить данные контекста, событие суммаризации
и доставку без блокировки для каждого клиента; поддержка пока не подтверждена.
B013 включает согласованное уточнение К2/К5: фиксируются замеченные проблемы
с последней подтверждённой суммаризации до фиксации, включая уже устранённые
с результатом; порог настраивается, 80% — значение по умолчанию.
B014 сохраняет три маршрута исполнения через существующий хук, прямой доступ
к встроенным средствам агента и проверку инструментов перед merge без новых
процедур на VAC. Правила распознавания, базовые вызовы, событие завершения
задачи и хранение результатов нужно определить перед реализацией.
B015 включает согласованное управление ревью через конфигурацию рига:
при отключении нет вызова модели или требования отчёта, остальные проверки
выполняются; ошибка включённого ревью препятствует merge. Реакцию gate
на неполный статический анализ нужно определить перед реализацией.
B016 включает согласованное расширение К9: устойчивые ID карточек и критериев,
согласованность заголовков, файлов и индекса, разрешение ссылок с учётом архива.
Способы обнаружения тестов, применимость прежних результатов и обработку
файлов без связи с проверками нужно определить перед реализацией.
Разбор всех 16 карточек завершён после явного согласования каждой в чате.
Проверка памяти и пробелов после последнего сохранения пройдена; текст B016
сверен с согласованной карточкой и уточнением К9. Предыдущие сохранения
B001–B015 также проверены при завершении соответствующих разборов.
