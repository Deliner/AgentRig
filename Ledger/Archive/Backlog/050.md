# B050 — guard-across-await: std-гард блокировки, удерживаемый через `.await` (Rust)

## Context

Межпроектный обзор (`rust-lint-mining` `wf_f2a6f63a-7ff`, 2026-11-01) показал в rustdesk
(`io_loop.rs:1486/1507`, причём `.await` — внутри тела макроса `allow_err!`) паттерн: гард std
`Mutex`/`RwLock` удерживается через точку `.await`. На однопоточном исполнителе это даёт дедлок, а
также делает future `!Send`. clippy `await_holding_lock` ловит это у пользователей clippy, но
переносимого правила нет. Собственный код AgentRig синхронный (нет `.await`), поэтому к нашему коду
неприменимо — ценность для проектов-потребителей с async.

## Proposal

Наблюдаемое поведение:

- **AC1 — гард, живущий через await.** `let`-связанный гард, чей инициализатор завершается
  `.lock()` / `.read()` / `.write()` (с опциональными `.unwrap()` / `.expect(...)` / `?` /
  `.unwrap_or_else(...)`, без `.await` в самом инициализаторе), за которым в том же блоке без
  промежуточного `drop` следует `.await` (в том числе `.await` внутри тела макроса), → находка.
  Уровень warn. Внешне похожее нарушенное состояние (сегодня): такой код молча проходит гейт.

**Границы и неизвестное.** Отклонено (не этот паттерн): варианты `block_on` / `spawn` / `join`.
Правило синтаксическое: распознаёт терминальный `.lock()/.read()/.write()` на гард-подобном
связывании и последующий `.await` в блоке; не проверяет тип блокировки через резолвинг (граница
D059) — отсюда уровень warn, а не err. Новый `kind:` → доставка двухфазная с мид-бранч пином
(D051). Новый decision — при доставке.

## Expected benefit

Потребитель с async-кодом не может незаметно удержать гард std-блокировки через точку ожидания
(носитель дедлоков на однопоточном исполнителе и `!Send`-future). Переносимо; на нашем
синхронном коде находок не даёт.
